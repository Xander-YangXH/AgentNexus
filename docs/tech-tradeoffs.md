# 与 Yuxi 的技术取舍对照

Yuxi 是一个团队长期迭代的企业级产品，基础设施按生产环境的规模和团队分工设计。AgentNexus 是 solo 开发、3-4 个月周期的简历项目，目标是**覆盖同样的能力广度**（RAG、知识图谱、多智能体、MCP/Skills、沙盒、多租户、Dashboard），但基础设施做了轻量化调整，避免把时间花在运维复杂度上而不是工程设计本身。

| 能力 | Yuxi 原版 | AgentNexus | 取舍理由 |
|---|---|---|---|
| 向量检索 | Milvus + etcd | Qdrant（或 Postgres + pgvector） | Milvus 生产级但运维重，Qdrant 单容器即可用，检索能力对 demo 规模足够 |
| 文档解析/OCR | MinerU + PaddleX + RapidOCR | pypdf / python-docx / unstructured | 自建 OCR 模型服务成本高，用轻量库覆盖大部分文档类型即可，图片密集型 PDF 可选接云端 OCR API |
| 任务队列 | ARQ + 独立 worker 容器 | 阶段 1-3 用 asyncio.Queue 单机版，阶段 4 升级到 ARQ + 独立 worker | 先把排队/持久化的语义想清楚，再引入真正的分布式执行，避免过早引入复杂度 |
| 工具沙盒 | 独立 agent-sandbox provisioner 微服务 | Docker SDK 在 worker 内直接起隔离容器 | 核心是"工具执行要隔离"这个设计理念，不需要复刻成独立微服务 |
| 多租户权限 | 用户/部门/资源级细粒度权限 + OperationLog | 用户/部门两级、基本可见性隔离 | 保留"权限在后端强制执行"这一原则，不做到企业级的权限矩阵配置界面 |
| Skills 生态 | 支持 skills.sh / 魔搭社区在线安装 | 配置文件形式的插件机制，本地/手动接入 | 在线安装是运营向功能，对简历项目价值不高 |
| 可观测性 | Langfuse 全链路 trace | 可选接 Langfuse，或自建简单的请求日志表 | 视时间富余程度决定是否接入第三方服务 |
| 知识图谱 | Milvus + Neo4j 双写 | 仅 Neo4j | 简化存储路径，突出图谱本身的抽取与查询能力 |

## 原则

1. 每一项简化都要在 `docs/decisions/` 里留一条记录，写清楚"如果以后要按生产级标准扩展，应该怎么改"——这样面试时能证明这是主动取舍而不是能力不够。
2. 不简化的部分：Agent 请求落库 → 排队 → 派发执行 → 状态推流这条主链路的正确性（幂等、可恢复、可观测），这是整个项目最有技术含量的地方，值得投入最多时间。
