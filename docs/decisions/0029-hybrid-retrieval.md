# 0029 - 阶段 7.5：混合检索（稠密向量 + 关键词，Qdrant 内 RRF 融合）

**状态**：已采纳（2026-10-25）。用户休息期间授权按推荐方案自主推进，选择由我按推荐方案决定，理由和数据写在下面，可以复核。

**背景**：0014 的评测集故意用"换一种说法"的问题（测语义理解），字二元组 BM25 只有 0.43，所以第一版不做混合检索，并写明"以后需要精确词（错误码、型号）时再评估"。0017 也把混合检索列为"等数据再定"。这次补上那类查询的评测。

## 一、实验（`backend/eval/eval_keyword_queries.py`，本地模型，零费用）
新增 20 个只含精确词的短查询，例如"429""CSV""72 小时""开户行""3 期免手续费"，每个只在一篇文档里出现。

**只有 30 篇文档时看不出问题**：10 个重排候选覆盖了三分之一的语料。线上的"向量 + 重排"已经是 1.00（只用向量时第一名 0.75）。

**加入 713 段干扰文本后**（本项目自己的技术文档，里面有很多"429""24 小时""CSV"之类的撞词）：

| 方法 | 精确词：候选召回 | 精确词：重排后第一名 | 精确词：前 4 | 换说法：第一名 | 换说法：前 4 |
|---|---|---|---|---|---|
| 向量 + 重排（原线上） | 0.70 | 0.70 | 0.70 | 0.90 | 1.00 |
| 字二元组 BM25 + RRF + 重排（原型） | 1.00 | 0.90 | 1.00 | 0.90 | 1.00 |
| **Qdrant 稀疏向量 + RRF + 重排（采用，线上实现实测）** | **1.00** | **0.95** | **1.00** | 0.90 | 1.00 |

- 原线上漏掉的 6 个精确词查询，**正确答案连向量召回的前 10 个候选都没进**，重排救不回来。
- 融合后换说法的问题不变差。
- 只有 30 篇时两种实现都是 1.00，也不变差。
- 延迟：Qdrant 里多一路稀疏检索，单次检索从 2.0ms 到 2.3ms（743 篇，50 次平均）。

说明：部分"漏掉"的干扰段落其实也相关。例如本项目文档里登录限流同样返回 429，所以"第一名"的数字偏保守。"候选召回"不受这个影响，是最干净的指标。

## 二、选项
| | A. Qdrant 稀疏向量 + 服务端 RRF（采用） | B. PostgreSQL 全文检索 + 应用层融合 | C. 不做 |
|---|---|---|---|
| 中文切词 | 自己切：字二元组 + 英文 / 数字整词，NFKC + 小写 | 需要 zhparser 等扩展，官方镜像没有；`pg_trgm` 对中文支持依赖区域设置 | — |
| 一次检索 | 一个请求：两路都带知识库过滤，Qdrant 内融合 | 两个系统各查一次再在应用里融合 | — |
| IDF | Qdrant 按整个集合计算（`modifier=IDF`），不用自己维护文档频率 | 数据库维护 | — |
| 代价 | 集合要有稀疏向量配置，旧集合需要重建索引 | 新扩展、两套查询 | 大语料下精确词查询约 30% 召回不到 |

## 三、实现
- `knowledge/keywords.py`：切词与稀疏向量。词用 CRC32 映射成维度。文档侧用 BM25 的词频饱和（k1=1.2、b=0.75、按固定平均长度归一），查询侧每个词权重 1，IDF 由 Qdrant 计算。
- `storage/vectors.py`：
  - 新集合带名为 `text` 的稀疏向量；
  - 写入时由分块原文生成稀疏向量；
  - 检索给了查询文本时用 `prefetch`（稠密、稀疏各取候选、都带知识库过滤）+ `FusionQuery(RRF)`；
  - 旧集合没有稀疏向量时退回只用稠密向量并记日志；是否支持每分钟复查一次，重建索引后不用重启。
- 检索服务把查询原文传给索引；融合后的分数是排名分，最终排序以重排为准。
- 升级已有部署：`docker compose exec worker python -m agentnexus.knowledge.reindex`（重算向量，本地模型不花钱）。

## 四、实现中发现的问题：重建索引在 api 容器里会清空索引
文档里一直写着"在 api 容器里运行重建"。阶段 5 起 api 的数据库角色受行级安全约束，没有"当前用户"时一行分块也看不到。这次按文档在 api 里运行：读到 0 个分块，建了一个空集合，**切换别名、删掉了旧索引**，开发环境的检索立即变空。在 worker 里重跑重建后恢复（24883 个分块）。

修复（两道保护，都有测试）：
- 启动时检查数据库角色：必须是超级用户、BYPASSRLS 或表的所有者，否则直接退出并提示在 worker 里运行；
- 新索引一个点都没有、而旧索引有数据时，不切换、删掉半成品、报错。

文档里的命令全部改为在 worker 里运行。教训：0023 引入 RLS 时没有回头检查"以全部数据为对象的运维命令"；而且破坏性的步骤（切换别名、删旧集合）之前缺少合理性检查。
