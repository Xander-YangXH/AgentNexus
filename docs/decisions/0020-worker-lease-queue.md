# 0020 - 阶段 4.1：独立 worker、任务队列与租约

**状态**：已决定（2026-10-22）。用户确认三项均按建议：PostgreSQL 租约队列、run 被接管后从 checkpoint 续做、一个 worker 服务执行所有任务。

**背景**：阶段 1~3 的后台任务（对话 run、文档入库、图谱构建）都在 api 进程里执行，靠“单进程假设”做启动恢复（0005）：
- run 被中断时，下次启动标为失败；
- 文档和图谱构建被中断时，下次启动改回 pending 重做；
- 只要有第二个进程，这套恢复就会误伤别人正在执行的任务；
- 向量化和对话在同一个进程里争 CPU：入库期间，重排从约 2 秒变成约 4 秒（0017）。

阶段 4 的里程碑之一是：**杀掉 worker 再重启，未完成的任务能被正确接管，既不卡死也不重复执行**。路线图原计划用 ARQ。

阶段 4 拆成三步：
- **4.1**：独立 worker + 任务队列 + 租约（本草稿）；
- **4.2**：工具、沙盒、MCP；
- **4.3**：多 Agent 编排、深度调研、产物下载、审批中断。

4.2 和 4.3 各自另写草稿。

## 一、实验：worker 崩溃 / 暂停时，任务怎么被接管
脚本在 `backend/eval/queue_exp/`。实验不调用模型。

**设置**：一个任务分 8 步，每步 2 秒，每步完成写一条“台账”（相当于一次模型调用或一次工具执行，有副作用、有成本）。worker A 做完 3 步后：
- 场景一：`kill -9`；
- 场景二：`SIGSTOP` 暂停，模拟长时间 GC 停顿或网络卡顿，进程其实还活着；B 接手后再让 A 恢复。

两个场景都立刻启动 worker B。

| | ARQ 0.28.0（job_timeout=30） | PostgreSQL 租约原型（租约 6s、心跳 2s） |
|---|---|---|
| kill -9 后 B 接手用时 | **34.1s** | **6.2s** |
| kill -9 后重复执行的步骤 | **3**（B 从第 1 步重做） | **0**（B 从第 4 步续做） |
| 暂停后 B 接手用时 | 34.0s | 6.1s |
| 暂停后重复执行的步骤 | 3 | 0（A 恢复后，下一步写入被 fencing 拒绝，记为 `fenced`） |
| 入队到开始执行 | 轮询，默认间隔 0.5s | `LISTEN/NOTIFY` 唤醒，中位数 21ms（20 次） |

### 读懂 ARQ 的结果
- ARQ 接手任务时写一个“进行中”标记，过期时间 = `job_timeout + 10s`，**期间不续期、没有心跳**。所以接管时间由任务超时决定：Agent 任务要给 300 秒超时，崩溃后就要等 5 分钟以上才有人接手。
- 新 worker **从头重做**：ARQ 不知道任务做到了哪一步，也没有“旧 worker 不能再写”的机制。
- 暂停场景下 A 恢复后没有继续写，是因为 A 自己的 `job_timeout` 先到期、取消了任务。ARQ 正是靠“标记过期 = 超时 + 10 秒”来避免两边同时执行的——代价就是接管慢。

### 读懂原型的结果
- **认领**：`UPDATE … WHERE id = (SELECT … WHERE 排队中 OR 租约已过期 … FOR UPDATE SKIP LOCKED LIMIT 1)`，认领时版本号加一。多个 worker 同时抢，不会抢到同一个任务，也不会互相阻塞。
- **心跳**：每 2 秒续期一次租约，续期时带上版本号。续期失败，说明已被别人接管，立刻停止执行。
- **fencing token**：每一步的副作用和进度更新放在**同一个事务**里，并校验版本号。被接管之后，旧 worker 的写入一定失败——“暂停后恢复”的 A 就是这样被挡住的。
- **按进度续做**：新 worker 从已提交的进度继续，不重做已完成的步骤。
- **局限**：只能保证“已提交的步骤”不重复。崩溃那一刻正在进行的一步（例如一次模型调用）会被重做，最多重复一步；外部副作用如果不能放进同一个事务，就需要幂等。

### 实验中踩到的坑
- 原型的 worker 第一次空等就崩了：用 `asyncio.wait_for(anext(异步生成器), 1)` 等通知，超时取消 `anext` 会把异步生成器关掉，下一次读就是 `StopAsyncIteration`。用最小复现确认后，改用驱动自带的 `notifies(timeout=…)`。
- psycopg 的游标没有 `.scalar()`（那是 SQLAlchemy 的方法），实验脚本里用错了一次。

## 二、方案对比
| | A. ARQ（路线图原计划） | B. PostgreSQL 租约队列（自己实现） | C. Procrastinate（基于 PostgreSQL 的任务库） |
|---|---|---|---|
| 状态存在哪 | Redis（ARQ 的任务）+ PostgreSQL（我们的 run）：**两份要对齐** | 只在 PostgreSQL，**业务行本身就是任务** | 库自己的任务表 + 我们的业务表：两份 |
| 崩溃后接管 | `job_timeout + 10s`，与任务时长绑定 | ≈ 租约时长（可独立设，如 30s），与任务时长无关 | 有心跳和“卡住的任务”检测，时间可配 |
| 防止旧 worker 写回 | 没有 | fencing token | 不提供（要自己做） |
| 从断点续做 | 不支持 | 支持（run 用 LangGraph checkpoint 续做，见下） | 要自己做 |
| 唤醒延迟 | 轮询（0.5s） | NOTIFY，约 20ms | NOTIFY |
| 维护状况 | 2025 年以来 3 个版本 | 约 200~300 行自己的代码 | 活跃 |
| 新依赖 | arq | 无 | procrastinate |

**建议 B**：
- 我们的“数据库是事实来源 + 原子认领”从阶段 1 就有了，B 只是在同一张业务表上加租约、心跳和 fencing。
- 接管时间与任务时长解耦，旧 worker 写不进来，run 还能从断点续做——这三点正是里程碑要的，ARQ 都不提供。
- 代价：
  - 队列逻辑要自己维护，测试要覆盖到位；
  - PostgreSQL 会多一些轮询和心跳请求：每个 worker 每秒 1 次空轮询、每个执行中的任务每 10 秒 1 次心跳，在这个规模下可以忽略；
  - 吞吐上限远低于专门的消息队列，但本项目每秒几个任务足够。
- 这是一个常见、成熟的模式（数据库即队列 + `SKIP LOCKED`），不是为了“自己造轮子”。

## 三、方案 B 的设计要点（确认后实现）
1. **租约放在业务表上**：`agent_runs`、`documents`、`kg_builds` 各加 `lease_owner`、`lease_expires_at`、`lease_version`、`attempts`（新迁移）。用一个通用的租约队列类按表参数化，同一套认领、续期、fencing 代码，替换现在三处“进程内队列 + 启动恢复”。
   - 否掉的方案：统一建一张 `jobs` 表——会有“任务状态”和“业务状态”两套状态机要对齐。
2. **独立 worker 容器**：compose 新增 `worker` 服务（`python -m agentnexus.worker`），执行三类任务；api 只负责落库、发 `NOTIFY`、提供接口，不再执行任务。
   - 好处：可以起多个 worker；api 也可以多实例（不再有“启动恢复误伤别人”的问题）；向量化不再和接口抢 CPU。
   - 代价：worker 也要加载 embedding 和重排模型（Agent 的检索在 worker 里执行），多约 1GB 内存。api 侧的检索测试页仍然需要模型；可以考虑改为按需加载，确认后再定。
3. **run 被接管后从断点续做**（替换 0009 的“中断即失败”）：
   - LangGraph 的 checkpoint 按 run_id 存（0006），新 worker 用同一个 thread_id 从最后一个 checkpoint 继续，已完成的模型调用和检索不重做；
   - 发 `run.resumed {attempt}` 事件，前端清空上一次尝试的半截文字；
   - token 事件带上 attempt，旧 worker 在被心跳发现之前（最多一个心跳间隔）流出的 token 会被前端忽略；
   - 最多尝试 3 次，仍失败就标为 `interrupted`。
4. **跨进程取消**（替换 0009 的“进程内信号”）：取消接口把 `cancel_requested_at` 写进数据库（事实来源），并通过 Redis 发一条取消消息（立即送达）。worker 订阅这条消息；心跳时也会检查数据库标记，作为兜底（最多一个心跳间隔）。
5. **参数**：租约 30s、心跳 10s（租约的 1/3，丢一两次心跳不会误判）、空闲轮询 1s。实验用 6s / 2s，是为了让实验跑得快。
6. **测试**：
   - 多个 worker 并发认领不重复；
   - 租约过期被接管；
   - fencing 拒绝旧 worker 的写入；
   - run 从 checkpoint 续做；
   - 跨进程取消；
   - 在 compose 里真实 `kill -9` worker（里程碑）。

## 四、实现要点（4.1 完成后补充）
- **代码位置**：
  - `runtime/lease.py`：通用租约队列，按表参数化；
  - `runtime/dispatcher.py`：run；
  - `runtime/jobs.py`：入库与图谱构建；
  - `runtime/cancel_bus.py`：Redis 取消广播；
  - `worker.py`：worker 进程；
  - `assembly.py`：api 与 worker 共用的装配；
  - 迁移 0009：三张表加租约字段，`agent_runs` 加 `cancel_requested_at`。
- **认领**：`UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)`，条件是“待执行，或执行中但租约为空 / 已过期”。认领时版本号加一、尝试次数加一。租约为空也按过期处理：升级前就在执行中的旧记录会被接管。时间一律用数据库的 `now()`。
- **写回**：run 的完成、失败、取消，文档的 ready / failed，图谱构建的进度与结束，全部带 `lease_version` 条件。
- **外部系统不受 fencing 保护**（实现时发现的关键问题）：Qdrant 不认版本号。原来“按文档删除向量点”的做法，会让恢复后的旧 worker 删掉接管者写好的点（文档 ready 却检索不到）。改为：
  - 每次尝试只写自己的点，失败时按 id 删除自己的点；
  - 带版本号成功提交的执行者，才清理“不属于本次结果”的点（`delete_document_except`）。
  - 同一事务里也要先做版本校验、再写分块（反过来会撞上接管者分块的唯一约束，直接抛异常）。
  - 图谱：重写 PostgreSQL 里的图之前，先在同一事务里锁住构建记录并校验版本；提交之后、写 Neo4j 之前仍有一个极小的窗口，用 sync 命令修复。
- **run 的接管**：
  - 认领后先检查 `cancel_requested_at`：取消后恰好被关停的 run，接手者直接收尾为已取消，不再执行；
  - 第 2 次及以后发 `run.resumed {attempt}`，token 带 attempt；
  - Agent 读 checkpoint：图没跑完就继续，跑完了直接用最终状态，没有就从头开始；
  - 超过 3 次标为 `interrupted`。
- **优雅关停**：放弃租约（立即过期），并**在同一事务里发 NOTIFY**。第一版没发，`docker stop` 后要 5.2 秒才被接管，修复后 0.9 秒。
- **跨进程取消**：取消接口写 `cancel_requested_at`；本进程在执行就直接取消，否则发 Redis 广播；worker 心跳时也检查数据库标记。
- **api 与 worker**：
  - api 不再执行任务。它的 `RunDispatcher` 和 `JobDispatcher` 不启动：`enqueue` 是空操作（通知已在提交任务的事务里发出），`cancel` 写数据库并广播；
  - worker 订阅 `LISTEN agentnexus_jobs` 唤醒对应的执行器，断线会重连，期间靠轮询兜底；
  - 存活检查：每 10 秒更新一个文件；
  - checkpoint 清理也移到 worker。
- **前端**：`run.resumed` 时清空半截文字；只接受当前尝试的事件，不带 attempt 的事件按第 1 次处理。

## 五、验证
- 后端测试：全量 219 个（其中 1 个 SSE 测试在 35 次全量运行中偶发失败 1 次，大概率是 4.1 之前就存在的问题，已加诊断，见 dev-log #117）。新增或改写的覆盖：
  - 接管无租约的 run；
  - 关停放弃租约后被续做；
  - 过期租约被接管，且旧 worker 被 fencing（新 worker 仍在执行时检查）；
  - 尝试上限；
  - 多个 worker 每个 run 恰好执行一次；
  - 跨进程取消（广播 / 广播丢失时靠心跳）；
  - 取消后关停不会再执行；
  - resumed 事件与 attempt；
  - 从 checkpoint 续做（预检索不重做）、跑完未落库直接用最终状态；
  - 文档与图谱构建的接管，以及旧 worker 不删接管者的向量点。
- 前端测试 39 个（新增接管相关）。
- 变异检查 15 项全部被发现。第一轮有 2 项存活（续约不校验版本、写回不校验版本）：测试里新 worker 执行太快、状态已不是 running，版本校验没有机会起作用；改为让新 worker 保持执行中再检查。
- 里程碑（compose，2 个 worker 副本，假模型慢速输出约 30 秒的回复）：

  | 操作 | 结果 |
  |---|---|
  | `kill -9` 执行中的 worker | 24.8 秒后被接管；1 条回复、内容正确；事件 started → resumed → completed |
  | `docker stop` | 0.9 秒后被接管；被关停的容器退出码为 0 |
  | 从 api 取消执行中的 run | 0.02 秒生效（Redis 广播），没有留下回复 |
- 真实 DeepSeek，单个 worker：入库 0.3 秒、带引用的对话 1.9 秒、图谱构建（1 块）$0.0004，三类任务都在 worker 里正常执行。

## 确认结果
1. 任务队列：PostgreSQL 租约队列（方案 B）。
2. run 被接管后：从 LangGraph checkpoint 续做，最多尝试 3 次。
3. worker 拓扑：一个 worker 服务执行所有任务，需要时起多个副本。
