# 0007 - 流式输出：事件通道、Agent 契约与断线续传

**状态**：草稿，待确认（阶段 1.5 开工前定）

**背景**：用户要看到回复逐字出现，而不是等十几秒后一整块。真实 Gemini 实测首块延迟约 7 秒、回复在之后 1~2 秒内分十来段到达。需要决定：token 事件怎么从执行方送到浏览器、Agent 怎么产出事件、客户端断线后怎么续上、事件和数据库谁说了算。

## 实验结论

在 compose 里用真实 Gemini 与真实 Redis 验证：

1. **LangGraph 能流式拿到节点内部的 token**：节点里仍然用 `model.ainvoke`，外层 `graph.astream(..., stream_mode="messages")` 就能收到逐段的 `AIMessageChunk`（真实模型 9 个事件，分散在 1.08 秒内；内容块类型是 `text`）。不需要改节点代码。
2. **没实现流式的模型只给 1 个整块**：我们的 `FakeEchoChatModel` 目前只有 `_generate`，流式下只产生 1 个事件。测试要验证“逐段”就得让假模型也能流式。
3. **Redis Streams 的语义正好对应需求**：`XADD` 返回单调递增的 ID，可直接当事件游标；从 `0-0` 读是全量回放，从某个 ID 读只返回其后的（等价于 `Last-Event-ID` 续传）；`XREAD BLOCK` 读到末尾会阻塞，被新写入立刻唤醒（实测 0.31s），无新数据则超时返回空；先于写入方连上也不丢（阻塞在尚不存在的 key 上，之后创建即收到）；`EXPIRE` 后整条流消失。
4. **每个阻塞读客户端占用 1 个 Redis 连接**（实测 5 个并发读 = 5 个连接）。redis-py 连接池 `max_connections` 默认是 **100**（我最初以为是不限，查证后才发现），所以单进程并发 SSE 客户端的上限大约就是这个数，必须显式配置。

## 方案

| | 事件通道 | 优点 | 缺点 |
|---|---|---|---|
| A | 进程内（asyncio.Queue / 内存缓冲） | 最简单，无外部依赖 | 阶段 4 把 worker 拆成独立容器后，事件无法跨进程；api 重启后缓冲丢失，无法续传 |
| B | **Redis Streams** | 跨进程；游标与回放现成；阻塞读即推送；Redis 本来就在栈里 | 多一次网络往返；每个客户端占一个阻塞连接 |
| C | 每个 token 写 Postgres + 轮询/LISTEN | 事件也持久 | 一次回复几百行写入、读放大，对“用完即弃”的事件不划算 |

## 决定（推荐 B，待你确认）

1. **事件通道用 Redis Streams**，每个 run 一条流 `run:{run_id}:events`。`XADD` 带 `MAXLEN ~ 5000` 防止无限增长；run 到终态后 `EXPIRE`（默认 1 小时）。流 ID 即 SSE 的 `id:`，续传用 `Last-Event-ID`。
2. **数据库永远是事实来源，事件只是“视图”**：
   - 终态事件（`run.completed` / `run.failed`）在数据库提交**之后**才发布，所以客户端看到“完成”时消息一定已落库。
   - 事件丢了（Redis 抖动、流过期、启动恢复把 run 置失败而没发事件）不会让客户端卡死：SSE 处理器在每次阻塞超时（15 秒）时查一次数据库，若 run 已终态就**合成**终态事件并结束；连接建立时若 run 已终态且流已过期，同样直接合成。
3. **事件类型**（`event:` 字段）：`run.started`、`token`（`data: {"text": "…"}`）、`run.completed`（含 `message_id`）、`run.failed`（含 `error`）。`data` 为 JSON 对象，保持可扩展（阶段 4 子 Agent 会加 `source` 等字段）。
4. **Agent 契约**：`RunContext` 增加 `events`（一个 `emit` 接口，默认空实现）。`run(ctx) -> str` 的签名不变，仍返回最终完整文本，由派发器照旧落库；流式只是 Agent 在执行中顺带 `emit` token。这样回声 Agent、现有测试、派发器的主流程都不用改。
   - 备选：把 `run` 改成异步生成器直接 `yield` 事件。更“纯”，但要改所有 Agent、派发器和测试，收益只有风格。
5. **ChatbotAgent** 改用 `graph.astream(stream_mode="messages")`：每个 `AIMessageChunk` 取文本（用已有的 `message_text`）`emit` 为 `token`，同时累积最终文本返回。checkpoint 与决策 0006 不变。
6. **SSE 接口**：`GET /api/runs/{id}/events`，和 `GET /api/runs/{id}` 同样的归属校验（不是自己的 run 返回 404）。每 15 秒无事件发一行注释心跳 `: ping`，防止代理断开；首块延迟 7 秒时尤其需要。客户端断开时服务端必须释放该 Redis 连接。
7. **连接上限**：显式设置事件客户端的 Redis 连接池 `max_connections`，并在文档里写明“并发 SSE 流 ≈ 连接池大小”是已知的扩展上限；更大规模需要改成“每个 run 一个读取协程 + 进程内扇出”。
8. **前端认证**：浏览器原生 `EventSource` 不能自定义请求头，而我们现在用 `X-User-Id` 头做鉴权占位（阶段 5 会换成 token）。前端改用基于 `fetch` 的流式读取（可用 `@microsoft/fetch-event-source`），仍走头部鉴权。**不采用**把用户标识放进 URL 查询串的做法，因为 URL 会进日志和浏览器历史。
9. **范围外**：取消 run、断线后自动恢复执行（阶段 4）、多个浏览器标签同时订阅的去重。

## 后果

- 好处：阶段 4 拆 worker 时事件通道不用改；断线续传和晚加入的客户端回放是现成能力；数据库仍是唯一事实来源，事件出问题只影响“实时性”，不影响正确性。
- 代价：每个 SSE 客户端占一个 Redis 连接；多了“事件与数据库不一致时以谁为准”的逻辑，需要专门测试；前端不能用最省事的原生 `EventSource`。
- 风险：合成终态事件的路径（Redis 丢事件、启动恢复）只有在测试里主动制造故障才会走到，必须有测试覆盖，否则线上才会发现客户端卡死。

## 开放问题（需要你决定）

1. **是否接受 Redis Streams 方案（B）**，尤其是第 2 点“数据库为准、事件为视图”和第 4 点“把 `events` 放进 `RunContext`、`run()` 仍返回完整文本”。
2. **失败时已推送的部分 token 怎么办**：当前设计是不入库——run 失败后 `messages` 表里没有这条助手回复，前端要把已显示的半截内容标成“生成中断”。你是否接受？（另一种是把部分输出落库，但会与决策 0006 的“只有最终文本入 messages”冲突，我不推荐。）
