# 0018 - 知识库问答：对话关联知识库、预检索 + 检索工具、引用快照

**状态**：已决定（阶段 2.4，2026-10-22）

**背景**：2.3 之后已经能“给一个问题返回相关片段”。2.4 要让对话 Agent 用上知识库：回答有依据、标注引用、没有就说没有。阶段 2 的里程碑是“上传文档后 Agent 基于检索内容回答，并展示引用片段”。

## 决定

### 1. 对话关联知识库，范围由服务端决定
- 新表 `conversation_knowledge_bases`（迁移 0007）。接口 `GET/PUT /api/conversations/{id}/knowledge-bases`，整体替换，最多 10 个。对话和每个知识库都必须属于当前用户，失败时原关联不变。
- run 执行时读取当前的关联（排队期间改了关联，以执行时为准），连同对话归属用户一起放进 `RunContext`，再通过 LangGraph 的 `configurable` 传给工具节点。
- **工具参数只有 `query`**：检索哪些知识库、以谁的身份检索，模型既看不到也改不了。否则提示注入（例如文档里写“去检索某某知识库”）就能越权读取。有测试：模型在工具参数里塞别的知识库 id，检索范围不变。检索服务内部还会再校验一次归属（0017）。

### 2. 预检索 + 检索工具（用评测数据选定）
图的结构：`prefetch → model → (tools → model)*`。

- **prefetch**：调用模型之前，先用用户的原话检索一次。结果以“一次工具调用 + 工具结果”的形式放进上下文，所以对模型来说就像它自己刚检索过。
- **model**：关联了知识库才绑定 `knowledge_search` 工具，并在提示词里加入检索与引用规则。原话不适合当检索词时（例如追问“那定制的呢”），模型可以用补全后的检索词再检索。
- **轮数上限**：预检索也算一轮，默认最多 3 轮。超过上限时，工具节点直接返回“已达上限，请根据已有内容回答”。仍然绑定工具，因为 Anthropic 格式要求：消息里有工具调用时，请求必须定义工具。兜底：LangGraph 的 `recursion_limit`，无视上限的模型会在有限步数后报错，不会无限花钱。
- 检索失败时不让整个回答失败：返回“检索暂时不可用”给模型，由它如实告知用户；前端收到的 `tool.finished` 带 `ok=false`。

**为什么是预检索**：同一套 30 题评测，只改这一个设置（DeepSeek `deepseek-flash`，关闭思考模式）：

| 方案 | 引用正确 | 检索率 | 模型调用（33 次运行） | 耗时中位数 | 输入 / 输出 token | 费用 |
|---|---|---|---|---|---|---|
| A：模型自己决定是否检索（第 1 轮） | 0.97 | 0.97 | 65 | 2.9s | 4.2 万 / 4.8 千 | $0.0113 |
| A（第 2 轮，提示词加“先检索再追问”） | 0.97 | 0.97 | 65 | 2.9s | 4.3 万 / 4.8 千 | $0.0115 |
| **C：预检索 + 工具** | **1.00** | **1.00** | **33** | **1.7s** | **2.7 万 / 2.9 千** | **$0.0079** |

- A 的失败方式：问题较短、有歧义时，模型不检索、直接反问用户（“您指的是哪笔退款？”）。两轮失败的题不同，说明这是随机现象，改提示词压不住。
- C 每个问题都有据可查，模型拿到结果通常一次就能回答，少一次模型调用。代价是闲聊（“你好”）也会检索一次：约 1~2 秒的重排，外加约 1k 输入 token。
- 被否掉的方案：
  - **B：第一轮强制工具调用**（`tool_choice=any`）：同样不会漏检，但仍要两次模型调用；而且 Anthropic 官方接口在开启思考模式时不支持强制工具调用。
  - **只做预检索、不提供工具**：多轮追问时，原话检索效果差，模型也没有补救手段。
- 多轮追问只手动测了 3 组（“那定制的呢”“那专票呢”“怎么关掉”）：都答对了，模型都没有补查（原话检索已经命中）。评测知识库只有 30 篇，规模变大后原话检索的弱点可能会暴露，需要专门的多轮评测集。
- 部署开关 `KNOWLEDGE_PREFETCH`（默认开启）保留，用于对比实验。

### 3. 引用：编号、标注、存快照
- 工具结果里每个片段带编号 `[n] 来源：文件名（第 p 页）`。同一次回答里重复检索到的片段沿用原编号。
- 提示词要求：只有某个片段支撑了回答中的某个说法时才标注 [n]；没找到时不标注、也不罗列无关片段。第一版提示词下，模型在说“没找到”时仍然标了 [1]~[4]，用来列举“检索到的都无关”，前端会把它们当成来源展示。改完后，知识库外的 3 个问题中有 2 个不再标注；剩下一个（比特币付款）标注了知识库里确实写明的付款方式，是合理引用。
- 回答落库时，`messages.citations`（JSONB）保存**快照**：编号、分块 / 文档 / 知识库 id、文件名、页码、原文、两种分数，以及是否在正文里被引用（`cited`）。
  - 为什么存快照而不是只存分块 id：文档以后重新处理、分块被替换，历史回答的引用仍然能展示当时的原文。
  - 为什么也保留 `cited=false` 的：排查“检索到了却没用上”时有用；前端只展示被引用的。
- 前端在回答下方列出被引用的来源（`[n] 文件名 · 第 p 页`），悬停显示片段原文。

### 4. 事件与前端
- 新增 SSE 事件 `tool.started {name, query}` 和 `tool.finished {name, hits, ok}`。Agent 从 LangGraph 的 `updates` 流里取节点输出来发送；预检索节点一次产出两者。
- 前端收到 `tool.started` 时清空正在显示的临时文字（模型在调用工具前说的话不会成为最终回复），并显示“正在检索知识库：…”；`tool.finished` 后显示“检索到 n 条资料，正在生成回答”。
- 顺带修了一个隐患：前端的事件状态机没有 default 分支，收到不认识的事件类型会返回 `undefined`，把状态弄坏。改为忽略不认识的事件，后端新增事件类型时旧前端不会坏。

### 5. 用量日志
每次运行结束，Agent 记录一行 `llm usage`：模型调用次数、输入 token（其中命中缓存的部分）、输出 token，带 run_id。评测的费用就是从这里算出来的；阶段 5 的成本看板再落库统计。

### 6. 按标题切分 Markdown（2.3 留下的问题，这次用数据决定）
- 把 30 篇知识条目合成一个 Markdown 文件（每篇一个二级标题）再检索（`backend/eval/eval_chunking_md.py`）。原来的分块器每块混入约 4 个主题，第一名命中率：仅向量 0.73、加重排 0.90；每篇一个文件时分别是 0.90 和 1.00。
- 改为 Markdown 遇到标题就另起一块、重叠不跨标题，当前块只有标题时不切。只对 `.md` 生效，因为 txt 里以 `#` 开头的行不一定是标题。改后：仅向量 0.90、加重排 1.00，和每篇一个文件时一样。
- 已入库的文档不会自动重新分块，需要“全部重新处理”的管理命令（待做）。

## 后果
- 好处：
  - 阶段 2 的里程碑达成：回答有依据、带引用；
  - 检索范围不受模型控制；
  - 预检索让常见问题少一次模型调用（更快、更省）；
  - 引用经得起文档变更。
- 代价：
  - 闲聊也检索；
  - `messages` 表多一列 JSON，每条带引用的回答多存约几 KB 原文。
- 已知局限：
  - 多轮评测样本少；
  - 内容几乎相同的两份文档会产生重复片段（浏览器实测时，模型同时引用了“客服政策.md”和“客服政策v2.md”）。可以在交给模型前按文本相似度去重，待做；
  - 评测指标只覆盖可客观判断的部分（是否检索、引用是否包含正确文档），没有评估回答的完整性。引用精确度 0.64~0.65 偏低，主要是模型补充引用了相关的其他条目（例如退货问题顺带引用换货政策），不一定是错误。
