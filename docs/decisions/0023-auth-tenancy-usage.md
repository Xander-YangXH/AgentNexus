# 0023 - 阶段 5：登录、部门隔离与用量看板

**状态**：草稿（2026-10-23），待用户确认第三节的选择。

**背景**：到阶段 4 为止，“当前用户”靠请求头 `X-User-Id` 占位，谁都可以冒充任何人；数据只按“属于哪个用户”隔离，没有部门、角色，也没有用量统计。阶段 5 的里程碑是：

1. 两个不同角色的账号登录后，互相看不到对方的数据；同部门共享的知识库能看到、别的部门的看不到；
2. Dashboard 上能看到真实的用量曲线（请求量、token、检索次数）。

需要回答四个问题：怎么登录（会话放在哪里）；隔离只靠应用代码，还是再加数据库层的第二道防线；角色和可见性做到多细；用量在哪里采集、怎么聚合。

实验脚本：`backend/eval/tenancy_exp/`。不调用模型，零费用。

## 一、实验
### 1. 密码哈希（`hashing.py`）
| 算法与参数 | 单次校验 |
|---|---|
| argon2id，OWASP 推荐参数（m=19MiB, t=2, p=1） | 15 ms |
| argon2id，argon2-cffi 默认参数（m=64MiB, t=3, p=4） | 27 ms |
| bcrypt cost=10 | 42 ms |
| bcrypt cost=12 | 168 ms |

- **必须放进线程池**：8 个并发登录时，一个普通请求要等 **254 ms**（直接在事件循环里算）对比 **3 ms**（`asyncio.to_thread`）。哈希是 CPU 计算，在事件循环里算会卡住所有请求（包括 SSE）。
- 测量踩坑：第一版在“普通请求”任务内部开始计时，两种方式都测出 0 ms——阻塞发生在它开始运行之前，根本没被测到。改为从请求到达（创建任务）时计时。（数字里包含了为准备数据先算哈希的时间，用来比较量级。）

### 2. 数据隔离：应用层过滤 vs 再加行级安全 RLS（`rls.py`）
模型：20 个部门、2000 个用户、5 万个知识库（30% 部门可见）、30 万篇文档。

| | 应用层 WHERE | RLS |
|---|---|---|
| 列出可见知识库（中位数 / p95） | 0.83 / 1.26 ms | 1.20 / 1.66 ms |
| 按 id 取文档 | 0.19 / 0.31 ms | 0.19 / 0.26 ms |
| **应用代码漏写过滤条件**（`SELECT count(*) FROM knowledge_bases`） | **50000 行，全部泄露** | **705 行（该用户应当可见的数量）** |

RLS 的四个陷阱（都实测过）：
- **超级用户和表所有者不受 RLS 约束**：现在 compose 里应用用的就是 postgres 镜像创建的超级用户——直接加策略，**完全不生效**（实测看到 50000 行）。要用 RLS，应用必须换成一个普通角色。
- **会话级 `SET` 会串到下一个请求**：连接池复用连接，上一个请求用会话级设置了用户，下一个请求忘了设置，看到的是上一个用户的 705 行。必须用事务级设置（`set_config(..., true)`），事务结束自动清除；实测下一个事务看到 0 行。
- **没设置用户时默认拒绝**：`current_setting(..., true)` 返回 NULL，策略结果为假，看到 0 行——漏设置不会泄露，只会“什么都看不到”，容易被测试发现。
- **写入也受约束**：我原以为“只写 USING 的策略不检查新写入的行”，实测不对——没写 `WITH CHECK` 时 `USING` 同时用于检查新行，以别人的身份插入被拒。

### 3. 用量明细直接聚合够不够快（`usage.py`）
100 万行明细、30 天、2000 个用户（约每天 3 万次模型调用，远超演示环境）：

| 查询 | 中位数 / 最大 |
|---|---|
| 单行插入（含提交） | 0.51 ms |
| 某用户 30 天每天的 token | 5.2 / 14.4 ms |
| 某部门 30 天每天的 token | 21.3 / 109.5 ms |
| 全站 7 天每小时 | 68.7 / 89.4 ms |
| 全站 30 天每天 | 261 / 684 ms |

表 + 索引 257MB。结论：个人、部门维度直接在明细上聚合足够；全站长时间范围在百万行时开始变慢，到那时再加按小时 × 部门的汇总表（30 天只有约 1.4 万行）。演示环境的数据量下，先不做汇总表。

### 4. 用量怎么采集（`callback_capture.py`）
4.3 的做法是把用量写进图状态，**崩溃那次执行中“在途”的调用会丢**。改用 LangChain 回调：在图的配置里挂一个回调，验证能否收到节点内部的所有模型调用——节点里直接 `model.ainvoke()`（没有显式传 config）、结构化输出、`bind_tools`、Send 并行的子任务、流式调用。

结果：**5 次调用全部捕获**（1 次计划 + 3 个子任务 + 1 次流式汇总），用量都在。回调在每次调用结束时触发、立即写库，和图是否提交无关，所以被打断的执行里已经花掉的钱也能记下来。

## 二、需求的取舍
- **“Agent 可见性”**：项目里目前没有“用户自定义的 Agent”这种资源（只有聊天 / 调研两种类型），所以可见性先落在**知识库**上：私有，或部门内共享（只读）。对话、产物、运行记录始终只属于自己。
- **角色**：不做通用的“角色—权限”配置表（路线图也说不需要企业级权限矩阵），用固定角色。
- **用户自己的数据怎么迁移**：已有用户没有密码；迁移后由管理员用命令行工具设置密码 / 创建第一个管理员。

## 三、待确认的选择
### 1. 登录与会话
| | A. 服务端会话 + HttpOnly Cookie（推荐） | B. JWT（Bearer 头） |
|---|---|---|
| 退出 / 禁用用户 | 删会话即刻生效 | 令牌过期前一直有效，要做黑名单就又回到了服务端状态 |
| 每个请求的成本 | 一次主键查询（会话表，约 0.2ms） | 验签，不查库 |
| 前端 | 浏览器自动带 Cookie：下载产物可以直接用链接；SSE 用 fetch 也自动带 | 每个请求手动加头；下载仍要 fetch 成 Blob |
| 脚本无法读取 | HttpOnly：XSS 偷不走令牌 | 令牌在 JS 里（localStorage），XSS 能直接拿走 |
| 要处理 | CSRF：同源部署 + `SameSite=Lax` + 写操作校验 `Origin` 头 | 不需要 CSRF 防护 |

- 密码：argon2id（OWASP 参数，argon2-cffi），在线程池里计算；登录失败统一报“用户名或密码错误”。
- 会话表存令牌的哈希（库泄露也拿不到能用的令牌），带过期时间；退出即删除。

### 2. 数据隔离
| | A. 应用层 + 越权测试矩阵 | B. 应用层 + RLS 第二道防线（推荐） |
|---|---|---|
| 主要防线 | 服务层的归属 / 部门检查（已有模式） | 同 A |
| 漏写过滤条件时 | 泄露（实验：5 万行全部可见） | 只看到应当可见的行 |
| 代价 | 最少 | 应用改用普通角色（不再是超级用户）；每个事务开始时设置当前用户（SQLAlchemy 事件钩子，事务级）；worker、迁移、后台任务用带 `BYPASSRLS` 的单独角色；列表查询多约 0.4ms |
| 测试 | 越权矩阵：每个接口 × （本人 / 同部门 / 别的部门 / 未登录） | 同 A，另加“故意漏写 WHERE 仍不泄露”的测试 |

为什么推荐 B：多租户系统最常见的事故是某个新接口忘了加归属条件。A 只能靠评审和测试覆盖到每个接口；B 让数据库在漏写时也默认拒绝。范围只做 api 进程（用户直接触达的路径）；worker 执行的任务本来就是按 run 归属取数据的，用 `BYPASSRLS` 角色，保持现有逻辑。

### 3. 角色与可见性
| | A. 三个固定角色 + 知识库部门共享（推荐） | B. 可配置的角色—权限表 |
|---|---|---|
| 角色 | 管理员（管理用户和部门、看全站用量）、部门负责人（看本部门用量）、成员 | 任意角色、任意权限组合 |
| 可见性 | 知识库：私有 / 部门共享（同部门只读，只有所有者能改）；其他资源只属于自己 | 同左，但权限可配置 |
| 代价 | 少量常量和检查函数 | 多两三张表、一个管理界面，演示里用不上 |

### 4. 用量采集与聚合
| | A. 回调写明细 + 查询时聚合（推荐） | B. 一开始就做汇总表 | C. 只看日志 |
|---|---|---|---|
| 采集 | 每次模型调用结束写一行（实验 4：所有调用都能捕获；崩溃前已花的也记得到）；检索每次一行；请求量用 run 表 | 同 A，另有定时汇总 | 现有的 `llm usage` 日志 |
| 查询 | 个人 / 部门 5~21ms；全站 30 天在百万行时 261ms | 都很快 | 没有查询能力 |
| 代价 | 一张表；数据量大了再加汇总 | 汇总任务、汇总与明细的一致性 | 做不了 Dashboard |

前端图表：ECharts（按需引入，Dashboard 页面单独打包、懒加载），实现时记录打包体积。

## 四、风险
- 从 `X-User-Id` 换成 Cookie 会话，几乎所有接口测试都要换鉴权方式：测试里用一个登录辅助函数，或覆盖“当前用户”依赖。
- 换应用数据库角色要改 compose 和迁移流程（迁移用所有者角色，api 用普通角色，worker 用 `BYPASSRLS` 角色）；已有部署要执行一次授权。
- 共享知识库被同部门的人在对话里引用时，检索要按“可见”而不是“属于自己”判断——0018 里“知识库由服务端决定”的检查要相应修改。
