# 0015 - 知识库的数据模型、原件存储、解析与分块

**状态**：已决定（阶段 2.1，2026-10-21）

**背景**：决策 0014 定了 embedding、重排与向量库。在接入向量之前，先要把“文档进来”这一段做扎实：存哪里、怎么防重复、怎么解析、怎么切块。这些决定会影响检索质量（分块）、数据一致性（上传顺序）和后续扩展（存储接口）。

## 决定

### 1. 数据模型（迁移 0006）
- `knowledge_bases`：按用户归属（阶段 5 改为部门 / 角色可见性），同一用户内名称唯一。
- `documents`：文件名、大小、内容 SHA-256、原件 key、状态（pending → processing → ready / failed）、错误码与原始报错（原始报错不对外，同 0009）、分块数、处理完成时间。**同一知识库内按内容哈希唯一**：重复上传返回 409 并告知已有文档的 id，避免同一段内容被检索出两遍；不同知识库之间允许相同文件。
- `document_chunks`：原文、序号、token 数、PDF 页码（用于标注引用出处）；**冗余存一份知识库 id**，检索时按知识库过滤不必再连表。分块是检索的**事实来源**，Qdrant 只是从这里派生的向量索引（0014）。
- 文档 id 由应用生成（不是数据库默认值）：写原件时就需要用它作为 key。

### 2. 原件存储：接口 + 本地数据卷（暂不上 MinIO）
- 原件**不放进数据库**：大文件会拖慢备份、事务和复制，数据库只存元数据和解析后的文本。
- `BlobStore` 接口按 key 存取，与 S3 / MinIO 语义一致；第一版用 `LocalBlobStore`（compose 数据卷 `blob_data`）。路线图原定 MinIO，但它多一个服务，当前单机部署用本地卷足够；**换 MinIO 只需新增一个实现**。
- key 只允许安全字符并校验落在根目录内（防路径穿越）；写入用“临时文件 + 改名”，崩溃不会留下写了一半的文件；文件 IO 放到线程里，不阻塞事件循环。

### 3. 上传顺序：校验 → 写原件 → 事务里插入记录
- 归属校验、类型、空文件、大小都在**写原件之前**完成：不给无权限或不合规的请求写任何东西。
- 先写原件、再插记录：如果反过来，原件写失败会留下一条“找不到原件”的文档，比一个没人引用的孤儿文件更糟。插入失败（含重复）时尽力删除刚写的原件。
- 接口层只读“上限 + 1”字节，超出即拒绝，不把超大文件完整读进内存；服务层再校验一次（纵深防御，以后 worker 直接调用服务时也安全）。
- 上传返回 **202**：文档已落库（pending），解析、分块、向量化是异步的（2.2 起由后台任务处理）。

### 4. 解析
- `.txt` / `.md`：先按 UTF-8（含 BOM）、再按 GB18030 解码，覆盖 Windows 上常见的 GBK 中文文件。
- `.pdf`：pypdf 逐页提取并记录页码；加密 PDF、没有文字层（扫描件，需要 OCR）都明确失败，而不是入库一个空文档。
- `.docx`：python-docx，段落 + 表格（按“单元格 | 单元格”拼行，价格表、参数表很常见）。
- 失败按原因给错误码：`unsupported_type`、`encrypted`、`empty`、`corrupt`。
- 选型：pypdf（纯 Python、无系统依赖）+ python-docx；否掉 unstructured（依赖重、安装体积大，对本项目的几种格式没有必要）。pypdf 固定在发布满两周的 6.19.0。

### 5. 分块（中文友好）
- **硬约束**：bge-small-zh 最多读 512 个 token，超出部分被静默截断（丢失）。每块目标 300、硬上限 480（给特殊 token 留余量）。
- 按段落、再按句子边界（。！？；!?; 与换行，引号跟随句号）切句，**不在句子中间切断**；单句超过硬上限时才按字符强制切开。
- 相邻块**重叠约 50 个 token**，且**只取整句**：上一块最后一句就超过重叠上限时，这次不重叠（半句话会制造语义残缺的片段）；重叠 + 下一句会超过硬上限时，放弃重叠；重叠永远不会把上一块整块带过去。
- token 计数可注入：2.1 用估算器（汉字 1 个、英文按词约 1.3 个）；2.2 接入模型时换成 bge 自带的分词器，保证计数与模型实际看到的一致。

### 6. 处理的一致性
- 处理前原子地把文档从 pending 改为 processing（与 AgentRun 的 claim 同一模式），同一文档只会被处理一次；
- “写入全部分块”与“标记 ready”在**同一事务**：标记失败（状态被别处改掉）时整体回滚，不留半套分块。
- 数据库的“同一文档分块序号唯一”约束是第二道防线：即使抢占逻辑失效，重复处理也会被拦下（变异检查中实际观察到）。

### 7. Nginx 请求体上限
- Nginx 默认只允许 1MB，实测 3.2MB 的文件被拦截，且返回的是 HTML 错误页。设为 12m（略大于应用的 10MB）：10~12MB 由应用返回统一格式的 JSON 错误，只有更大的才被 Nginx 拦。**调大 `MAX_UPLOAD_MB` 时要同步修改**。

## 后果
- 好处：文档入口稳健（不留半成品、不重复、不越权、不读超大文件进内存），分块保证不被模型截断，存储可替换。
- 代价：原件在单机数据卷上，阶段 4 拆出 worker 后需要共享卷或换 MinIO；token 计数在 2.1 是估算值。
- 已知局限：没有 OCR；没有删除文档的接口；原件存储没有垃圾回收（被拒上传已清理，但进程在“写原件后、插记录前”崩溃仍会留下孤儿文件）。

## 验证
- 测试 40 个（解析 10、分块 10、知识库服务与接口 20），全量 159 个通过。
- 变异检查：分块 5 项（第一轮有 2 项存活：一项是测试漏洞，补测试后被抓住；另一项是等价变异，说明那段代码多余，已删除）；知识库服务 5 项（第一轮 M5 存活，因为接口层已拦住超大文件，补了服务层的单独测试后被抓住）。
- 容器实测：迁移 0006；中文 md 上传 202、原件写入数据卷；经 Nginx 3.2MB → 202、10.5MB → 应用返回 JSON 413、13MB → Nginx 拦截。
