# 0016 - 入库流水线：后台处理、向量化与 Qdrant 索引

**状态**：已决定（阶段 2.2，2026-10-21）

**背景**：2.1 让文档可以上传、解析、分块，但处理要手动触发，也没有向量。2.2 要把它接成一条自动的流水线：上传 → 后台解析分块 → 向量化 → 写入 Qdrant → 可检索。约束沿用 0014：**PostgreSQL 是事实来源，Qdrant 是可重建的派生索引**；embedding 用本地 bge-small-zh-v1.5，零 API 费用。

## 决定

### 1. 后台处理：沿用“先落库再投递”，单独一个小派发器
- 文档以 pending 落库就代表“必须被处理”。上传接口落库后投递到内存队列；投递丢了，周期扫描会把 pending 的补上（与 0005 的 run 相同）。
- 不重复处理靠数据库里的原子抢占（pending → processing 的条件更新），不靠队列。
- `IngestDispatcher` 是独立的小类，没有和 `RunDispatcher` 抽成通用类：两者重复的只有队列和扫描的二三十行；文档处理没有取消、流式事件和超时。阶段 4 两者会一起换成独立 worker，现在抽象等于提前猜以后的形状。
- 并发默认 1：向量化是 CPU 密集的，ONNX 自己就会用满多核，并发多了只会互相抢。实测处理期间 API 的响应时间为 10~20ms，api 容器 CPU 约 1000%。
- 解析、分块、向量化放在 `asyncio.to_thread` 里，不阻塞同进程里的对话和 SSE。

### 2. 启动恢复：处理到一半的文档改回 pending（不是标为失败）
- run 被中断时标为失败（0009），因为重跑要花模型费用，用户也在等。文档处理是**幂等**的、不花钱，所以直接重做。
- 幂等的前提是：重做前先按文档 id 删掉索引里的旧点；分块与 ready 状态在同一个事务里，中断时数据库里不会留下分块。

### 3. 写入顺序：先写索引，再在一个事务里写分块并标记 ready
- Qdrant 写入用 `wait=True`，返回时已经可查。之后再提交“分块 + ready”，所以 **ready 的文档一定能被检索到**。
- 反方向的失败（索引里多了点、数据库没提交）是安全的：
  - 检索时按点的 id 回数据库取原文，没有对应分块的点会被自然过滤；
  - 失败路径会尽力删掉这些点；
  - 重新处理前也会再清一次。
- 点的 id 就是分块的主键（应用生成的 UUID）。payload 只放 `knowledge_base_id` 和 `document_id`，原文不放进 Qdrant，避免两边的文本不一致。

### 4. 失败与重试
- 失败按原因记错误码：
  - 解析错误沿用 0015 的错误码；
  - 写索引失败记为 `index_unavailable`；
  - 其他错误记为 `internal`。
- 新接口 `POST /api/documents/{id}/reprocess` 只允许 failed → pending（其他状态返回 409 `document_not_retryable`），用来在 Qdrant 恢复后重试。不做自动重试：避免文件本身有问题时无限循环。

### 5. Qdrant 的组织方式
- **一个集合放所有知识库**，按 payload 的 `knowledge_base_id` 过滤。这是 Qdrant 推荐的多租户做法，`is_tenant=True` 让它按租户组织存储。另外给 `document_id` 建 payload 索引，用于按文档删除。
  - 否掉的方案是“每个知识库一个集合”：集合数会随知识库线性增长，每个集合都有固定开销。
- **应用只通过别名访问**（默认 `chunks`），实际集合名带时间戳。为重建索引做准备，见第 7 条。
- 启动时检查集合维度与模型是否一致，不一致就直接启动失败（`IndexMismatch`）。换了模型却悄悄写进维度不同的集合，比启动失败更难排查。
- 关闭 Qdrant 默认开启的匿名统计上报（`QDRANT__TELEMETRY_DISABLED`）。
- 镜像里没有 curl / wget，健康检查用 bash 的 `/dev/tcp` 请求 `/readyz`。
- 就绪探针 `/health/ready` 加入 Qdrant。

### 6. 向量化与 token 计数
- 用 `FastEmbedder`（fastembed + ONNX，不需要 PyTorch），加载一次，整个进程共用。
- 输出已经归一化，余弦相似度等于点积。查询不加前缀（0014）。
- **分块计数改用模型自己的分词器**，替换 2.1 的估算器。用的是复制出来的一份，并关掉截断和补齐：fastembed 内部那份开着“截断到 512”，拿它计数，超长文本永远只数出 512。
- **计数加字符下限**：实际取 `max(模型 token 数, 字符数 / 6)`。bge 的 WordPiece 会把超过 100 个字符的单个“词”整体记成 1 个 `[UNK]`。实测一个 3.3MB 的无空格文本因此只算 1 个 token、整段成了一块，被检索到时会把几 MB 文本塞进模型上下文。正常文本里每个 token 平均远不到 6 个字符，所以这个下限不影响正常文本。存进库的 `token_count` 仍是模型的真实计数。
- 二分切长句时只对不超过“上限 × 6”个字符的前缀计数，避免每切一段都把剩下的几 MB 重新分词，否则耗时会随长度平方增长。

### 7. 重建索引：新集合 + 原子切换别名 + 补录
- 命令：`docker compose exec worker python -m agentnexus.knowledge.reindex`（阶段 5 起必须在 worker 里运行：api 的数据库角色受 RLS 约束；见 0029 的踩坑记录）。
- 用途：换模型，或 Qdrant 数据丢失、与数据库不一致。
- 步骤：
  1. 建新集合；
  2. 按分块 id 键集分页，读出 ready 文档的分块，重新向量化写入；
  3. 一次请求里删旧别名、建新别名，原子切换；
  4. 补录重建期间完成的文档（`processed_at >= 开始时间`，用数据库时钟）；
  5. 删除旧集合。
- 切换之前失败会删掉半成品，旧索引不受影响。
- 剩余空档：文档在切换前写入旧集合，但在补录查询之后才提交 ready。概率很小，需要时再跑一次即可。已写进代码注释。
- 向量不存数据库：重建要重新计算，本地模型只花 CPU 时间。

### 8. 模型在构建镜像时下载
- fastembed 默认把模型下到系统临时目录，容器重建就丢，每次启动都要联网。现在改为构建镜像时下载到 `/opt/models`（91MB），运行时设置 `HF_HUB_OFFLINE=1`。
- 验证：在 `--network none` 的容器里能正常加载模型并计数。
- compose 不在运行时覆盖 `EMBEDDING_MODEL`：模型是构建时下载的，运行时改名只会启动失败。
- 代价：镜像变大。**更正（2.3）**：当时写的“1.01GB”是 `docker images` 的数字，在 containerd 存储模式下它是“压缩包 + 解包内容”的合计，不是镜像实际大小。按各层解包大小算，2.2 时约 0.77GB（其中 embedding 模型层 95MB、Python 依赖约 0.5GB）。

### 9. 依赖锁文件（顺带完成“贯穿”里的待办）
- 新依赖带进来的间接依赖里，有好几个是不到两周前才发布的版本（numpy 2.5.4、onnxruntime 1.31.0、tokenizers 0.23.3），手动逐个限制版本已经管不过来。
- 做法：
  - `requirements.txt` 只写直接依赖和版本范围（人工维护）；
  - `uv pip compile --universal --python-version 3.12 --exclude-newer <今天减 14 天>` 生成 `requirements.lock`，**连间接依赖一起**只取发布满两周的版本；
  - 镜像和开发环境都按锁文件安装。
- 结果：fastembed 从评测时用的 0.9.0（刚好 14 天）变为 0.8.1。用到的接口一致，真实模型测试在 0.8.1 上通过。
- 否掉的方案：
  - pip-tools：不支持按发布日期过滤；
  - poetry / uv 项目模式：要改整个项目结构，收益不大。

### 10. Nginx 动态解析后端地址
- `proxy_pass http://api:8000` 写死主机名时，Nginx 只在启动时解析一次。api 容器单独重建、IP 变化后会一直 502（实测）。
- 改为 `resolver 127.0.0.11`（Docker 内置 DNS）加变量形式的 `proxy_pass`，按 10 秒间隔重新解析。

## 后果
- 好处：
  - 上传后自动可检索，失败可见（有错误码）、可重试；
  - 进程崩溃不丢、不重复处理；
  - 索引坏了可以从数据库重建，切换时检索不中断；
  - 对异常输入有界（字符下限）。
- 代价：
  - api 进程同时承担向量化，CPU 密集，阶段 4 拆出 worker 后解决；
  - 一个 10MB 的中文文档处理约 5 分钟（实测 3.3MB、4667 块用了 109 秒）；
  - 镜像变大。
- 已知局限：
  - 单进程假设，同 0005；
  - 没有删除文档的接口（删除时也要删掉 Qdrant 里的点，到时一并做）；
  - 只嵌入分块正文，没有加文档标题等上下文，2.4 评测后再决定；
  - payload 索引和 `is_tenant` 只能在真实 Qdrant 上验证（测试用的进程内模式不支持），已在容器里核对。

## 验证
- 新增测试 14 个，全量 174 个通过：
  - 入库流水线 13 个，其中 2 个使用真实模型，本机有模型缓存时才运行；
  - 分块的字符下限 2 个。
- 变异检查共 13 项，全部被测试发现：入库流水线 9 项，字符下限与计数 4 项。
- 容器实测：
  - 迁移后启动会自动建集合和别名；2.1 遗留的 pending 文档被扫描补投并处理完成；
  - 经 Nginx 上传 3.3MB 中文文件：接口 60ms 返回 202，后台处理 4667 块用时 109 秒；处理期间 `/health` 响应 10~20ms；
  - 3.3MB 无空格文本重新处理后得到 1166 块，每块最多 2880 字符，耗时 4.5 秒；
  - Qdrant 点数与数据库 ready 分块总数一致（10514）；
  - api 容器重建后经 Nginx 访问正常；
  - 在容器里对真实 Qdrant 跑了重建索引命令：15181 块用时 7 分 30 秒；别名切到新集合、旧集合已删除；点数与数据库一致；租户索引为 `is_tenant: true`。
