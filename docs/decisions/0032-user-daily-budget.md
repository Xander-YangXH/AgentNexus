# 0032 - 阶段 7.9：每个用户的模型费用上限（最近 24 小时）

**状态**：已采纳（2026-10-25）。用户休息期间授权按推荐方案自主推进，选择由我按推荐方案决定，理由写在下面，可以复核。

**背景**：任何登录用户都可以无限发消息，每条都会调用模型、产生费用。一个失控的脚本、反复重试，或者被诱导反复提问，都没有上限。用量明细已经按用户记录在 `usage_events`（0023），有"用户 + 时间"的索引，检查的代价很小。

## 选择
| | A. 费用上限，最近 24 小时（采用） | B. token 数上限 | C. 请求频率限制 |
|---|---|---|---|
| 量的是什么 | 真实花的钱（与用量看板同一套价格） | token 数：缓存命中的输入便宜约 50 倍，按 token 会把正常的多轮对话算得很贵 | 次数：一次深度调研和一句"你好"算一样 |
| 窗口 | 滚动 24 小时：不会出现"零点一过额度全满" | 同左 | 秒 / 分钟级 |

- 默认每人 $1（按实测每次回答约 $0.0003，约 3000 次回答），是防失控的护栏，不影响正常使用；`USER_DAILY_BUDGET_USD=0` 表示不限。管理员不受限。
- **在哪里检查**：发消息、重试（都会开始一次新的执行），在写入消息的同一事务里。不在执行中途打断，例如已经批准的调研计划继续执行。图谱构建有自己的预估和确认（0019），它的费用计入用量、会让之后的提问更早到上限，但构建本身不受这里限制。
- **超限**：429 `quota_exceeded`，`details` 里给出已用和上限；前端提示"最近 24 小时的模型用量已达个人上限（上限 $1），请稍后再试或联系管理员"。不写入任何消息。

## 实现
- `RunService` 的 `Budget`（上限和三档价格）与 `_check_budget`：在 SQL 里按价格算出最近 24 小时的费用；管理员跳过。
- `server/main.py` 从配置构造 `Budget` 放进 `app.state`，`get_run_service` 传给服务；测试里为 None（不限）。
- 配置 `USER_DAILY_BUDGET_USD`（compose、.env.template）。

## 验证
- 测试 4 个：到上限后发消息和重试都被拒绝；缓存命中按低价计算；24 小时之前的用量不算；管理员和上限 0 不受限；接口返回 429 和数字。变异检查 5 项全部被测出。
- compose：临时把上限设得极低，用演示账号在一个临时对话里发消息，返回 429（已用 $0.003），对话里没有写入消息；随后恢复为 $1。验证过程中我犯了一次错误，见 dev-log 7.9。
