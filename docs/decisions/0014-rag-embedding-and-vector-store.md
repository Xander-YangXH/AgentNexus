# 0014 - RAG 选型：embedding 模型、重排与向量库

**状态**：已决定（2026-10-21，用户确认三项均按建议：本地 bge-small-zh-v1.5、默认开启重排、Qdrant 作为派生索引）。

**背景**：阶段 2 要让 Agent 基于上传的文档回答，并展示引用了哪些片段。第一步要定三件事：用什么模型把文字变成向量（embedding）、要不要在召回之后再重排、向量存在哪里。约束：
- **省钱**：用户明确要求尽量减少 API 花销；DeepSeek 官方模型列表只有两个对话模型，没有 embedding 接口。
- **中文为主**的客服知识库场景。
- 阶段 5 有**多租户**：检索必须限定在“本用户 / 本部门可见”的文档里，也就是**带过滤条件的向量检索**。
- 决策 0002 已定：不引入 LlamaIndex，RAG 链路手写，每一步都要能讲清楚。

所有实验脚本与评测集都在 `backend/eval/`，可复现；实验**不调用任何付费 API**。

## 一、embedding 模型

### 实验：自写的中文客服检索评测集（`backend/eval/retrieval_zh_v0.json`）
- 30 篇知识条目，每篇一个主题，**刻意放入近似主题**（退货 / 退款、普票 / 专票、改密码 / 两步验证、物流查询 / 运输破损……）。
- 30 个问题用用户口吻、**换一种说法**，尽量不与原文同词（例如“鞋子开胶了能换一双吗”对应换货条款），这样测的是语义理解而不是关键词。
- 指标：R@1（第一名就是正确答案的比例）、R@3、MRR（正确答案排名倒数的平均）。模型通过 fastembed 在本机 CPU 运行（ONNX，不需要 PyTorch）。

| 方法 | R@1 | R@3 | MRR | 维度 | 编码一篇文档 | 单条查询 | 模型体积 |
|---|---|---|---|---|---|---|---|
| 关键词基线：字二元组 BM25 | 0.43 | 0.53 | 0.53 | – | – | – | – |
| **BAAI/bge-small-zh-v1.5（不加前缀）** | **0.90** | **1.00** | 0.95 | 512 | 2.9 ms | 1.3 ms | 0.09 GB |
| BAAI/bge-small-zh-v1.5（加官方推荐查询前缀） | 0.83 | 1.00 | 0.92 | 512 | 2.4 ms | 2.0 ms | 0.09 GB |
| jinaai/jina-embeddings-v2-base-zh | 0.90 | 1.00 | 0.95 | 768 | 10.1 ms | 7.7 ms | 0.64 GB |
| Qwen/Qwen3-Embedding-0.6B（int8 量化） | 0.97 | 1.00 | 0.98 | 1024 | 54 ms | 165 ms | 1.12 GB |
| Qwen3-Embedding（加推荐指令） | 0.97 | 0.97 | 0.97 | 1024 | 53 ms | 222 ms | 1.12 GB |
| paraphrase-multilingual-MiniLM（弱基线） | 0.73 | 0.83 | 0.80 | 384 | 6.0 ms | 3.2 ms | 0.22 GB |

### 解读
- **语义检索远强于关键词**：换了说法的问题，关键词基线只有 0.43。
- **bge-small-zh 性价比最高**：体积是 Qwen 的 1/12，查询快 100 倍以上，正确答案 **100% 在前三**。
- **官方推荐的查询前缀在本评测集上没有帮助**（bge 反而从 0.90 降到 0.83）。
- 各模型答错的都集中在近似主题上（如“包裹三天没动静”被排到“运输破损”之后）。
- **局限（必须如实说明）**：只有 30 题，每题占 0.03；bge 的 0.90 与 Qwen 的 0.97 只差 2 题，**不足以说明谁更强**。文档和问题都是我写的，可能带有个人表达习惯。结论只能是“bge-small 在这个规模上够用”。阶段 2 要扩充评测集（更多题、真实风格的问法、多篇相关的情况）。

### 建议
- 默认 **BAAI/bge-small-zh-v1.5**，查询不加前缀；本地运行，**零 API 费用**。
- 约束：输入上限 512 token，**分块大小必须控制在这之内**（分块策略在实现时另定）。
- 升级路径：如果扩充后的评测集显示召回不够，再换 Qwen3-Embedding（更强，但 CPU 上单条查询 165ms、体积 1.1GB），或在有 GPU 的环境里使用。换模型要**全量重新计算向量**，所以表里要记录每条向量用的是哪个模型。

## 二、重排（cross-encoder）

### 实验：bge-small 召回前 10 名，用 BAAI/bge-reranker-v2-m3（int8，0.57GB）重排

| | R@1 | R@3 | MRR |
|---|---|---|---|
| 只召回 | 0.90 | 1.00 | 0.95 |
| **召回 + 重排** | **1.00** | 1.00 | **1.00** |

- 原来答错的 3 题全部改对，没有改错任何一题。
- 代价：CPU 上每个问题约 **300 ms**（中位数 303ms，最大 348ms），外加 0.57GB 模型。

### 与成本的关系
DeepSeek 按 token 计费。重排能让第一名基本就是正确答案，于是可以只把最相关的 1~2 段放进提示词，而不是“多塞几段保险”，**直接减少输入 token**；代价是多等约 0.3 秒（相对于 LLM 生成的时间不算大）。

## 三、向量库：pgvector 还是 Qdrant

### 实验（`backend/eval/bench_vector_store.py`）
- 5 万条 512 维向量（与 bge-small 维度一致），分属 100 个租户（每个约 500 条）；100 个查询；两边 HNSW 参数相同（m=16，ef_construction=64）。
- 衡量：召回@10（与暴力精确计算相比）、平均返回条数、延迟 p50 / p95（本机、经网络或驱动的端到端耗时）。
- 版本：pgvector 0.8.7（PostgreSQL 16）、Qdrant 1.19.2，均为发布满两周的版本。
- **局限**：用的是随机向量。随机高维数据对近似索引特别难，召回的绝对值偏低；真实文本的 embedding 有聚类结构，两边都会高得多。两边数据相同，**相互比较是公平的**，但不能把绝对值当成真实场景的表现。

**不过滤时，召回随搜索参数的变化**

| ef | 40 | 100 | 200 | 400 |
|---|---|---|---|---|
| pgvector 召回@10 / p50 | 0.076 / 1.6ms | 0.175 / 2.1ms | 0.321 / 3.4ms | 0.515 / 5.9ms |
| Qdrant 召回@10 / p50 | 0.361 / 2.9ms | 0.560 / 4.3ms | 0.753 / 5.4ms | **0.912 / 5.6ms** |

同样的延迟下 Qdrant 的近似检索质量明显更好。部分原因是结构差异：Qdrant 按段分别建图，小于阈值的段直接精确扫描（本次有约 4000 条未建图）。

**只在一个租户里检索（过滤条件命中 1%）**——这正是阶段 5 多租户的检索方式

| 方式 | 召回@10 | 平均返回 | p50 |
|---|---|---|---|
| pgvector：规划器默认（只有向量索引时选“全表扫描 + 精确排序”） | 1.000 | 10 | 2.6ms |
| pgvector：加租户 B 树索引（规划器选“按租户取出 + 精确排序”） | **1.000** | 10 | **1.2ms** |
| pgvector：**强制走 HNSW**，迭代扫描关闭 | 0.047 | **0.5** | 1.5ms |
| pgvector：强制走 HNSW，迭代扫描 relaxed_order | 0.623 | 10 | 12.6ms |
| pgvector：强制走 HNSW，迭代扫描 strict_order | 0.173 | 10 | 13.2ms |
| Qdrant：租户字段 payload 索引 | **1.000** | 10 | 2.5ms |

- “强制走 HNSW、关闭迭代扫描”复现了 pgvector 的经典问题：先近似取出 40 个最近邻、再按租户过滤，只剩约 0.5 条。0.8 版的迭代扫描能补足条数，但召回和延迟都不理想。
- **关键发现**：每个租户 / 知识库的数据量不大时，**租户内精确检索（B 树取出 + 精确排序）又快又准**，根本不需要近似索引。规划器默认就会这样选。
- Qdrant 也是同样的思路：过滤条件命中的数据很少时，它会直接用 payload 索引取出再精确比较，所以同样是 1.000。
- 数据量继续增长（例如单个知识库几十万块）时，精确检索的成本随数据量线性增长；那时需要“带过滤的近似检索”，Qdrant 的 filterable HNSW 更成熟。

**中文关键词检索（为以后的“语义 + 关键词”混合检索探路）**
- PostgreSQL 内置全文检索不切分中文：“退货政策：商品签收后……”被当成两个整块，用“退货”查**查不到**；标准镜像没有 zhparser / pg_jieba，只有 `pg_trgm`（对中文能做模糊匹配，“退货”0.67、近似词“退款”0.33，很粗糙）。
- 评测集上关键词基线只有 0.43，对“换说法的问题”帮助不大。**第一版不做混合检索**；以后需要精确词（错误码、型号）时，两种方案都要额外处理中文分词。

### 两个方案的取舍

| | pgvector（装在现有 PostgreSQL 里） | Qdrant（独立服务） |
|---|---|---|
| 运维 | 少一个服务；备份、权限统一 | 多一个容器（内存约百 MB 级） |
| 一致性 | 向量与文档元数据**同一事务**：删文档时向量一起删，没有双写问题 | **双写**：文档在 PostgreSQL、向量在 Qdrant，需要保证两边一致 |
| 多租户过滤 | 本规模下租户内精确检索又快又准；规模大了要靠迭代扫描（实测不理想） | 带过滤的近似检索成熟（filterable HNSW + 按命中量选择策略） |
| 近似检索质量（同延迟，随机数据） | 较低 | 较高 |
| 迁移成本 | 现在是 `postgres:16-alpine`：数据库排序规则 `en_US.utf8`、运行在 **musl libc** 上（已核实），且已有文本索引（如用户名唯一索引 `users_name_key`）。pgvector 官方镜像基于 Debian 的 **glibc**，同名排序规则的排序结果不同，直接复用数据目录会让这些索引与数据不一致；musl 不提供排序规则版本号，PostgreSQL **检测不到、也不会警告**。要么导出再导入、要么重建所有文本索引 | 不改动现有数据库 |
| 与路线图 | tech-tradeoffs 中的备选 | ROADMAP / README 原定方案 |

### 建议：Qdrant，但 PostgreSQL 仍是事实来源
- 理由一：多租户（阶段 5）下所有检索都带过滤；数据增长后，Qdrant 的带过滤近似检索明显更可靠，而 pgvector 的迭代扫描实测召回只有 0.62。
- 理由二：不需要更换现有的 PostgreSQL 镜像，避开排序规则迁移的风险。
- **一致性用项目已有的原则解决**：PostgreSQL 存文档与分块（含文本），是事实来源；**Qdrant 只是派生出来的索引，可以随时从 PostgreSQL 重建**——和 Redis 事件流是“视图”是同一个思路（决策 0007）。写入、删除向量都作为后台任务，沿用“先落库再投递”（决策 0005），失败可重试，并提供“全量重建索引”的命令。
- 备选：如果更看重“少一个服务、同事务一致”，pgvector + 租户内精确检索在本项目的数据规模下完全够用；代价是要处理镜像迁移，以及数据增长后的过滤检索问题。

## 四、部署注意（与模型选择无关，必须处理）
- fastembed 默认把模型下载到**系统临时目录**（实验中已占 2.5GB）；临时目录会被清理、容器重启也会丢。上线时要在**构建镜像时下载模型**，或把缓存目录（`FASTEMBED_CACHE_PATH`）放进持久化数据卷。
- embedding 与重排都在 CPU 上运行，会占用 api / worker 进程的 CPU。阶段 1 的派发器在 api 进程里；文档入库（批量计算向量）是重活，应放到后台任务里做，不能阻塞请求。
