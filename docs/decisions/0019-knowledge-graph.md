# 0019 - 知识图谱：抽取方式、存储与范围（草稿）

**状态**：草稿，待用户确认（2026-10-22）。末尾有三个待确认的问题。

**背景**：阶段 3 的目标是“选一个知识库，看到自动抽取的实体关系图，点击节点展开关联”。要定的事：
1. 实体和关系怎么抽取，质量和成本如何；
2. 图存在哪里——路线图原计划用 Neo4j；
3. 范围：抽取什么时候触发、图谱要不要参与问答检索。

约束与前面的决策一致：省钱（DeepSeek 按 token 计费）、PostgreSQL 是事实来源、多租户（按知识库隔离）、每一步都能讲清楚。

实验脚本在 `backend/eval/`：`eval_kg_extract.py`（抽取）、`bench_graph_store.py`（存储）。抽取实验调用了真实模型，花费 $0.09。

## 一、抽取：用 LLM 输出结构化的实体与关系

### 做法
- 每个分块单独调用一次模型。用 `with_structured_output`（强制工具调用）让模型按 Pydantic 定义的结构输出 `{entities: [{name, type, description}], relations: [{source, target, relation, description}]}`，解析失败重试一次。
- 实体类型用固定的 8 类（产品服务、规则政策、流程操作、组织角色、渠道地点、期限数量、技术组件、概念术语），比让模型自由命名更一致。
- 关系的两端必须是同一次输出里的实体，否则丢弃（这类“悬空关系”在 69 块中出现了 5 条）。
- 关闭思考模式（0013），temperature 0，并发 4。

### 实验：两份语料（DeepSeek `deepseek-flash`）
| 语料 | 块数 | 原文字数 | 实体（合并后） | 关系 | 跨块共享的实体 | 费用 | 每千字原文 | 单块耗时中位数 |
|---|---|---|---|---|---|---|---|---|
| 客服条目（30 篇合成一个 md，按标题切块） | 30 | 2.5k | 205（198） | 175 | 几乎没有（出现最多的“订单详情页”只有 3 次） | $0.0185 | $0.0074 | 1.9s |
| 本项目的 5 篇决策记录 | 69 | 20.6k | 842（612） | 693 | 有枢纽：qdrant 18 次、pgvector 8 次、redis 6 次 | $0.0714 | $0.0035 | 2.9s |

- 解析失败 0 次。输出 token 和输入差不多，**成本主要来自输出**。
- 合并后有 39 个实体名在不同块里被标成了不同类型，需要合并规则（例如按多数投票）。

### 抽样核对（6 块、46 条关系，由我人工判断；逐块结果在 `backend/eval/results/kg_extract_*.json`，可复查）
- 正确或可接受：约 36 条（**约 78%**）。
- 典型错误：
  - 方向或谓词错误：例如“取消 run 接口 -[更新为]-> queued 状态”，实际是从 queued 改成 cancelled；“已发货订单 -[需要]-> 快递员”。
  - 噪声实体：代码标识符（`_generate`、`text`）、状态码（“200 响应”）、数值（“p50”“7天期限”）都成了节点。
  - 类型错误：“自动续费管理”被标成技术组件。

### 结论
1. **图谱不是对所有语料都有用**：短小的 FAQ 条目几乎不共享实体，图是碎的；技术文档有枢纽实体，图才有意义。这是“按知识库手动构建、不默认开启”的主要理由（见第四节）。
2. **提示词要收紧**：
   - 每块最多约 8 个实体；
   - 数值、期限、代码标识符、HTTP 状态码不单独成为节点，写进描述里；
   - 关系谓词从一份推荐清单里选。

   这样既减少噪声，也减少输出 token（即成本）。改完在实现阶段用同样的脚本重新测。
3. **成本必须可见、可控**：
   - 按每千字原文 $0.0035~0.0074 估算，2.2 测试用的 3.3MB 文件（112 万字）要 $4~8；
   - 而且其中大量块的内容完全相同，重复的块只抽一次，可以省下绝大部分；
   - 每次构建前先显示预估费用，并设上限。

## 二、存储：PostgreSQL（邻接表）还是 Neo4j

### 实验：同一份合成图（`bench_graph_store.py`）
- 数据：10 个知识库，共 18.5 万实体、55.5 万关系。被测的知识库有 5 万实体、15 万关系，其中 20 个枢纽实体（最大度数 12465），关系度数的中位数是 5。
- 查询（都限定在被测知识库内，对应页面操作）：

| 查询 | PostgreSQL 16 p50 / p95 | Neo4j 2026.08.1 p50 / p95 |
|---|---|---|
| Q1 名称包含关键词（PG 用 pg_trgm，Neo4j 用文本索引） | 0.2 / 0.7ms | 3.5 / 5.1ms |
| Q2 一跳邻居（普通 / 枢纽） | 0.3 / 0.2ms | 1.2 / 2.6ms |
| Q3 两跳子图，最多 200 个节点（普通） | 0.9 / 4.3ms | 3.4 / 5.2ms |
| Q3 两跳子图，最多 200 个节点（枢纽） | 7.5 / 16.3ms | 3.6 / 4.4ms |
| Q4 最短路径，最多 4 跳 | 应用层双向 BFS：2.3 / 11.1ms | `shortestPath`：1.4 / 2.6ms |
| Q4 用递归 CTE 直接写 | **全部 3 秒超时** | — |
| 导入 + 建索引 | 0.8s | 10.4s |
| 内存 | 复用现有实例，约增加 0 | 新增约 **1.0GB**（堆 1g + 页缓存 512m） |

- **两个实验过程中的教训**：
  - 第一版合成图本想用“偏好连接”造出枢纽，结果脚本打印的最大度数只有 81，其实没有枢纽，测不出多跳查询在枢纽上的代价。改为显式指定枢纽后重测，上表是第二版的结果。第一版的数据也保留了：在没有枢纽的图上，两边都在 5ms 以内。
  - PostgreSQL 的递归 CTE 按“路径”展开，不去重。遇到度数上万的枢纽，4 跳内的路径数量爆炸，每次都超时。要么在应用层逐层做广度优先（每层一条查询、维护已访问集合），要么换图数据库。

### 分析
- 在这个规模下，两者都满足页面交互（都在 20ms 以内）。
- Neo4j 的优势：
  - 枢纽节点上的多跳查询稳定（带 LIMIT 时边找边停）；
  - 有内置的最短路径；
  - 可变长度的模式查询用 Cypher 写起来简洁；
  - 简历上有 Cypher 经验。
- Neo4j 的代价：
  - 多一个服务、约 1GB 内存。目前 api 已约 1.1GB，开发机和小规格服务器都会吃紧；
  - 多一条一致性边界：抽取结果仍然要以 PostgreSQL 为准（溯源、权限、删除），Neo4j 只能是派生数据，就像 Qdrant 一样，需要同步和重建；
  - 社区版是 GPLv3 协议。
- 不考虑 Apache AGE（在 PostgreSQL 里跑 Cypher）：它需要更换 PostgreSQL 镜像，会遇到 0014 里记录的排序规则迁移风险。

### 建议：先只用 PostgreSQL；图查询放在一个接口后面，需要时再加 Neo4j 作为派生存储
- 我们需要的查询是：搜实体、一跳 / 两跳展开、偶尔查最短路径，在 PostgreSQL 上都是毫秒级。最短路径用应用层双向 BFS。
- 什么时候值得加 Neo4j：需要图算法（如社区发现、PageRank），或者需要深度不固定的复杂模式查询，或者单个知识库的图规模比现在大一个数量级、枢纽查询变慢。到那时按“派生索引”的方式加入，和 Qdrant 一样可以从 PostgreSQL 重建。
- 这和路线图的原计划不同，属于主动取舍，理由见上表。README 与 tech-tradeoffs 也要相应修改。

## 三、数据模型（PostgreSQL，事实来源）
- `kg_entities`：知识库、规范化名称（合并的依据）、显示名称、类型（多数投票）、描述、被提及次数。在（知识库, 规范化名称）上唯一。
- `kg_relations`：知识库、起点、终点、谓词、描述、权重（被提及次数）。在（起点, 终点, 谓词）上唯一。
- `kg_mentions`：实体或关系 ↔ 分块。用来溯源（在图上点一个节点，能看到它出自哪些原文）和删除：文档重新处理或删除时，删掉这些提及，没有提及的实体和关系一并清理。
- `kg_builds`：每次构建的记录（状态、块数、跳过的重复块、token、费用）。沿用“先落库再投递”和原子抢占，与入库流水线同一个模式。
- **实体合并**：先按规范化名称合并（全角转半角、去空白、英文转小写）。“7天”和“7天期限”这类近义合并，先靠收紧提示词减少，需要时再加“名称向量相似度 + 人工确认”。

## 四、范围
- **抽取的触发**（建议）：知识库页面上手动点“构建图谱”。先显示预估费用（块数、去重后块数、估算金额），确认后在后台执行。不在入库时自动抽取：不是所有知识库都适合做图谱，而且抽取要花钱。
- **前端**：用 cytoscape.js（3.34.3，满两周，MIT 协议，内置力导向布局）做图谱浏览：
  - 关键词搜实体；
  - 点击节点查看属性和出处原文；
  - 展开一跳邻居、高亮子图。

  ECharts 打包后约 1MB，太大；AntV G6 v5 也偏重。
- **图谱参与问答**（建议推迟）：先把图谱做成“浏览和溯源”工具。以后做“图扩展召回”，要先有能证明收益的评测——在现有评测集上，检索已经是 R@1 1.00，体现不出收益，需要专门的多跳问题集。
