# 0025 - 阶段 6.4：安全收尾（登录限流、依赖漏洞、不可信文件解析）

**状态**：已采纳（2026-10-25）。三项都选了推荐方案：登录限流用 Redis 按“账号 + IP”和按 IP 计数；有漏洞的依赖按“安全修复例外”升级、CI 加扫描；PDF / Word 在子进程里解析，有超时和内存上限。

**背景**：功能完成后做一轮安全检查，补 PROGRESS 里一直没勾的“安全清单”。这一轮先用零费用的实验找问题，结果发现三类需要处理的：登录完全没有限流、依赖里有已知漏洞（修复版本都还不满两周）、解析用户上传的文件时一个恶意文件就能卡死入库流水线。

实验脚本：`backend/eval/security_exp/`。不调用模型，零费用。

## 一、实验
### 1. 登录能被多快地猜（`bruteforce.py`）
对本机 api 并发发送错误密码：
| 目标 | 速度 | 结果 |
|---|---|---|
| 真实存在的 admin | **217 次/秒** | 400 次全部 401，没有任何限制 |
| 不存在的用户名 | 271 次/秒 | 同上 |

一天能试约 1900 万次。argon2id 让每次校验花 15ms，但服务端会用线程池并发算，挡不住在线猜测——它防的是“库泄露后离线破解”。

### 2. 响应时间会不会泄露用户名是否存在（`timing.py`）
顺序交替各 200 次：存在的用户中位数 14.0ms，不存在的 14.2ms，分布几乎一致。阶段 5 的设计（用户不存在时也拿假哈希校验一次）有效，上面吞吐量的差别是噪声。**不需要改**。

### 3. 依赖里的已知漏洞（pip-audit 2.10.1、npm audit）
| 包 | 当前 | 漏洞 | 修复版本（发布日期） | 对我们的影响 |
|---|---|---|---|---|
| pypdf | 6.19.0 | 11 个：构造的 PDF 导致死循环、内存耗尽 | 6.21.2（10-21） | **高**：worker 解析用户上传的 PDF |
| pillow | 12.3.0 | 37 个 | 13.0.0（10-16） | 低：后端不处理图片（被 onnxruntime 等间接依赖）；沙盒里 matplotlib 用它写 PNG，但沙盒代码本来就不可信且被隔离 |
| certifi | 2026.7.22 | 内置了一个中间证书私钥泄露的根证书 | 2026.10.19（10-20） | 中：所有对外 TLS（模型 API、fetch 工具）都信任它 |

### 4. 解析不可信文件：一个恶意文件能造成什么（`parse_isolation.py`，在 worker 容器里跑）
不复现具体漏洞，用两个模拟的“恶意解析”（死循环、无限分配内存）比较两种执行方式：

| | A. 线程里解析（现在的做法） | B. 子进程解析（超时 3 秒、内存上限 512MB） |
|---|---|---|
| 死循环 | `wait_for` 报超时，但**线程停不下来**；30 秒后进程仍然退不出去 | 3.0 秒后被杀掉 |
| 内存炸弹 | 吃到容器内存上限，整个 worker 被系统杀掉（影响同一进程里的所有任务） | 0.3 秒后 MemoryError，只有这一次解析失败 |
| 正常 20 页 PDF | 76~109ms | 146~255ms（多约 40~150ms 的进程启动） |

在 worker 里，情况 A 的后果比“一次解析失败”严重得多：
- 心跳在事件循环里照常续约，所以这篇文档**永远停在“处理中”**，租约永不过期，也不会被别的 worker 接管；
- 入库默认只有 1 个执行槽，**之后上传的所有文档都会排队等它**；
- 优雅关停时进程退不出去，只能等 30 秒后被强制杀掉。

实验踩坑：第一版直接在实验进程里 `asyncio.run` 情况 A，实验自己卡了 5 分钟（`asyncio.run` 退出时要等线程池里的线程，Python 3.12 最多等 300 秒）——这正是要证明的现象。改为在独立子进程里测、30 秒超时。

## 三、选项（已确认，均选 A）
### 1. 登录限流
| | A. Redis 计数：按“账号 + IP”和按 IP（推荐） | B. 记在 PostgreSQL | C. 只在 Nginx 上 limit_req |
|---|---|---|---|
| 规则 | 同一账号同一 IP 15 分钟内失败 5 次 → 429（带 Retry-After）；同一 IP 15 分钟内失败 30 次 → 429；登录成功清掉该账号 + IP 的计数 | 同 A，计数放表里 | 每个 IP 每秒最多 N 个登录请求 |

| 代价 | Redis 已有；几十行代码 | 每次失败写库，表要清理 | 粒度粗：分不清不同账号；直连 api 时绕过 |

## 四、实现
### 1. 登录限流（`security/throttle.py`、`server/routers/users.py`）
- 每次登录先 `INCR` 两个计数（“账号 + IP”、IP），超过上限直接 429，**不再校验密码**（猜中了也不知道）；登录成功清掉“账号 + IP”，IP 计数只退回这一次；
- 先计数、再校验：`INCR` 是原子的，并发的请求各自拿到不同的计数，不会“20 个请求同时通过检查”；
- 键名里的用户名取 SHA-256，Redis 里不留明文；固定窗口（`EXPIRE NX`），默认 5 次 / 30 次 / 15 分钟，都可配置；
- 429 带 `Retry-After` 头和 `details.retry_after`，前端显示“请 N 分钟后再试”；
- 客户端 IP：Nginx 用 `$remote_addr` **覆盖** `X-Real-IP`；api 只在 `TRUST_PROXY_HEADERS=true`（compose 里设置）时读这个头，否则用直连的对端地址；
- **计不了数就拒绝（503 `login_unavailable`）**，连接池满了排队等（`BlockingConnectionPool`）。第一版是“Redis 出错就放行”，compose 实测时被绕过，见第五节。

### 2. 依赖
- 例外升级：pypdf 6.19.0 → 6.21.2、certifi 2026.7.22 → 2026.10.19（后端和 MCP 网关）、markdown-it 15.0.2 → 15.0.3。锁文件用 `uv pip compile --exclude-newer <两周前> --exclude-newer-package <包>=<修复版本发布次日>` 生成：只有这几个包放开，而且只放开到修复版本（日期设得太晚会顺带升到更新的版本，certifi 就踩了这个坑）。原因逐条写在 `requirements.txt` 里；
- 不影响我们的写进 `scripts/audit-allowlist.json`（pillow、langgraph-checkpoint-postgres、filelock），每条带原因、修复版本、`review_by`（修复版本满两周的日期）；
- `scripts/audit_deps.py` 对三个锁文件跑 pip-audit：白名单之外的漏洞、过了 `review_by` 的条目都让 CI 失败；前端 `npm audit --audit-level=moderate`。CI 新增 `audit` 任务。

### 3. 解析不可信文件（`knowledge/isolation.py`）
- `.pdf` / `.docx` 在 forkserver 子进程里解析（`.txt` / `.md` 只是解码，不走子进程）；子进程先 `setrlimit(RLIMIT_AS)` 再解析；父进程 `poll(timeout)`，超时就 `kill`；
- 结果映射回 `ParseError`：`parse_timeout`（超时）、`too_complex`（MemoryError）、`parse_failed`（子进程异常退出）；解析器自己的判断（encrypted、empty 等）原样传回；
- forkserver 而不是 fork：worker 是多线程的异步进程，直接 fork 不安全；预先在 forkserver 里导入解析库，之后每次只需 fork，正常 PDF 多约 10~20ms（首次约 200ms）；
- 配置 `PARSE_TIMEOUT_SECONDS`（60）、`PARSE_MEMORY_MB`（1024）；内存上限只在 Linux 上生效。

### 4. `SECURITY.md`
威胁模型、每道防线在哪里、已知局限、怎么报告问题。

## 五、实现中发现的问题
**限流第一版能被并发绕过。** 第一版在 Redis 出错时放行（理由是“限流是附加的一层，不能因为它让所有人都登录不了”），连接池上限 10。单元测试全部通过，但在 compose 里经 Nginx 用 20 个并发请求攻击时，真实账号有 8 次返回 401 而不是 5 次。api 日志里有 3 条 `MaxConnectionsError: Too many connections`：连接池满了，超出的请求拿不到连接、抛异常、被放行。

也就是说，**攻击者不需要让 Redis 宕机，只要并发发请求，就能让一部分尝试跳过限流**。改为：
- 连接池满了排队等（`BlockingConnectionPool`，最多等 5 秒），正常的并发不再报错；
- 真的计不了数（Redis 不可用、等连接超时）就返回 503，不放行。

代价是 Redis 故障时没人能登录。api 本来就依赖 Redis（事件流、取消广播），Redis 故障时对话本身就不可用，所以这个代价可以接受。原则是：**安全检查出错时不能默认通过**。补了两个回归测试：连接池只有 2 个连接、20 个并发请求，结果必须正好 5 个 401、15 个 429；Redis 不可用时返回 503。

## 六、验证
- 单元 / 集成测试：限流 9 个、解析隔离 6 个（内存炸弹那个只在 Linux 上跑）；Python 3.13 和 3.12 各 299 个通过；前端 65 个通过。
- **变异测试**：以下改动都会让测试失败——只按账号计数、无条件信任 `X-Real-IP`、先校验再计数、成功不清计数、成功时清 IP 计数、普通连接池、出错放行、超时不杀子进程。其中“成功时清 IP 计数”第一次**没有**被测出来（测试里的成功登录发生在超限之后，根本走不到清零的代码），补了“先猜 7 次、用自己的账号登录一次、再猜”的测试后才测出来。
- compose 实测：
  - 经 Nginx、50 个并发攻击真实账号：200 次里正好 5 次 401、195 次 429；不存在的用户名 200 次全部 429（IP 上限）；api 日志里没有“计不了数”；
  - 每次换一个伪造的 `X-Real-IP`：第 6 次仍然 429（Nginx 覆盖了这个头），429 带 `Retry-After: 900`；
  - 浏览器里第 6 次错误登录显示“尝试次数过多，请 15 分钟后再试”；
  - worker 容器里：正常 20 页 PDF 首次 0.22 秒、之后 0.08~0.09 秒；死循环 3.01 秒被终止；内存炸弹（上限 1024MB）0.53 秒被拦下；都没有残留子进程；经接口上传 PDF 正常入库；
- 依赖：`scripts/audit_deps.py` 退出码 0（`--today 2026-10-27` 时因白名单到期退出码 1）；`npm audit` 0 个漏洞。

## 七、已知局限
- 本机直连 api 的 8000 端口时可以伪造 `X-Real-IP`（compose 里信任这个头）。这个端口只绑定在 127.0.0.1 上；生产部署不要对外暴露 api 端口。
- 限流只防在线猜测，不防撞库后用对的密码登录；没有多因素认证。
- 分布式攻击（大量 IP 各猜几次）只能靠“账号 + IP”的上限减慢；需要的话可以加“单账号全局失败次数”触发验证码，但那会引入锁别人账号的问题。
- 内存上限只在 Linux 上生效；macOS 上开发时只有超时这一层。
- 白名单里的包要在 `review_by` 之前升级（10-26 langgraph-checkpoint-postgres，10-30 pillow，10-31 filelock），到期 CI 会变红提醒。
