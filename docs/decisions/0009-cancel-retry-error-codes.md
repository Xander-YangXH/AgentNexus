# 0009 - run 的取消、重试与错误码

**状态**：已决定（阶段 1 收尾，2026-10-21）。其中“取消时半截内容不保存”“重试不新增用户消息”是产品取舍，可以再调整。

**背景**：阶段 1 里程碑达成后，run 的生命周期还缺三块：用户不能中途停止；失败只有供应商的原始报错（对用户无意义，还可能泄露内部信息），而且刷新页面后就看不到了；失败后只能重新输入一遍问题。

## 决定

### 1. 错误码：原始报错只给开发者，对外只给错误码
- `agent_runs` 新增 `error_code` 列（迁移 0002）；原始报错仍写进 `error` 列和日志，**不出现在 API 和事件里**。
- 错误码：`timeout`、`llm_rate_limited`（429）、`llm_unavailable`（5xx）、`llm_config`（400/401/403/404）、`interrupted`（关停或重启）、`internal`（其他）。前端负责把错误码翻译成面向用户的文案。
- 分类方法（`runtime/failures.py`）：沿异常链（`__cause__`/`__context__`）查找 HTTP 状态码。OpenAI/Anthropic 的 SDK 异常带 `status_code`；Gemini 经 LangChain 包装后，状态码在异常链下一层 Google SDK 异常的 `code`/`status` 上（已在容器里用错误的 key 实际触发验证）。找不到状态码一律归为 `internal`：宁可保守，也不把我们自己的 bug 说成“供应商问题”。
- 历史数据（0002 之前的失败记录没有错误码）用数据迁移 0003 按原始报错文本回填。**新建迁移而不是修改已执行的 0002**：已执行的迁移不会再次运行，修改它会让各环境的库不一致。

### 2. 取消
- `POST /api/runs/{id}/cancel`：
  - 还在排队：数据库里 `queued → cancelled`，与 `claim` 用同一个条件（`WHERE status='queued'`），两者并发只有一个成功。返回 **200**。
  - 正在执行：取消执行 Agent 的那个任务，返回 **202**；最终结果以 `run.cancelled` 事件和 run 状态为准。
  - 已成功或失败：**409**。已经取消过：**200**（重复请求无害）。
- 实现要点（`runtime/dispatcher.py`）：
  - 每个 run 的 Agent 在**独立任务**里执行，取消只取消这个任务，worker 循环继续工作。
  - **先登记再取消**：取消请求可能落在“已认领、执行任务还没创建”的空档里，所以先记入 `_cancel_requested`，任务创建后立即检查。
  - **区分用户取消与服务关停**：两者都表现为 `CancelledError`。用 `Task.cancelling()` 判断外层 worker 任务是否正在被取消：是 → 关停（记为 `interrupted` 并继续向上抛）；否 → 用户取消（记为 `cancelled`，不再上抛）。如果把所有取消都当用户取消吞掉，关停时 worker 收不到第二次取消，`stop()` 会永远挂住（测试与变异检查已验证）。
- **取消时已生成的半截内容不保存**，与失败时一致（0006/0007）。这是产品取舍：很多聊天产品在用户主动停止时会保留半截内容；如需调整，只要在取消分支里把已累积的文本按助手消息落库。
- 单进程限制：取消信号只在本进程内传递。阶段 4 拆出独立 worker 后，要改为跨进程信号（Redis 或数据库标记，worker 定期检查或订阅）。

### 3. 重试
- `POST /api/runs/{id}/retry`：对**同一条输入消息**新建一个 run，**不新增用户消息**，历史里不会出现重复提问。
- 只允许重试失败或已取消的 run，且输入必须是对话的**最后一条消息**：`load_context` 取的是截止到输入消息的历史，如果后面已经有别的消息，新回复会被追加到最后，顺序就乱了。
- 同一对话仍然受“至多一个活跃 run”的部分唯一索引约束，重试与新消息之间不会并发。

### 4. 刷新后可见
- `GET /api/conversations/{id}/runs` 返回对话的所有 run。前端为每条用户消息取最新的 run：失败或已取消就在消息下方标注原因；最后一条消息再给“重试”按钮。
- 等待首字超过 20 秒时提示“模型响应较慢，可以继续等待或停止”（Gemini 免费档首字实测 7~173 秒）。

## 后果
- 好处：用户能停止、能看到可理解的失败原因、能一键重试；原始报错不再外泄；关停时不会因为取消处理而挂住。
- 代价：错误分类是启发式的，新接入的供应商可能需要补规则；历史数据的回填只能按文本近似。
- 已知局限：取消信号不跨进程（阶段 4 处理）；错误码文案在前端维护，新增错误码要前后端一起改。

## 验证
- 后端新增测试 22 个（`test_run_lifecycle.py` 21 个、`test_migrations.py` 1 个），全量 83 个通过：分类（含异常链、成环、字符串 code、bool）、失败只发错误码、超时与关停各有错误码、取消排队/执行中/空档/已结束、用户取消与关停同时发生时 `stop()` 不挂住、重试复用输入消息且受规则约束、三个接口的状态码、迁移 0003 在独立新库上按版本升级后的回填结果。
- 变异检查 6 项全部被抓住：去掉空档检查、不区分关停（`stop()` 挂住被 3 秒超时抓到）、取消时不登记、重试不检查最后一条、分类不沿异常链、回填正则去掉整词边界（“took 5003 ms”被误判为 5xx）。
- 前端新增测试 6 个（共 23 个）。浏览器实测：等待 21 秒出现“较慢”提示 → 点“停止”（202）→ 显示“已停止生成”与重试 → 刷新后标注仍在、半截内容不在 → 点“重试”（202）得到回复且没有重复的用户消息；开发库回填后，旧的 Gemini 503 失败显示为“模型服务暂时不可用”。
