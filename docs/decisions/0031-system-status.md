# 0031 - 阶段 7.8：运行状态（从业务表聚合，管理员页面 + Prometheus）

**状态**：已采纳（2026-10-25）。用户休息期间授权按推荐方案自主推进，选择由我按推荐方案决定，理由写在下面，可以复核。

**背景**：可观测性只有请求日志、request-id 和用量明细（0011、0023）。看不到队列是否积压、有没有失败在累积、删除后的清理任务是否在重试、有几个 worker 在干活。出了问题只能翻日志。

## 一、关键观察
任务就是业务表里的行（0020：run、文档、图谱构建、清理任务都用租约队列）。所以这些指标**不需要埋点**，直接从表里聚合即可：
- 积压：排队中的数量、最久的等了多久；
- 失败：24 小时内失败的 run、处理失败的文档；
- 耗时：24 小时内成功 run 的 P50 / P95；
- 清理：清理任务数、重试中的数量、最多重试次数；
- worker：此刻持有租约的不同 owner 数（"执行中的 worker"；空闲的 worker 不持有租约，所以看不到——这是局限）。

## 二、选项
| | A. 数据库函数聚合 + 两个出口（采用） | B. prometheus_client 在进程里埋点 | C. 只写日志 |
|---|---|---|---|
| 数据来源 | 业务表（事实来源），多进程、多副本天然一致 | 每个进程自己的计数器，要汇总；worker 没有 HTTP 端口 | — |
| 新依赖 | 无（文本格式自己拼） | prometheus_client | 无 |
| 局限 | 只有"状态"类指标，没有请求级的直方图 | 能做请求级指标 | 只能事后查 |

## 三、RLS 怎么办
api 的数据库角色受行级安全约束（0023），直接 `SELECT count(*) FROM agent_runs` 只能数到"当前用户"的行。做法：迁移 0014 建一个 `SECURITY DEFINER` 函数 `system_status()`：
- 以表所有者的身份执行，绕过 RLS；
- **只返回计数和时长，不返回任何行**；
- 固定 `search_path`，防止调用方用同名对象劫持；
- `REVOKE ALL FROM PUBLIC`，只授权给 api / worker 角色（`storage/roles.py`）。

有测试对照：以 bob 的身份直接查 alice 的 run 是 0 行，函数返回的计数却包含它。去掉 `SECURITY DEFINER` 的变异会被测出来。

## 四、两个出口
- `GET /api/admin/status`：只给管理员，管理页面顶部的"运行状态"卡片。需要关注的项（排队超过 1 分钟、24 小时有失败、文档处理失败、清理任务在重试）标黄。
- `GET /metrics`：Prometheus 文本格式（0.0.4），不要求登录。**它不在 `/api` 下，Nginx 只转发 `/api/`**，所以不会暴露到外网（实测经 Nginx 访问返回的是前端页面），只能在内部网络或本机的 api 端口抓取。

## 五、验证
- 测试 3 个（RLS 角色下的全局计数、管理员 / 非管理员、Prometheus 文本）+ 前端 3 个；去掉 SECURITY DEFINER 的变异被测出。
- compose：迁移到 0014，api 角色有执行权限、PUBLIC 没有；`127.0.0.1:8000/metrics` 输出真实数据（24 小时 39 个成功回复，P50 1.5 秒、P95 9.0 秒）；经 Nginx 的 `/metrics` 返回前端页面；管理页面卡片正常，没有横向滚动。
