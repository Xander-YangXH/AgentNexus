# 0022 - 阶段 4.3：多 Agent 编排、审批中断与报告产物

**状态**：草稿（2026-10-22），待用户确认第三节的选择。

**背景**：阶段 4 的里程碑是“给 Agent 一个复杂任务（例如调研 A、B、C 三个主题分别写一段），能看到它拆解成子任务、并行执行、最后汇总成一份可下载的报告”。4.1 解决了“worker 崩溃后任务被接管、不重复执行”，4.2 解决了“工具在安全边界内执行”。这一步要回答：

1. 子任务（子 Agent）在哪里、以什么粒度并行执行？worker 崩溃时，已完成的子任务会不会重做（重做 = 重复花模型费用）？
2. 一个任务要调用 N 个子 Agent，花费是普通问答的数倍——执行前要不要让用户确认计划？等待确认时，worker 和 run 处于什么状态？
3. 汇总出的报告存在哪里、怎么下载？

实验脚本：`backend/eval/multiagent_exp/`。用真实的 AsyncPostgresSaver（与生产相同的 checkpoint 存储），模型调用用 sleep 模拟，**零费用**。

## 一、实验
### 1. 子任务并行与崩溃续做（`fanout.py`）
用 LangGraph 的 `Send` 把一个计划扇出成多个并行的子任务节点：

| 场景 | 结果 |
|---|---|
| 4 个各 1 秒的子任务，并发不限 | 1.02 秒 |
| 同上，`max_concurrency=2` | 2.03 秒（并发上限生效，可以用来限制同时调用模型的数量） |
| A、B（0.3 秒）已完成，C、D（3 秒）进行中时 `kill -9`，用同一个 thread_id 续做 | **只重做 C、D**，汇总结果 A、B、C、D 完整 |
| 对照：同样 4 个子任务写在一个节点里循环执行，同样时刻 `kill -9` | **4 个全部重做** |

原因：同一步（superstep）里并行的任务，每完成一个，LangGraph 就把它的输出作为 pending write 写进 checkpoint；续做时已完成的任务直接用保存的输出。粒度是“节点（任务）”——**想要“已完成的不重做”，每个子任务就必须是一个独立的任务**，不能在一个节点里循环。

### 2. 审批中断（`interrupt_exp.py`）
用 `interrupt()` 暂停、`Command(resume=...)` 恢复，每一步都在一个新进程里执行（模拟“worker 执行到中断后释放 → 用户批准 → 另一个 worker 恢复”）：

| 场景 | 结果 |
|---|---|
| 计划、审批分成两个节点：开始 → 批准 | 新进程只凭 checkpoint 就能恢复；模型调用 **1 次**；审批节点被执行 2 次（恢复时节点从头重新执行） |
| 反例：模型调用和 `interrupt()` 写在同一个节点 | 模型调用 **2 次**；而且**用户批准的计划（A758…）和实际执行的计划（A759…）不一样** |
| 拒绝并给修改意见 → 回到“制定计划” → 再批准 | 正常：按修改后的计划执行 |
| 等待审批期间的存储 | 3 个 checkpoint，约 1.6KB；不占 worker |

**最重要的发现**：恢复时，含 `interrupt()` 的节点会**从头重新执行**，`interrupt()` 之前的代码再跑一遍。如果那里有模型调用，不只是多花一次钱——真实模型每次输出不同，用户批准的是第一次的计划，执行的是第二次的计划，**审批形同虚设**。所以：有成本或有副作用的步骤，必须放在审批节点之前的独立节点里，审批节点里只做 `interrupt()` 和处理答复。

## 二、和现有系统怎么衔接
- **等待审批不能占着 worker**：等多久取决于用户（可能几小时）。所以 run 进入新状态 `awaiting_approval`：结束这次执行、放弃租约，worker 的执行槽立即释放。用户批准后，api 把 run 改回 `queued` 并记下答复，worker 认领后用 `Command(resume=答复)` 从 checkpoint 继续。这和 4.1 的“接管续做”是同一套机制。
- **仍然算“活跃”**：同一对话同一时刻最多一个活跃 run（已有的唯一索引）。等待审批的 run 也算活跃——用户要先批准、拒绝或取消，才能在这个对话里发新消息，避免两个 run 写同一个 checkpoint。
- **超时只算执行时间**：现有的 run 超时（300 秒）是单次执行的上限；等待审批的时间不计入。调研类任务的执行时间更长，需要单独的超时（例如 900 秒）。
- **审批过期**：等待超过一定时间（例如 24 小时）自动取消，checkpoint 由现有的清理任务回收。
- **事件**：新增 `run.awaiting_approval {plan}`，前端显示计划和“批准 / 修改后重试 / 取消”按钮；刷新页面后从 run 记录恢复这个状态（不依赖事件流）。

## 三、待确认的选择
### 1. 子 Agent 在哪里执行
| | A. 同一个 run 里用 Send 扇出（推荐） | B. 每个子任务是一个独立的子 run，进租约队列 | C. 顺序执行 |
|---|---|---|---|
| 并行 | 同一个 worker 里 asyncio 并发（瓶颈是模型调用的网络等待，不是 CPU） | 可以分散到多个 worker | 无 |
| 崩溃后 | 已完成的子任务不重做（实验 1） | 每个子 run 独立接管 | 同一节点内全部重做 |
| 复杂度 | 一个图；事件、取消、超时沿用现有逻辑 | 父 run 等待子 run、子 run 的事件汇总、取消要级联、计费要归集——都要新做 | 最简单 |
| 代价 | 单个调研任务受一个 worker 的并发上限约束 | 多一套父子任务的状态机 | 慢 N 倍 |

### 2. 审批放在哪里
| | A. 调研计划审批（推荐） | B. 再加“按工具审批”（指定的工具每次调用前都要批准） | C. 不做审批 |
|---|---|---|---|
| 解决什么 | 一次调研会调用 N 个子 Agent，执行前让用户看到子任务列表，确认或修改——控制花费，也避免方向跑偏 | 有外部副作用的工具（发邮件、写入外部系统）需要人确认 | — |
| 现状 | 有明确需求 | 现有工具都没有外部副作用（沙盒、抓取都是只读或隔离的），暂时没有需要它的工具 | — |
| 代价 | 一个审批节点 + run 新状态 + 前端审批卡片 | 同一套机制，多一个按工具的策略配置；建议等有了副作用工具再加 | 里程碑的“可控”无从体现 |

### 3. 报告存在哪里
| | A. 产物表 + 原件存储 + 下载接口（推荐） | B. 写进对话的沙盒工作空间，api 转发下载 |
|---|---|---|
| 结构 | 新表 `artifacts`（属于哪个用户、哪个对话、哪个 run，文件名、类型、大小），内容放在已有的原件存储（api 和 worker 共用的数据卷）；`GET /api/artifacts/{id}/download` 校验归属 | 报告是工作空间里的一个文件 |
| 权限 | 和对话、知识库一样按用户校验 | api 要接入 sandbox 网络、持有 sandbox 令牌——扩大了能接触沙盒服务的进程 |
| 以后 | 沙盒里生成的图表也可以“发布”成产物（4.2 遗留的“文件不能下载”一并解决） | — |

### 4. 怎么进入调研模式
| | A. 对话级的 Agent 类型（推荐） | B. 聊天 Agent 里加一个“派发子任务”工具，由模型决定 |
|---|---|---|
| 结构 | 新建对话时选“聊天”或“深度调研”；调研 Agent 是一个固定流程的图：制定计划 → 审批 → 并行子 Agent → 汇总成报告 | 模型自己决定什么时候拆、拆成几个 |
| 可预测性 | 流程固定，计划结构化（子任务列表），好测、好审批、好估算费用 | 灵活，但拆不拆、拆几个都不确定，审批和费用控制难以统一 |
| 代价 | 对话表加一个字段；用户要先选模式 | 少一个设置，但测试和费用控制都更难 |

## 四、调研 Agent 的草案（按推荐选项）
```
制定计划（1 次模型调用，结构化输出：2~5 个子任务，每个有标题和要回答的问题）
  → 等待审批（interrupt；批准 / 修改意见 → 回到制定计划 / 取消）
  → Send 扇出：每个子任务一个子 Agent（独立的消息上下文，可用对话关联知识库的 knowledge_search 和 MCP 的 fetch，最多 4 轮工具调用）
  → 汇总（1 次模型调用：只拿各子 Agent 的结论和出处，不拿它们的完整过程）
  → 保存报告（Markdown 产物），回复里给出摘要和下载链接
```
- **子 Agent 的上下文是隔离的**：每个子 Agent 只看到自己的子任务，汇总只看到各自的结论。这本身就是控制上下文长度的方法：不需要单独的“摘要压缩”中间件。
- **费用**：大致是 2 次（计划、汇总）+ 每个子任务约 2~4 次模型调用。按 DeepSeek 的价格，3 个子任务一份报告预计约 $0.01~0.03（实现后实测）。
- **上限**：子任务最多 5 个，同时最多 3 个子 Agent 调用模型（`max_concurrency`），调研 run 单独的执行超时。

## 五、风险
- 子 Agent 抓取的网页内容可能包含提示注入：子 Agent 没有沙盒执行和写文件的工具，只能检索和抓取；汇总节点没有工具。
- DeepSeek 的并发与限流：并发上限设为 3，限流错误按现有的模型调用重试处理（实现时确认）。
- 报告内容来自模型，下载接口返回 `Content-Disposition: attachment` 和 `text/markdown`，不在页面里以 HTML 渲染。
