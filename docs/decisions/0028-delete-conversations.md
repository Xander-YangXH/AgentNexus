# 0028 - 阶段 7.3：删除对话

**状态**：已采纳（2026-10-25）。用户休息期间授权按推荐方案自主推进，选择由我按推荐方案决定，理由和备选写在下面，可以复核。

**背景**：0012 只做了"归档"，对话不能删除；对话的沙盒工作空间也从不清理（4.2 的待办）。用户上传给 Agent 的数据、Agent 生成的文件和报告，都只能永久留着。0026 已经有了"数据库事务 + 清理任务发件箱"，删除对话可以沿用。

## 一、一个对话的数据在哪里
| 数据 | 位置 | 删除方式 |
|---|---|---|
| 对话、消息、运行记录、产物元数据、关联的知识库 | PostgreSQL | 删除事务里直接删 |
| 产物原件（调研报告、`share_file` 交付的文件） | 原件存储 | 清理任务 |
| 沙盒工作空间（按对话划分，0021） | sandbox 服务的卷 | 清理任务调用 sandbox 服务新增的 `DELETE /workspaces/{id}` |
| LangGraph checkpoint（thread_id = run_id，0006） | PostgreSQL 的 checkpoint 表（LangGraph 管理） | 清理任务调用 `adelete_thread`；已被保留期清理过的 run 不再列出 |
| 用量明细 | `usage_events`（`run_id` 不加外键） | **保留** |

## 二、选择
- **用量明细保留**：只有 token 数和费用，没有内容；删除对话不改变已经发生的费用，看板和计费要能对得上。阶段 5 建表时就为此没给 `run_id` 加外键。
- **有进行中的 run 时拒绝**（409 `run_conflict`，"请先停止"），而不是自动取消再删。自动取消要等 worker 响应、还要处理"取消后又被接管"等竞态；拒绝是确定的，用户只需点一下停止。删除事务锁住对话行：新消息和新 run 对对话有外键，插入时要拿这一行的共享锁，所以与删除串行。
- **清理任务需要的部件只在 worker 里**：sandbox 客户端（令牌只给 worker）和 checkpointer。api 进程不执行清理任务。即使误执行，缺部件时也会失败并退避重试，不会被当成"已清理"（有测试）。
- **前端二次确认**，并提示"只是不想看到它，可以用归档"。

## 三、实现
- 迁移 `0013`：`purge_jobs` 的知识库 id 改为可空，新增 `conversation_id`、`run_ids`，类型增加 `conversation`。
- `ConversationService.delete`、`DELETE /api/conversations/{id}`（204）；`PurgeService._purge_conversation`；sandbox 服务 `DELETE /workspaces/{id}`（幂等）与客户端 `delete_workspace`。
- assembly：sandbox 客户端改为在 worker 分支里创建一次，工具和清理任务共用。
- 前端：对话菜单里的"删除"与确认框；删除当前对话时清空右侧；`run_conflict` 的中文提示。

## 四、验证
- 测试：删除后各表清空、用量保留、清理任务的内容（已清理的 checkpoint 不列入）、清理执行（原件、checkpoint、工作空间）、缺 checkpointer 时退避重试、进行中的三种状态都拒绝、别人的对话 404、两种数据库角色下的接口、sandbox 删除工作空间（幂等、不影响别的对话、沙盒里写的文件也删得掉）。后端全量通过，前端 70 个。
- 变异检查 7 项全部被测出。
- compose 实测：删除一个用过沙盒的对话，204 后随即 404；消息、run 清零；它的 checkpoint 22 行变 0；工作空间目录（3 个文件）删除；11 条用量明细保留。浏览器里菜单与确认框正常，点"取消"不删除。
