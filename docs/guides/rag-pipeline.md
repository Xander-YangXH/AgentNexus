# 一份文档的完整旅程：从上传到回答里的引用

> 配套《一条消息的完整旅程》（message-lifecycle.md）。那份讲“一条消息怎么变成回复”，这份讲阶段 2：**一份文档怎么变成回答里的 [1]**。
> 读法：先看第 0 节的总图，再按编号逐段读。每段都写了**为什么这样设计**、**对应的代码**和**被实验或踩坑验证过的事实**。最后有自测题。
> 决策记录：0014（选型）、0015（文档入口）、0016（入库流水线）、0017（检索）、0018（问答与引用）。

## 0. 总图

```
上传 ──▶ documents（pending）+ 原件（数据卷）           ← 先落库，再投递
            │  IngestDispatcher（队列 + 扫描兜底，原子抢占）
            ▼
解析（txt/md/pdf/docx）──▶ 分块（句子边界、≤480 token、整句重叠、Markdown 按标题切）
            ▼
向量化（bge-small-zh，本地 ONNX）──▶ 写 Qdrant（等写完）──▶ 同一事务写分块 + 标记 ready
                                                        PostgreSQL 是事实来源，Qdrant 是派生索引

提问 ──▶ prefetch：用原话检索 ─┐
                               ▼
         检索 = 向量召回（按知识库过滤）→ 回库取原文（只要 ready）→ 重排（cross-encoder）
                               ▼
         模型（可再调用 knowledge_search 补查）──▶ 回答带 [n] ──▶ messages.citations 存快照
```

一句话：**写入时先落库再派生，读取时从派生索引找 id、回事实来源取原文。**

## 1. 上传：校验 → 写原件 → 插记录（0015）
- 代码：`services/knowledge.py` 的 `upload`，接口在 `server/routers/knowledge.py`。
- **顺序为什么是这样**：
  - 归属、类型、大小都校验完才写文件，不给无权限或不合规的请求写任何东西；
  - 先写原件再插记录：插入失败时删掉原件即可；反过来，会留下一条“找不到原件”的记录，比孤儿文件更糟。
- **去重**：同一知识库内按内容的 SHA-256 唯一，重复上传返回 409 和已有文档的 id。按文件名去重，改个名就绕过了。
- **原件不进数据库**：大文件会拖慢备份和复制。存储用 `BlobStore` 接口，现在的实现是本地数据卷，以后换 MinIO 只需加一个实现。
- 部署层的坑：Nginx 默认只允许 1MB 的请求体（3.2MB 的文件被拦，返回的还是 HTML）。上限要设得比应用的上限略大，这样超限时由应用返回统一格式的 JSON 错误。

## 2. 后台处理：复用“先落库再投递”（0016）
- 代码：`runtime/ingest.py`，处理逻辑在 `KnowledgeService.process`。
- 文档以 pending 落库，就代表“必须被处理”；内存队列只负责加速，周期扫描兜底。不重复处理靠数据库里 `pending → processing` 的条件更新（与 run 的 claim 同一个模式）。
- **崩溃恢复与 run 不同**：run 中断时标为失败，因为重跑要花模型费用，用户也在等；文档处理到一半时改回 pending 重做，因为它是**幂等**的，用本地模型也不花钱。幂等的前提是：重做前先删掉索引里的旧点，而分块与 ready 状态在同一个事务里，中断时不会留下半套分块。

## 3. 解析与分块：按模型的“视力”切（0015、0016、0017、0018）
- 代码：`knowledge/parsing.py`、`knowledge/chunking.py`。
- **硬约束**：bge-small-zh 最多读 512 个 token，超出部分被静默截断。每块目标 300、上限 480，token 用模型自己的分词器计数。
- 规则：
  - 按句子边界切，不切断句子；
  - 相邻块重叠约 50 个 token，只带整句——宁可不重叠，也不带半句话；
  - 保留原文的空白，段落结构不丢；
  - Markdown 遇到标题就另起一块。
- 三个踩坑，都可以在面试里讲：
  1. **`[UNK]` 击穿限长**：WordPiece 会把超过 100 个字符的单个“词”整体记为 1 个 token，于是一个 3.3MB 的文件只切出了 1 块。解法是计数时取 `max(token 数, 字符数 / 6)`。
  2. **分块吃掉了空白**：每句都做了 `strip()`，导致 Markdown 的标题和正文粘在一起，`Really? Yes` 变成了 `Really?Yes`。2.1 的测试数据太“干净”（只有没有空白的中文句子），没能发现。
  3. **主题混在同一块里**：30 篇条目合成一个 Markdown 文件后，每块混了约 4 个主题，第一名命中率从 0.90 掉到 0.73。按标题切分后回到 0.90，加重排后回到 1.00。

## 4. 向量化与索引：Qdrant 是派生的（0014、0016）
- 代码：`knowledge/embedding.py`、`storage/vectors.py`。
- 模型在**构建镜像时**下载，运行时 `HF_HUB_OFFLINE=1`，启动不联网。
- 写入顺序：先写 Qdrant（等写完），再在一个事务里写分块并标记 ready。所以 ready 的文档一定能被检索到。反方向的失败（索引里多了点）无害，原因在第 5 节。
- 组织方式：
  - 一个集合放所有知识库，按 `knowledge_base_id` 过滤（租户索引）；
  - 应用只认别名。重建索引时建新集合、灌数据、原子切换别名、补录重建期间完成的文档，检索不中断。
- 向量不存数据库：本地模型重算只花 CPU。

## 5. 检索：找 id、回库取原文、重排（0017）
- 代码：`services/search.py`。
- 召回：Qdrant 在指定知识库内做近邻搜索，只返回 id 和相似度。过滤和搜索在一起做，条数不会被过滤掉。
- **回库**：用 id 从 PostgreSQL 取原文，只保留 ready 文档、且再按知识库过滤一次。
  - 派生索引里的脏数据（处理失败没清掉的点）在这里自然消失；
  - 权限不单靠索引里的 payload。
- 重排：cross-encoder 把问题和每个候选放在一起打分，比向量召回更准，但也更慢。端到端评测里，第一名命中率从 0.90 提到 1.00；10 个约 200 字的候选，重排要 1~2 秒。
- 两个关于性能的教训：
  - 0014 的“重排约 300ms”是用 66 字的短条目测的，偏乐观，后来做了更正；
  - 本机实验说“限制向量化线程数，两边都更快”，在容器里结论却相反。性能结论要在部署环境里测。

## 5.5 混合检索：补上精确词（0029）
- 检索时稠密向量和关键词稀疏向量两路各取候选（都带知识库过滤），在 Qdrant 里按排名融合（RRF），再交给重排。代码：`knowledge/keywords.py`、`storage/vectors.py` 的 `search`。
- 为什么：语料大了以后，“429”“CSV”这类只有精确词的查询，正确答案可能进不了向量召回的前 10 个候选（实测 30%），重排救不回来。
- 切词不用分词词典：中文按字二元组，英文和数字按整词；IDF 由 Qdrant 在服务端计算。
- 旧集合没有关键词向量时退回只用稠密向量；在 worker 里运行 `python -m agentnexus.knowledge.reindex` 升级（不能在 api 里运行：api 的角色受 RLS 约束，看不到数据）。

## 6. 问答：预检索 + 工具 + 引用（0018）
- 代码：`agents/buildin/chatbot/`，主要是 `graph.py`、`tools.py`、`agent.py`。
- **图**：`prefetch → model → (tools → model)*`。
  - 预检索用用户的原话先检索一次，结果以“工具调用 + 工具结果”的形式放进上下文；
  - 模型拿到结果通常直接回答，必要时用补全后的检索词再查；
  - 最多 3 轮，`recursion_limit` 兜底。
- **为什么是预检索**：用同一套评测比较。让模型自己决定时，约 3% 的问题它不检索、直接反问用户，而且每次都要调用两次模型；预检索后引用正确率 1.00，模型调用次数减半，耗时从 2.9 秒降到 1.7 秒，费用约少 30%。
- **安全**：工具参数只有 `query`。检索哪些知识库、以谁的身份检索，来自 `RunContext` 和 LangGraph 的 `configurable`，模型改不了，可以防止提示注入导致越权。
- **引用**：
  - 片段编号为 [n]，同一片段重复检索到时沿用原编号；
  - 回答里的 [n] 由正则识别，标出 `cited`；
  - 落库的是**快照**（原文、来源、分数），文档以后重新处理，旧回答的引用依然有效。
- **流式**：`tool.started` / `tool.finished` 事件让前端显示“正在检索”。收到 `tool.started` 时清空临时文字，因为最终回复以图的最终状态为准。

## 6.5 追问：两路预检索（0030）
- 对话里有上一个问题时，预检索查两路：这一句、上一个问题 + 这一句，各自重排后交替合并、去重，仍取 4 个。
- 为什么不直接拼接：换话题时会把检索带偏（实验里第一名从 0.8 掉到 0.2）；两路交替在追问和换话题上都是 1.00。
- 只用于预检索：模型自己发起的检索会写完整的检索词。代价是追问时多一次检索和重排（约 0.3 秒）。

## 7. 怎么证明它是好的：三层评测
| 层 | 脚本 | 测什么 | 结果 |
|---|---|---|---|
| 模型 | `eval_embeddings.py` / `eval_rerank.py` | 选哪个 embedding 和重排模型 | bge-small 第一名命中率 0.90，加重排 1.00 |
| 检索系统 | `eval_search_api.py`、`eval_chunking_md.py` | 经 HTTP 走完整链路后，效果有没有损失 | 和模型层一致；Markdown 按标题切分后也一致 |
| 问答 | `eval_answer_api.py`（花钱，每轮约 $0.01） | 是否检索、引用是否指向正确文档 | 预检索方案 30/30 |

- 为什么要分三层：模型好，不等于系统好（分块、过滤、回库都可能掉点）；系统检索好，也不等于回答好（模型可能不检索、不引用、乱引用）。
- 诚实地说局限：评测集只有 30 篇、30 题，是自己写的；多轮追问只测了 3 组；没有评估回答是否完整。

## 7.5 删除：数据库事务 + 清理任务（0026）
- **一个事务里**：删掉文档（级联分块、图谱出处）；裁剪图谱（没有出处的关系、实体删掉，提及次数重算，用不到的抽取缓存删掉）；插入一条清理任务。代码：`services/knowledge.py` 的 `delete_document` / `delete_kb`，`services/purge.py` 的 `prune_graph`。
- **worker 清理派生副本**：`PurgeService` 删 Qdrant 的点、删原件、按数据库重写 Neo4j；失败按 5、10、20 秒……退避重试，成功后删掉任务。
- **为什么安全**：提交后数据库里就没有了；Qdrant 的点晚几秒删，检索时回库取原文也会过滤掉（第 5 节）。
- **并发**：图谱构建中拒绝删除；处理中的文档可以删，旧 worker 带版本号的写回会失败、丢弃自己写的点（和第 2 节同一套机制）。

## 9. 已知局限（面试时主动讲）
- 单进程：向量化和对话在同一个进程里争 CPU（入库期间重排会慢一倍），阶段 4 拆出独立 worker。
- 改了分块策略后，已入库的文档不会自动重新分块，缺一个“全部重新处理”的管理命令。
- 内容几乎相同的文档会产生重复片段，交给模型前还没有按相似度去重。
- 没有 OCR。（删除接口已在 7.1 补上，见 7.5 节；混合检索已在 7.5 补上，见 5.5 节）
- 评测规模小，多轮评测样本少。
