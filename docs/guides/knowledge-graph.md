# 知识图谱：从分块到可以点开的关系图

> 配套《一份文档的完整旅程》（rag-pipeline.md）。阶段 2 把文档变成可检索的分块，阶段 3 从这些分块里抽出“实体—关系”，存成一张能浏览、能溯源的图。
> 决策记录：0019。实验脚本：`backend/eval/eval_kg_extract.py`、`bench_graph_store.py`。

## 0. 总图

```
知识库页面「构建图谱」──▶ 预估（分块数、去重、已缓存、需调用模型几次、大约多少钱）──▶ 确认
        │ 落库 kg_builds（pending），投递给后台（JobDispatcher，与文档入库共用）
        ▼
按内容去重 ──▶ 查抽取缓存 ──▶ 只对没缓存的文本调用模型（结构化输出，并发 4，每抽完一个立刻缓存）
        ▼
合并（规范化名称、类型多数投票、记录出处）──▶ PostgreSQL：实体 / 关系 / 出处（事实来源，一个事务）
        ▼
整体替换 Neo4j 里这个知识库的子图（派生存储，可以用 sync 命令重建）

浏览：搜实体 / 概览 / 展开邻居 / 最短路径 ← Neo4j（Cypher）
溯源：实体描述、关系、出自哪些原文      ← PostgreSQL
```

## 1. 为什么手动构建、还要先看价钱
- 每个分块都要调用一次模型，成本主要来自**输出** token。技术文档每千字原文约 $0.0025（第 2 版提示词）。
- 实验中，FAQ 类的短条目几乎不共享实体，抽出来的图是碎的，价值不大。所以不在入库时自动抽取，而是由用户对适合的知识库手动构建。
- 三道省钱的关：
  1. 内容相同的分块只抽一次（2.2 测试用的 3.3MB 文件里，大部分块完全一样）；
  2. 抽取结果按“文本哈希 + 提示词版本”缓存，失败后重试、再次构建都不再花钱；
  3. 单次构建有上限（`KG_MAX_CHUNKS_PER_BUILD`），确认框里写明调用次数和金额。

## 2. 抽取：让模型“填表”
- 代码：`knowledge/graph/extraction.py`。
- 用 Pydantic 定义要填的“表”（实体：名称、类型、描述；关系：起点、终点、谓词、描述），`with_structured_output` 通过强制工具调用让模型按表输出。格式不对就重试一次，实际上没有发生过。
- 提示词迭代了一次（v1 → v2），都有数据：
  - **v1 的问题**：数值、代码标识符、状态码都成了节点；同一个名字被标成不同类型。
  - **v2 的做法**：每段最多 8 个实体，上面那些不单独成为节点，谓词优先从推荐清单里选。
  - **结果**：实体数减少约 40%，同名不同类型从 39 个降到 17 个，费用降低约 28%。但抽样的关系正确率仍然约 76%，没有提高——**收紧提示词能去掉噪声，治不了“理解错”**。
- 程序侧的清洗：丢弃两端不在实体里的关系（悬空关系）和自环，合并同一段里重复的实体。

## 3. 合并：同一个东西只留一个节点
- 代码：`knowledge/graph/merge.py`（纯函数，方便测试）。
- 合并规则：
  - 规范化名称（全角转半角、去空白、英文转小写）相同就合并，例如“Qdrant”“qdrant”“Ｑｄｒａｎｔ”；
  - 显示名称取出现最多的写法；
  - 类型多数投票；
  - 描述取最长的一条；
  - 提及次数 = 出现在几个分块里。
- 局限：近义词（如“7天”和“7天期限”）不会合并。先靠提示词减少，以后可以加“名称向量相似度 + 人工确认”。

## 4. 存储：为什么既有 PostgreSQL 又有 Neo4j
- 选型时做了基准测试（5 万实体、15 万关系，含度数上万的枢纽节点）：
  - PostgreSQL 的页面查询都在 20ms 以内；
  - 用递归 CTE 求最短路径，遇到枢纽会路径爆炸、全部超时；改成应用层双向 BFS 只要 2.3ms；
  - Neo4j 在枢纽上更稳（约 4ms），但要多约 1GB 内存。
- 最终按原计划引入 Neo4j，取舍是：用资源换来 Cypher 的表达力（可变长度路径、`shortestPath`）和后续接图算法的空间。
- **分工和 Qdrant 一样**：PostgreSQL 是事实来源（实体、关系、出处、构建记录、权限），Neo4j 是派生存储（只存节点和边）。每次构建的最后一步整体同步过去；坏了或丢了，就用 `python -m agentnexus.knowledge.graph.sync` 重建。
- 查询分工：图的结构查 Neo4j，详情和出处查 PostgreSQL；权限先在 PostgreSQL 里校验，再按知识库过滤 Neo4j。

## 5. 失败与恢复（都有测试）
| 情况 | 结果 | 重试的代价 |
|---|---|---|
| 抽到一半模型限流（429） | 构建失败，错误码 `llm_rate_limited`；已抽的已缓存 | 只补剩下的 |
| Neo4j 不可用 | 构建失败，错误码 `graph_store_unavailable`；PostgreSQL 里的图已写好 | 只重新同步，不调用模型 |
| 进程重启 | 执行中的构建改回 pending，自动继续 | 全部命中缓存 |
| 同时点两次构建 | 第二次返回 409（部分唯一索引：一个知识库同时只能有一个进行中的构建） | — |

## 6. 前端
- 代码：`web/src/components/GraphPanel.vue`，用 cytoscape.js 绘制。
- 节点按类型着色、按被提及次数决定大小。点击节点：周围以外的元素变暗，右侧显示描述、关系、出处原文。可以展开邻居、查最短关联（红色高亮）。
- 踩坑：右侧详情栏一开始宽度为 0。cytoscape 给内部 canvas 设了固定宽度，flex 布局里的画布不肯收缩，把详情栏挤没了。解法是给画布加 `min-width: 0`、详情栏设 `flex: none`，并在详情栏出现后调用 `cy.resize()`。

## 8. 已知局限
- 关系正确率约 76%（抽样，人工判断），图上会有错误关系，需要靠出处原文核对。这正是做“溯源”的原因。
- 文档重新处理后，图不会自动更新，需要重新构建（有缓存，未变的分块不花钱）。
- 近义实体不合并；没有图算法（社区发现等）；图谱还没有参与问答检索（按 0019 的决定推迟）。
- Neo4j 多占约 1GB 内存。
