# 独立 worker 与租约：任务怎么在进程崩溃后被正确接管

> 配套《一条消息的完整旅程》。阶段 1 时 run 在 api 进程里执行，靠“单进程假设”做恢复；阶段 4.1 把执行拆到独立的 worker 进程，
> 可以起多个副本，任何一个崩溃、卡住或被关停，它的任务都会被别的副本接管——**既不卡死，也不重复执行**。
> 决策记录：0020（含 ARQ 与原型的对比实验）。代码：`runtime/lease.py`、`runtime/dispatcher.py`、`runtime/jobs.py`、`worker.py`。

## 0. 总图

```
api 进程                                         worker 进程（可多个副本）
提交 run / 上传文档 / 创建图谱构建                   ┌─ LISTEN agentnexus_jobs ──▶ 唤醒对应的执行器
  └─ 同一事务：写业务行（queued / pending）           │   （没收到通知时，空闲执行槽每 5 秒轮询一次）
       + SELECT pg_notify('agentnexus_jobs', 'run') ─┘
                                                   认领：UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)
                                                         待执行 或 执行中但租约已过期 → 执行中，版本号 +1，尝试次数 +1
                                                   执行：心跳每 10 秒续约（带版本号）→ 续约失败 = 已被接管，立刻停止
                                                   写回：完成 / 失败 / 取消都带 lease_version 条件（fencing）
取消：写 cancel_requested_at（事实来源）         ◀── Redis 广播（立即送达）；心跳时也检查数据库标记（兜底）
```

## 1. 为什么不能再用“启动恢复”
- 阶段 1（0005）：api 启动时把所有 `running` 的 run 标为失败。这只在“只有一个进程”时正确。
- 一旦有两个进程：B 启动时，会把 A 正在执行的 run 标成失败——**误伤**。
- 租约把“谁还活着”变成一个可以判断的问题：持有者定期续约；超过租约时长没续，就算死了，可以接管。不管有几个进程都成立。

## 2. 三个缺一不可的机制
| 机制 | 解决什么 | 没有它会怎样 |
|---|---|---|
| 租约（30 秒） | 判断执行者是否还活着 | 只能靠超时，接管时间和任务时长绑定（ARQ：kill 后 34 秒，Agent 任务会是 5 分钟） |
| 心跳（10 秒，租约的 1/3） | 长任务不会被误判为死；续约失败就知道自己被接管了 | 跑得久的任务会在执行中途被别人接管 |
| fencing token（`lease_version`） | 没死、只是卡住的旧 worker 恢复后，不能再写回结果 | 两份结果互相覆盖、重复写入（只靠时间永远分不清“死了”和“卡了”） |

实验（`backend/eval/queue_exp/`）：kill -9 后，原型 6 秒接手、0 重复；ARQ 34 秒接手、从头重做 3 步。暂停后恢复的旧 worker，写入被 fencing 拒绝。

## 3. 接管之后怎么继续
- **对话 run**：LangGraph 的 checkpoint 按 run_id 保存。接管者用同一个 thread_id 读取进度：
  - 图还没跑完：从最后一个 checkpoint 继续，已完成的检索和模型调用不重做；
  - 图已经跑完、只是没来得及落库：直接用最终状态；
  - 没有 checkpoint：从头开始。
- **事件**：接管者先发 `run.resumed {attempt}`，之后的 token 都带 attempt。前端清空上一次的半截文字，并忽略更早尝试的残余 token（旧 worker 在心跳发现自己被接管之前，最多会再流出一个心跳间隔的 token）。
- **文档入库、图谱构建**：本来就可以安全重做（入库幂等；图谱的抽取有缓存，重做不重复花钱）。
- **上限**：一个 run 最多执行 3 次（含接管）。如果每次执行都会把 worker 搞崩，第 4 次就直接标为 `interrupted`，不再无限循环、无限花钱。
- **边界**：只能保证“已提交的步骤”不重复。崩溃那一刻正在进行的一步（例如一次模型调用）会重做，最多一步。

## 4. 最容易漏掉的一点：fencing 管不到外部系统
- fencing token 只对**数据库里的写入**有效。Qdrant 不认我们的版本号。
- 文档入库原来的做法有两处“按文档 id 删除向量点”。时间线：旧 worker 卡住 → 新 worker 接管，写好点并标记 ready → 旧 worker 恢复，按文档删除——**把新 worker 的点全删了**。文档显示 ready，却检索不到，而且没有任何报错。
- 改法：只删“自己的”，只由“赢家”清场：
  - 每次尝试只写自己的点（分块 id 每次都是新的）；
  - 失败时按 id 删除自己写的点；
  - 只有带版本号成功标记 ready 的执行者，才清理这个文档下“不属于本次结果”的点；
  - 旧 worker 在清理之后才写的点会成为孤儿点：检索时回数据库取原文，自然被过滤，无害。
- 同一个事务里也要**先做版本校验、再写数据**：第一版先写分块，旧 worker 撞上接管者分块的唯一约束、直接抛异常，走不到“删自己的点”那一步。
- 图谱的 Neo4j 同步也有一个极小的窗口（两条语句之间恰好被暂停并被接管），无法完全消除。Neo4j 是派生存储，用 sync 命令或再构建一次即可修复。

## 5. 取消为什么写两份
- 取消请求写进数据库（`cancel_requested_at`），这是事实来源；再通过 Redis Pub/Sub 广播，立即送达执行它的 worker（实测 0.02 秒）。
- 广播丢了也没关系：心跳时会检查数据库标记（最多晚 10 秒）。
- 如果用户取消后 worker 恰好被关停、放弃了租约，接手的 worker 认领后会先看到取消标记，直接收尾为“已取消”，**不会再执行一遍**。

## 6. 唤醒：NOTIFY 在事务里发
- 提交任务时，在同一个事务里执行 `pg_notify`：**事务提交时才送达，回滚就不送达**——不会出现“通知到了、任务却不存在”。
- 放弃租约（优雅关停）时也发通知，空闲的副本立即接手：修复前 `docker stop` 后要 5.2 秒，修复后 0.9 秒。
- worker 的通知监听断了会重连，期间靠轮询兜底。
- 一个 asyncio 的坑：不要用 `asyncio.wait_for(anext(异步生成器), t)` 等通知——超时取消 `anext` 会把生成器关掉，下一次读取就是 `StopAsyncIteration`。

## 7. 部署与验证
- compose 新增 `worker` 服务（`python -m agentnexus.worker`），可以 `--scale worker=2`。api 不再执行任务，也可以多实例。
- 存活检查：worker 每 10 秒更新一个文件，30 秒没更新就判为不健康。关停宽限期 30 秒，用来放弃租约。
- 里程碑实测（2 个副本，假模型慢速输出约 30 秒的回复）：

| 操作 | 接管 | 结果 |
|---|---|---|
| `kill -9` 正在执行的 worker | 24.8 秒后（租约到期）被另一个副本接管 | 1 条回复、内容正确，事件 started → resumed → completed |
| `docker stop`（优雅关停） | 0.9 秒后被接管（放弃租约时发了通知） | 同上，被关停的容器退出码为 0 |
| 从 api 取消执行中的 run | 0.02 秒（Redis 广播） | 状态为已取消，没有留下回复 |

## 9. 已知局限
- 只能保证已提交的步骤不重复，崩溃时正在进行的一步会重做（最多一步）；外部副作用需要幂等。
- api 和 worker 都加载 embedding 与重排模型，各约 1GB 内存。
- 进程退出时 onnxruntime 与其他原生库偶发析构崩溃（只在测试进程里观察到，退出码 134）。测试里用 `os._exit` 绕过；生产 worker 优雅关停时退出码为 0。
- Neo4j 同步有一个极小的不一致窗口（见第 4 节）。
