# 开发日志

按时间顺序记录每一步**做了什么、为什么这么设计、备选方案与取舍、遇到的问题与解法**。与其他文档的分工：`decisions/` 只记重大决策的结论；`interview-prep.md` 按模块整理成"面试怎么讲"；本文件保留过程，尤其是排错过程，因为"遇到过什么问题、怎么定位的"是最有说服力的项目经历。

条目模板：目标 → 设计思路 → **技术选型明细（选了什么、为什么、否掉了什么）** → 备选与取舍 → 遇到的问题 → 验证 → 面试可讲点。

## 2026-10 · 阶段 0：环境与交付物

### 目标
一条 `docker compose up` 起 Postgres + Redis + FastAPI，`/health` 返回 200，新人 clone 即可复现。

### 设计思路
- **依赖就绪靠 healthcheck，不靠 sleep 或重试**。`depends_on` 默认只等容器启动，而 Postgres 进程起来到真正接受连接之间有窗口期。给 postgres（`pg_isready`）、redis（`redis-cli ping`）配 healthcheck，api 用 `condition: service_healthy` 等待。
- **存活与就绪探针拆开**。`/health` 不查依赖：依赖挂了重启 api 也没用，反而可能引发重启风暴。`/health/ready` 才真连 Postgres 和 Redis，失败返回 503，并带上是哪个依赖挂了。
- **配置全走环境变量**。`.env` 不提交，提交 `.env.template`；连接串在 compose 里用服务名拼装，应用代码只读 `DATABASE_URL`、`REDIS_URL`。
- **宿主机端口只绑 127.0.0.1**，避免开发机上的数据库被局域网访问。
- **Dockerfile 先装依赖再拷代码**，改业务代码时依赖层缓存不失效；uvicorn 监听 `0.0.0.0`，否则端口映射后宿主机访问不到。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| `postgres:16-alpine` | 16 是稳定的主流版本，与 `learning/langgraph` 练习用的版本一致，行为可对照；alpine 镜像小，拉取快 | 17 太新、生态跟进不全；`pgvector` 镜像暂不需要（向量库选 Qdrant）。alpine 用 musl，排序规则（collation）与 Debian 镜像略有差异，生产环境建议换 Debian 系镜像 |
| `redis:7-alpine` + `--appendonly yes` | 后续要放队列信号、事件流，开 AOF 持久化，重启不丢最近写入 | 默认只有 RDB 快照，崩溃会丢最近几分钟数据 |
| `python:3.12-slim`（而不是 alpine） | 依赖 `psycopg-binary`、`uvloop` 等带 C 扩展的包，glibc 的 slim 镜像有预编译 wheel；alpine（musl）常没有 wheel，需要现场编译，慢且易失败 | 镜像比 alpine 大。注意：本机 venv 是 Python 3.13、容器是 3.12，代码用到的 `StrEnum` 需 ≥3.11，两者都满足；若后续依赖出现版本差异再统一 |
| 单阶段 Dockerfile | 当前依赖少，先求简单可读 | 多阶段构建能缩小镜像，等镜像体积成为问题再做 |
| `uvicorn[standard]` | 带 `uvloop`（更快的事件循环）和 `httptools`（更快的 HTTP 解析） | 纯 `uvicorn` 更轻，但性能收益在 I/O 密集的 Agent 场景里值得 |
| 依赖清单用 `requirements.txt` | 对 solo 项目足够，Dockerfile 里"先拷清单再装依赖"容易利用层缓存 | `uv`/`poetry` 有锁文件、可复现性更好；依赖多起来后再迁移 |
| Compose 而不是 Kubernetes | 本地一键复现，学习与运维成本低 | K8s 的滚动发布、弹性伸缩，对简历项目的体量是过度设计 |

### 备选与取舍
- 健康检查用 `curl` 还是 Python 标准库？slim 镜像没有 curl，为一个探针装 curl 会增大镜像，所以用 `python -c "urllib.request.urlopen(...)"`。
- `/health` 要不要顺带查依赖？不查。把"进程活着"和"能提供服务"分成两个探针，各自语义清晰。

### 遇到的问题
1. **demo yml 解析失败**（`mapping values are not allowed in this context`）。原因：`command: sh -c "echo 'x: y'"` 里的 `: ` 被 YAML 当成映射的键值分隔。先试了加外层引号，内外引号又冲突；最终改成列表形式（`command: [sh, -c, "..."]`），不再依赖引号转义。教训：compose 里带冒号、引号的 shell 命令一律用列表形式。
2. **一开始 Docker daemon 没启动，无法验证里程碑**。当时只能做到 `docker compose config` 校验配置和用 TestClient 测应用代码，镜像构建与真实 `up` 没跑过。做法是把"已验证/未验证"在交接文档里分开写清楚，不把未验证的写成已完成；等 Docker 起来后在本机补测：三服务 healthy，停掉 postgres 后 `/health` 仍 200、`/health/ready` 变 503，恢复后回到 ok。
3. 仓库里残留了一个 0 字节的 `.git/HEAD.lock`，导致提交失败。先确认没有 git 进程在运行，再删除。教训：删锁文件前先确认没有持有者。

### 验证
`docker compose ps` 三个服务 healthy；两个探针行为符合预期（见上）；api 容器内能按服务名解析 postgres、redis。

### 面试可讲点
`depends_on` 与 healthcheck 的区别；存活 vs 就绪探针为什么要分；容器里的 localhost 是自己，容器间用服务名；`down -v` 会删数据卷。详见 `interview-prep.md` 的"本地开发环境"一节与 `decisions/0003`。

## 2026-10 · 阶段 1（一）：数据层

### 目标
把用户、对话、消息、AgentRun 落库，并实现"先落库再投递"的第一半：提交消息的同时创建一个 `queued` 的 run。

### 设计思路
- **事实来源是数据库，队列只是触发器**。run 以 `queued` 状态落库后，投递队列即使失败或进程崩溃，也可以靠扫描 `status=queued` 补发。这要求"用户消息"和"queued run"必须在**同一个事务**里提交。
- **并发正确性交给数据库，不在应用层加锁**。多个 api/worker 实例下，应用层的"先查后改"都有竞态，而数据库的约束和条件更新是串行化的：
  - 抢占执行权：`UPDATE agent_runs SET status='running' WHERE id=? AND status='queued'`，根据 `rowcount` 判断是否抢到。
  - "同一对话同一时刻最多一个活跃 run"：部分唯一索引 `WHERE status IN ('queued','running')`。原因是两个 run 并发写同一个 thread 的 checkpoint 会互相覆盖。
  - 终态不可覆盖：`finish()` 只允许从 running 转出，迟到的结果不能改写已结束的 run。
- **分层各管一件事**：`repositories` 只做单表读写、不管事务；`services` 一个方法一个事务，成功全提交、失败全回滚；表定义放 `storage/postgres`。
- **消息排序用自增 `seq`**：同一事务内 `now()` 都是事务开始时间，多条消息时间戳相同；uuid 又无序，两者都不能保证顺序。
- **迁移用独立的一次性 `migrate` 服务**：多个实例同时启动各自跑迁移会互相抢，一次性服务跑完退出，api 用 `service_completed_successfully` 等它。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| SQLAlchemy 2.0 异步 | 需要部分唯一索引、CHECK、条件更新这类细粒度控制，同时表会越来越多，需要模型层和迁移联动；2.0 风格（`Mapped[]` 类型注解）与 FastAPI 的类型驱动风格一致 | 直接写 SQL：灵活但表多了后重复代码和迁移同步成本高；SQLModel：封装更薄但对复杂约束支持不如原生 SQLAlchemy；Tortoise 等：生态和资料不如 SQLAlchemy |
| psycopg3 作为驱动 | LangGraph 的 `PostgresSaver` 用的就是 psycopg3，项目里只维护一套 Postgres 驱动和连接配置；同时支持同步和异步 | asyncpg 更快，但会出现两套驱动、两套连接串格式，收益不值得 |
| Alembic | 模型改了能 autogenerate 出迁移草稿，再人工审核；迁移有版本链，可回滚 | `create_all()` 只能建表不能演进已有表；纯手写 SQL 脚本没有版本管理 |
| 主键用 UUID，由数据库 `gen_random_uuid()` 生成 | id 会出现在 URL 里，自增整数可枚举、会泄露数据量；UUID 不可猜，多实例无需协调；PG13+ 内置该函数，不用装扩展 | 自增 bigint 索引更紧凑、插入更有序；UUID 索引更大。所以**需要顺序的地方（messages）单独加 `seq` 自增列**，主键仍用 UUID |
| 时间列用 `timestamptz` | 带时区，跨时区部署和展示不出错 | 不带时区的 `timestamp` 容易在服务器时区变化时产生歧义 |
| status/role 用 `String + CHECK` | 增减枚举值只需一次迁移改约束；原生 PG enum 增删值更麻烦 | 原生 enum 存储更省，但演进成本高 |
| Alembic 用同步引擎 | 迁移是一次性脚本，异步无收益，同步更简单稳妥 | 在 env.py 里跑异步引擎要额外样板代码 |
| 测试用真实 Postgres + `pytest-asyncio` | 部分唯一索引、`UPDATE … WHERE` 的 rowcount、事务回滚，SQLite 模拟不出来；测试库由真实迁移建表，顺带验证迁移脚本 | SQLite 内存库更快，但会测出"假通过"；代价是跑测试要先起 Postgres |

### 备选与取舍
- **ORM**：SQLAlchemy 异步 vs 直接写 SQL。选 SQLAlchemy，因为表和关系会随阶段 2-5 不断增加，需要迁移工具和模型层；驱动选 psycopg3，与 LangGraph 的 PostgresSaver 同一个，不维护两套驱动。代价是学习成本，且部分唯一索引、条件更新必须在真实 Postgres 上测试，SQLite 模拟不了。
- **Alembic 用同步引擎**：迁移是一次性脚本，不需要异步，同步更简单稳妥。
- **status/role 用 CHECK 约束而不是 PG 原生 enum**：枚举值后续要增减时，改 CHECK 约束只需一次迁移，原生 enum 的变更更麻烦。
- **lease 字段这一步不加**：阶段 4 才需要，提前加是臆测的设计；届时通过新迁移追加，也正好能练习"在线加列"。

### 遇到的问题
1. **`Column object 'id' already assigned to Table 'users'`**。我把 `mapped_column(...)` 的结果存在模块变量 `_uuid_pk` 里给四个模型共用。一个列对象只能属于一张表。改成函数 `_uuid_pk()`，每次新建。
2. **测试夹具里 `Could not parse SQLAlchemy URL`**。想用 `psycopg.conninfo.make_conninfo` 替换库名，但它返回的是 `key=value` 格式，不是 URL。改用 SQLAlchemy 的 `make_url(...).set(database=...)`，全程保持 URL 形式。
3. **macOS 的 `sed -i` 报 `invalid command code`**：BSD sed 要求 `-i ''`。
4. **Alembic 弃用警告**（`No path_separator found`）：在 `alembic.ini` 加 `path_separator = os`。
5. **预防性处理：Alembic 的 `sqlalchemy.url` 含 `%` 时会被 ConfigParser 当成插值语法报错**。数据库密码里出现 `%`、`@` 等字符很常见。设置到 Alembic 配置时把 `%` 转义成 `%%`（`conftest.py` 里的 `.replace("%", "%%")`）。同时统一用 `to_sqlalchemy_url()` 把应用通用的 `postgresql://` 转成 SQLAlchemy 需要的 `postgresql+psycopg://`，避免连接串格式在各处不一致。
6. **一个我不确定的点：在 `session.begin()` 块里手动 `rollback()` 再退出，是否安全？** 没有凭印象判断，写了测试 `test_complete_only_from_running_and_leaves_no_orphan`，验证"run 不在 running 时，助手消息整体回滚、不留孤儿"，通过。
7. **验证 compose 时误判**：执行 `up -d --build` 后只 `sleep 10`，并用 `grep` 过滤了输出，看到 api 还是旧容器、`migrate` 不在列表里，一度以为没生效。实际是镜像还在构建，grep 又把关键信息过滤掉了。重新查看完整输出后确认 `migrate` 退出码 0。教训：验证时看完整输出和状态，不要过早过滤；耗时操作要等它真正结束。

### 验证
- 8 个集成测试在真实 Postgres 上通过：原子提交；他人对话/不存在的对话统一报 `ConversationNotFound`；提交失败不留孤儿消息；前一个 run 结束后可以再提交；8 路并发 claim 只有 1 个成功；未 claim 不能直接 complete；失败记录错误且终态不可再改；同事务内消息顺序正确。
- compose：`migrate` 退出码 0，五张表建成，重复 `up` 迁移幂等，`/health/ready` 仍为 ok。

### 面试可讲点
为什么 submit 要同事务；为什么用条件更新和部分唯一索引而不是应用层加锁；消息为什么不能按 `created_at` 排序；迁移为什么单独成一次性服务。详见 `interview-prep.md` 的"Agent 运行链路"与 `decisions/0004`。

## 2026-10 · 阶段 1（二）：API 路由层

### 目标
把 `RunService` 等服务暴露成 HTTP 接口：创建用户/对话、发消息、查历史、查 run 状态。

### 设计思路
- **路由薄、服务厚**：路由只做"解析参数 → 调服务 → 返回"；业务规则（归属校验、同事务写入）在服务层。HTTP 状态码不出现在服务层：服务只抛领域异常（`ConversationNotFound`、`RunConflict`…），在 `main.py` 统一映射成 404/409。这样以后换成 worker 或 CLI 调同一套服务时不依赖 HTTP。
- **发消息返回 202 Accepted，不是 200/201**：消息和 run 已经落库，但执行是异步的。响应体直接返回 run（含 `status=queued`），客户端拿 run id 轮询或订阅进度。语义上 202 恰好是"已受理，尚未处理完"。
- **鉴权占位**：阶段 5 才做真正的 RBAC，但数据隔离从现在就要生效。用 `X-User-Id` 头 + 一个 `current_user_id` 依赖（校验用户存在，否则 401）。以后接 token 认证只替换这个依赖。路由签名里写 `CurrentUser`，不关心身份从哪来。
- **越权与不存在一视同仁**：访问别人的对话/run 返回 404，和不存在一样，不泄露 id 是否存在（返回 403 会暴露资源存在）。
- **sessionmaker 通过依赖注入**：lifespan 里创建引擎并挂到 `app.state`，路由经 `Depends` 取用；测试用 `dependency_overrides` 换成测试库，不用改任何业务代码。
- **`create_app()` 工厂**：测试可以创建独立的 app 实例。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| Pydantic 请求/响应模型（`schemas.py`）与 ORM 模型分开 | 对外接口字段由 schema 显式声明，数据库加列不会意外泄露到接口；校验（如内容 1~20000 字符）放在入口 | 直接返回 ORM 对象省代码，但接口和表结构耦合，改表即破坏接口 |
| `X-User-Id` 头做鉴权占位 | 数据隔离从现在起就生效，又不引入密码哈希、token 签发这些阶段 5 的内容；替换点只有一个依赖函数 | 直接上 JWT：这一步会被无关代码淹没；完全不做隔离：之后补隔离要改所有查询 |
| 依赖注入传 sessionmaker | 测试用 `dependency_overrides` 换成测试库，业务代码零改动 | 全局单例连接：测试要打补丁，且难以并行 |
| `create_app()` 工厂 | 每个测试得到独立 app 实例，互不污染 | 模块级全局 `app` 在测试间共享状态 |
| 测试用 `httpx.AsyncClient` + `ASGITransport` | 数据库夹具本身是异步的，客户端也用异步，整条链路在同一个事件循环里；不需要真的监听端口 | Starlette 的同步 `TestClient` 内部起独立线程/事件循环，与异步夹具混用容易出现跨事件循环的问题（这里是设计上避开，并非实际踩到） |
| 发消息返回 202 + run | 语义为"已受理、未处理完"，客户端用 run id 查进度 | 200/201 会让客户端误以为已处理完；同步等待 Agent 完成则会占住 HTTP 连接几十秒 |

### 备选与取舍
- 重复用户名：先查再插有竞态，改成以数据库唯一约束为准，捕获 `IntegrityError` 转成 `UserExists`（409）。和阶段 1（一）"并发正确性交给数据库"一脉相承。
- 创建用户暂不做登录/密码：这一步的目标是链路，密码哈希、token 属于阶段 5，提前做会引入大量与主线无关的代码。
- 这一步**还没有派发和执行**：发消息后 run 停在 `queued`。这是有意的，把"落库"和"派发"拆成两步，各自可单独验证。

### 遇到的问题
1. **`TypeError: 'function' object is not subscriptable`**：在 `ConversationService` 里定义了方法 `list`，类体里后面的 `list[Message]` 类型注解取到的是这个方法，而不是内置 `list`。症状在 import 时就爆，但报错位置指向的是别的方法的注解，一开始不直观。解法：方法改名 `list_for_user`。教训：不要用 `list`/`dict`/`type`/`id` 这类内置名当类里的方法名，类体内它们会遮蔽内置名。
2. 把异常类从 `runs.py` 拆到 `errors.py` 后，旧测试仍从 `runs` 导入。因为 `runs.py` 自己也导入了这些名字所以没报错，但依赖了"碰巧能导入"，所以把测试改成从 `errors` 导入。

### 验证
- 新增 6 个 API 测试（共 14 个通过）：重复用户名 409；缺失/非法/不存在的用户头 401；发消息 202 且历史可查；活跃 run 期间再发消息 409 且不留孤儿消息；两个用户互相看不到对方数据（对话列表、消息、发消息、run 都是 404）；空内容和非法 uuid 返回 422。
- 在 Compose 里用 curl 端到端走了一遍：建用户 → 建对话 → 发消息 202 → 再发 409 → 历史只有一条 → 不带头 401，api 日志无错误。

### 面试可讲点
202 的语义；为什么越权返回 404；领域异常到 HTTP 状态码的映射放在哪一层；鉴权占位怎么保证以后可替换。见 `interview-prep.md` 的"分层架构"与"Agent 运行链路"。

## 2026-10 · 阶段 1（三）：派发与执行（进程内单机版）

### 目标
让 `queued` 的 run 真正被执行：派发 → 抢占 → 执行 → 回写，并处理好超时、异常、崩溃、关停。用回声 Agent 打通，暂不接 LLM。

### 设计思路
- **数据库是事实来源，队列只是加速**。run 一旦以 `queued` 落库，就“必须被执行”。内存队列丢了不要紧：周期扫描 `status=queued` 补投。这样“提交成功 ⇒ 一定会被执行”这个承诺不依赖任何内存状态。
- **正确性靠 `claim`，不靠队列**。入队时可能重复（提交时入队 + 扫描补投），所以执行前一律先 `claim`（`UPDATE … WHERE status='queued'`），抢不到就跳过。`_pending` 集合只是减少重复排队的优化。我专门做了变异检查：去掉它测试依然全过，证实真正的保证来自 `claim`。
- **每个失败路径都要把 run 收尾到终态**，否则对话会被“同一对话最多一个活跃 run”的唯一索引永久锁死。覆盖了四种情况：Agent 抛异常 → failed 并记录错误；超时 → failed；优雅关停 → failed（用 `shield` 保证收尾写库不被再次取消打断）；进程被强杀 → 下次启动时恢复为 failed。
- **启动恢复只在单进程下安全**。把所有 `running` 置为 failed，多实例会互相误杀。这条假设写进了 decisions/0005 和代码注释，它就是阶段 4 需要 lease + heartbeat 的最直接理由。
- **Agent 用“函数”契约**：`RunContext -> str`。Agent 不依赖数据库，上下文由服务层构造，历史截止到本次输入消息（按 `seq`），重放结果稳定。
- **投递放在路由里 `submit` 成功之后**，而不是服务层事务内：投递是副作用，不能发生在事务提交之前，否则消费者可能读不到刚写的数据。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| `asyncio.Queue` + N 个消费协程 | 单进程内最简单的“生产者-消费者”，与 FastAPI 同一个事件循环，无需外部依赖 | Redis/ARQ：现在没有多 worker 的需求，过早引入会同时面对业务与分布式两类 bug；代价是进程崩溃丢内存队列（靠扫描补投兜底） |
| 周期扫描补投（默认 5s） | 把“队列丢任务”变成“最多延迟一个扫描周期”，实现成本极低 | 数据库通知（LISTEN/NOTIFY）延迟更低但复杂；5s 对聊天场景可接受，间隔可配置 |
| `asyncio.wait_for` 做超时 | 标准库，超时后会取消 Agent 协程，资源能释放 | 线程/进程级超时：对纯异步协程没必要 |
| 回声 Agent 打通链路 | 把“链路 bug”和“LLM/提示词 bug”分开排查；测试快速、确定、免费 | 直接接 LLM：慢、非确定、要密钥，出问题时分不清是谁的错 |
| 配置走环境变量并给默认值 | 沿用已有约定；并发、超时、扫描间隔不用改代码即可调 | 配置中心：对当前规模过度 |
| 集成测试 + **变异检查** | 测试一次全过时，不能默认它有效；故意破坏实现看测试会不会失败，才能证明它真的在保护行为 | 只看覆盖率：覆盖到不等于断言有效 |

### 备选与取舍
- 被打断的 run：重试还是标失败？选**标失败**，由用户重发。自动重试需要幂等保证（比如工具已产生副作用），现在没有 checkpoint，不能保证；接入 LangGraph checkpoint 后再改成断点恢复。
- 启动恢复：全部置 failed vs 重新入队？重新入队可能让一个“毒任务”（每次都让进程崩溃的 run）无限重启进程，所以选 failed。

### 遇到的问题
1. **接线脚本找不到文件**：我先 `cd ../../..` 想回到 `backend`，实际退到了仓库根，后半段修改 `server/*.py` 的脚本报 `FileNotFoundError`，而前半段（仓储、服务、派发器）已写成功，处于“改了一半”的状态。靠输出里的报错发现，先 `git status` 确认哪些已改、哪些没改，再从正确目录重跑后半段。教训：多步脚本里不要靠相对 `cd` 切换目录，写绝对路径或每步显式 `cd`；出错后先查清状态再补，不要整体重来以免重复修改。
2. **测试一次全过，反而要警惕**。8 个新测试第一次运行全部通过。为了确认它们真的有效，对实现做了 7 种变异：去掉启动恢复 / 去掉补投 / 关停时不收尾 / 并发翻倍 / 去掉超时，对应测试都按预期失败；去掉 `_pending` 去重，测试仍然通过。最后这一条不是测试缺陷，而是证明了“去重只是优化，claim 才是保证”。
3. **变异检查结论的边界**：我还试了“连 claim 判断一起去掉”，结果 7 个测试失败，但原因是 run 永远停在 `queued`（我把状态转换一并破坏了），**不能**当成“证明会重复执行”的证据，所以没有把它写成结论。
5. **文档脚本崩溃后仍提交了半成品（和第 1 点同类的失误，我再犯了一次）**。统计完成度的脚本里，正则在 `r'...'` 原始字符串里又多写了一层反斜杠，匹配 0 项，`d*100//t` 除零报错。脚本与 `git add && git commit` 是分开的两条命令，前者失败后者照样执行，于是提交里 decisions/dev-log/interview-prep 是新的，而完成度表、HANDOFF、`.env.template`、qa-log 还是旧的。发现方式：脚本输出里的 Traceback。处理：逐项检查每个文件的“标志性内容”是否已写入，只补缺的部分，再追加一个修复提交（提交未推送，本可 amend，但保留修复提交更能如实反映过程）。改进：统计脚本加 `assert t > 0`；需要“成功才提交”时把脚本和提交写进同一条 `&&` 链，或先看输出再提交。
4. **一个我暂时无法在测试里复现的点**：强杀进程（kill -9）时的恢复，只能靠下次启动的 `fail_orphaned_running`；测试里用“手工 claim 后再启动派发器”模拟了这个状态，而不是真的杀进程。

### 验证
- 22 个测试通过（原 14 个 + 派发器 8 个）。
- 容器内端到端：发消息 202 → run 变 `succeeded` → 历史里出现 `echo: …`；`docker compose restart api` 后历史仍在，继续发消息 202 且再次得到回复；api 日志无报错。

### 面试可讲点
“先落库再投递”的完整闭环；为什么队列不是事实来源；为什么正确性靠原子 claim；每个失败路径为什么必须收尾（否则对话被唯一索引锁死）；单进程假设的边界以及 lease 为什么必要；变异检查如何验证测试有效。见 `interview-prep.md` 的“Agent 运行链路”与 `decisions/0005`。

## 2026-10 · 阶段 1（四）前置：对话历史的事实来源（调研与 decision 草稿）

### 目标
在写 LangGraph chatbot 之前，先决定“历史以 `messages` 表为准还是以 checkpoint 为准”，以及 checkpoint 的 `thread_id` 绑谁。这是 PROGRESS 里标记过的风险（双份事实来源），不先定，后面接入会返工。

### 设计思路
- 不凭印象下结论，用最小图（一个节点只报告“收到了几条消息”）在真实 Postgres 上做对照实验，把三种方案的行为差异跑出来。
- 实验覆盖：只传新消息 / 失败后重发 / 全量历史叠加 checkpoint / 带稳定 id / 每个 run 一个 thread / 失败后按 thread 续跑 / 清理能力。
- 结论写成 `decisions/0006`，状态是草稿，把需要用户拍板的点单列为“开放问题”。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| 方案 A：`messages` 表为准，checkpoint 的 thread 按 run | 单一事实来源；阶段 4 的中断/崩溃恢复本质是“同一 run 续跑”，按 run 划分 checkpoint 正好对应；摘要/过滤等“改写历史”只动一处 | B（checkpoint 为准）：历史藏在二进制状态里，我们的表要么变成副本、要么对不上；C（混合）：实验证明会重复，加稳定 id 也只修好一半 |
| 用临时数据库做实验、结束后删除 | 不污染开发库和测试库 | 在代码仓库里留实验脚本：一次性结论，留着只会过时 |

### 遇到的问题
1. **我自己之前的论断被实验推翻了一半**。上一条消息里我说“以 messages 表为准，失败的 run 不会污染历史”，并用实验 5 支撑——但实验 5 里我是在代码里人为把失败那条消息排除在外，等于预设了结论。真实系统里，失败 run 的用户消息在提交时就已落库，A 和 B 的下一轮都会看到它。发现方式：设计实验 2 时对照“真实系统的数据流”逐步推演，发现实验 5 的构造和真实流程不一致。处理：在 decision 里明确更正，并把 A 的真实优势改写为“策略握在我们手里、可见、可调”。教训：实验要复刻真实数据流，而不是替方案挑一个有利的输入。
2. **实验输出里 `count(*)` 的结果被行工厂变成了字典**，且没有给聚合列起别名，导致“线程数”那一列丢失，数字不可靠。所以 decision 里**不引用 checkpoint 表的具体行数**，只写“线性增长，未测量”。教训：拿不准的数字宁可不写。

### 验证
7 条实验结论逐条写入 decisions/0006；临时数据库 `scratch_lg` 已删除。尚未验证的明确标注：任何真实 LLM 供应商、checkpoint 的实际存储增长速度。

### 面试可讲点
“业务表和框架 checkpoint 两份数据，谁是事实来源”；用对照实验而不是直觉做架构决定；混合方案为什么是陷阱；按 run 划分 checkpoint 如何自然支撑中断与崩溃恢复；自己发现并更正了论断中的错误。

## 2026-10 · 阶段 1（四）：接入 LangGraph chatbot（决策 0006 落地）

### 目标
把回声 Agent 换成 LangGraph 聊天图：历史以 `messages` 表为准，checkpoint 的 `thread_id` 用 `run_id`，模型通过工厂可替换；真实 LLM 暂不接入，用确定性的假模型跑通。

### 设计思路
- **Agent 是“函数”契约，LangGraph 是它的内部实现**。`BaseAgent.run(RunContext) -> str` 可直接作为派发器的 handler，派发器完全不知道 LangGraph 的存在。以后换 Agent、加多 Agent，派发层不动。
- **两个世界的边界集中在 `messages.py`**：数据库里的 `role + content` ↔ LangChain 消息类型。映射只写一处，也只测一处。数据库里出现 `tool` 角色直接报错，而不是静默丢弃——决策 0006 规定工具中间结果不入 `messages` 表，出现就说明数据异常。
- **系统提示词只在调用模型时拼接，不写进 state**。这样 checkpoint 里不重复保存它，改提示词也不用迁移任何历史状态。
- **checkpoint 表由 LangGraph 自己建（`setup()`），不放进我们的 Alembic**，在 `migrate` 一次性服务里于 Alembic 之后执行。原因：那套表的结构和升级由 LangGraph 维护，我们再抄一份迁移，升级时两边会打架；`setup()` 本身幂等。
- **api 进程只连接、不建表**：和“迁移不在 api 启动时跑”的既有原则一致。
- **模型工厂默认 `fake`**：没有密钥也能把整条链路跑通和测试；真实供应商只改环境变量。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| `AsyncPostgresSaver` + `psycopg_pool.AsyncConnectionPool` | 整个服务是异步的，同步 saver 会阻塞事件循环；连接池让多个 run 并发读写 checkpoint 不互相等 | 同步 `PostgresSaver`：简单但会卡住事件循环；`MemorySaver`：进程重启即丢，无法支撑崩溃恢复 |
| 模型工厂：`fake` / `openai` / `anthropic` 三种 | `openai` 通过 `base_url` 覆盖 DeepSeek、通义、智谱等所有 OpenAI 兼容接口，一个分支顶很多家；`anthropic` 单独保留，因为它的 content 可能是内容块列表（已在 `message_text` 处理） | 每家供应商一个分支：重复；只支持一家：绑死 |
| 供应商 SDK 延迟导入 | 用 fake 时不加载 openai/anthropic SDK，启动更快，也不要求配置密钥 | 全局导入：启动慢，且缺密钥时也要构造客户端 |
| 假模型自写 `FakeEchoChatModel`（回复 `echo: …`） | 确定、免费、秒级；出问题时能确定不是 LLM 的锅 | 直接用 LangChain 自带的 `FakeListChatModel`：回复是预设列表，无法按输入回声，不能验证“历史有没有喂对” |
| 测试用 `RecordingModel` 记录模型收到的消息 | 能直接断言“模型收到了什么”，这才是验证决策 0006 的关键 | 只断言最终回复文本：看不出历史是不是全量、有没有叠加 |
| 本阶段先不做流式 | 流式要改 Agent 契约（返回异步迭代器）并配套事件通道，属于 1.5，一次做完比现在半做更清晰 | 现在 `run()` 返回完整文本 |

### 备选与取舍
- 历史转换放在 Agent 里还是服务层？放在 Agent 里：`RunContext.history` 保持与框架无关（`ChatMessage`），换框架时服务层不用动。
- 系统提示词是否可配置？先放常量，等有多个 Agent、多租户配置时再抽到配置里，避免现在为不存在的需求设计。

### 遇到的问题
1. **`psycopg_pool` 的 `min_size` 默认是 4**。我写的连接池 `max_size=1`（给 migrate 建表用）和 `max_size=3`（测试用）直接报 `max_size must be greater or equal than min_size`。不只是测试问题：同样的代码生产里 `setup_checkpoint_tables` 也会崩，是测试把它提前暴露出来的。处理：显式 `min_size=1`。教训：第三方库的默认值要读，尤其是“我只设了一个参数”的时候。
2. **我在 1.3 留下的潜伏 bug**：`.env.template` 里写了 `WORKER_CONCURRENCY` 等可选变量，但 `docker-compose.yml` 没把它们传进容器——compose 只传 `environment:` 里列出的变量，`.env` 里多写的只用于 compose 文件内的 `${}` 替换。所以用户改了 `.env` 也不会生效，而当时我没发现，因为默认值恰好和代码默认值一致。发现方式：这一步要加 LLM 变量时，核对“`.env` → 容器 → 代码”整条路径，发现链路少了一环。处理：在 compose 里显式列出并带默认值，并在容器内 `os.environ` 实际读取验证。教训：配置要验证到“进程里读到的值”，不能只看配置文件写了没有。
3. **变异检查**：测试全过后，对实现做 4 种破坏（thread_id 改回 conversation_id / 只传最后一条消息 / 系统提示词写进 state / 去掉 checkpointer），分别有 2~4 个测试失败，说明测试确实在保护决策 0006 的各条规则。
4. **没有验证的事**：真实供应商的调用（没有密钥）。只验证了工厂的配置分支，以及 `ChatOpenAI` / `ChatAnthropic` 能用我们传的参数名构造出来（不联网）。流式、工具调用、各家对 `content` 格式的差异都还没碰到。

### 验证
- 37 个测试通过（原 22 + 新增 15）：消息映射、工厂分支、全量历史+系统提示词顺序、checkpoint 的 thread 是 run_id 且不含系统提示词、同一对话的多个 run 不叠加、失败后同一 thread `invoke(None)` 续跑、经派发器的两轮端到端（第二轮模型看到的是表里的历史）。
- 容器内：`migrate` 建出 checkpoint 表；两轮对话成功；checkpoint 里只有 run_id 作为 thread（没有以 conversation_id 为线程的记录）；容器内 `os.environ` 读到 `LLM_PROVIDER=fake` 等配置。

### 面试可讲点
Agent 与派发层如何解耦；业务库与框架状态的边界集中在哪、怎么测；为什么 checkpoint 表不进自己的迁移；为什么按 run 划分 checkpoint 并实测过续跑；配置要验证到进程内读到的值；第三方库默认值引发的线上才会炸的 bug 被测试提前抓出。

## 2026-10 · 阶段 1（五）：新增 Google (Gemini) provider 与真实调用冒烟脚本

### 目标
用户计划用 Gemini 的免费 key。新增原生 `google` provider，并提供一条命令即可验证“真实调用是否通”的脚本。**真实调用由用户配好密钥后验证，我这边没有 key。**

### 设计思路
- **原生 provider，而不是复用 OpenAI 兼容端点**：Gemini 提供 OpenAI 兼容端点，理论上现有 `openai` 分支改 `base_url` 就能用，零代码。但后面 1.5 要做流式、阶段 4 要做工具调用，这两件事在原生集成里支持更完整、行为更可预期；兼容层通常是“能用但有差异”。多一个分支的成本只有几行。
- **显式传 key，不依赖库自己读环境变量**：`langchain-google-genai` 会回退读 `GOOGLE_API_KEY` 等环境变量，如果不显式传，容器里一个无关的环境变量就可能悄悄改变行为。我们的配置来源只能是 `LLM_*`，缺 key 时在工厂处直接报清晰的配置错误。
- **冒烟脚本独立于数据库和 HTTP**：真实调用一旦失败，原因可能是 key / 模型名 / 网络 / 额度，也可能是我们的服务代码。脚本把后者排除掉，只测“模型这一层”。它同时测非流式和流式，并报告流式的**分块数**——因为 1.5 的前提是 token 真的逐段到达，分块数为 1 就说明这条路径其实不是流式，要提前知道。
- **失败时输出异常类型和信息，且不打印 key**：脚本只显示“已设置/未设置”。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| `langchain-google-genai`（`ChatGoogleGenerativeAI`） | 原生集成，流式/工具调用/思考内容的支持最完整；与现有 LangChain `BaseChatModel` 接口一致，业务代码零改动 | OpenAI 兼容端点：零代码但行为有差异、较新特性可能缺失；直接用 `google-genai` SDK：要自己适配成 LangChain 接口，重复造轮子 |
| 冒烟脚本放 `backend/scripts/`，随镜像一起打包 | 用户在容器里一条命令就能跑，环境（依赖、`.env`）与服务一致，不依赖本机 Python | 放仓库根 `scripts/`：不在镜像里，容器内跑不了 |
| 模型名不在代码里写死，只通过 `LLM_MODEL` | 免费档模型和限额变化很快，写死会过期 | 在代码里枚举“支持的模型”：一旦 Google 改名就要发版 |

### 遇到的问题
1. **没有可用的真实 key，如何验证“确实打到了 Gemini”？** 用一个故意错误的 key 调用：Google 返回 `API_KEY_INVALID`（400），说明网络通、请求确实到达了 `generativelanguage.googleapis.com`、我们的脚本能把错误清晰呈现。这**不等于**真实调用成功，只验证了路径和错误处理。
2. **macOS 没有 `timeout` 命令**（`command not found`，退出码 127），导致一次自检没跑成，且容易误以为是脚本问题。改用工具自带的超时。属于“Linux 惯用命令在 macOS 上不存在”的同类小坑，与此前 `sed -i` 一样。
3. **库的构造不校验模型名**：用任意模型名也能无网络地构造成功，所以构造成功只能说明参数名对，不能说明模型存在。模型名是否正确只有真实调用才知道，这也是写冒烟脚本的原因之一。

### 验证
- 40 个测试通过（新增 3 个：google 缺 key / 缺 model 的配置错误、google 客户端构造、思考类内容块被跳过）。
- 脚本自检：fake 通过；google 缺 key 给出配置错误（退出码 2）；google 假 key 得到 Google 返回的 `API_KEY_INVALID`（退出码 1）；容器内 fake 通过且能导入 google provider。
- **未验证**：任何真实成功的 Gemini 调用、`message_text` 对 Gemini 真实返回的 content 形状（“思考块被跳过”的测试基于我的假设，已在测试注释里标明）。

### 面试可讲点
为什么原生集成优于兼容层；为什么显式传 key；如何在没有凭据时验证调用路径（错误 key → 看错误是否来自目标服务）；冒烟脚本把“模型层”和“服务层”的故障隔离开。

### 目标
用户配好密钥后，验证 `google` provider 的真实调用，并回答两个悬而未决的问题：content 的真实形状、流式是否真的逐段到达。

### 验证结果（`gemini-3.8-flash`，免费档）
| 项目 | 结果 |
|---|---|
| 模型名 | 有效（来自定价页的名字，此前无法独立核实，现已证实可用） |

### 值得注意的发现
- **首块延迟高（约 7.6s）**：回复开始前模型有较长的等待，推测是模型在“思考”，但我没有查证具体原因。对 1.5 的影响：前端要有“思考中/等待首字”的状态，不能把 7 秒无输出当成卡死；`RUN_TIMEOUT_SECONDS=300` 余量足够。
- **免费档的限额没有触发**：只调了十几次，未遇到 429；连续高频使用是否触顶仍未知。

### 遇到的问题
1. **我写的冒烟脚本，流式检查本身有缺陷**。第一次用户给的输出里：回复只有一个字，流式“首块延迟 2.85s ≈ 总耗时 2.85s”，分块数是 3。我原先的判据是“分块数 > 1 就算流式”，但这个结果其实**什么也证明不了**：一个字的回复在模型内部瞬间就生成完了，所有分块几乎同时到达，3 个分块里可能还有空文本块或带用量信息的末块。发现方式：对着输出做数字推演，注意到首块延迟和总耗时几乎相等。处理：脚本新增“长回答”测试，判据改为“分块数足够多且首末块之间有时间间隔”，然后重跑，才得到上表的结论。教训：判据要能区分“真流式”和“碰巧有多个分块”；一个只在好情况下才通过的检查，通过了也没有信息量。
2. 脚本在镜像里：改了脚本必须 `docker compose build api` 才会生效（脚本随镜像打包）。

### 面试可讲点
真实调用与假模型的差异（content 是块列表）；如何设计能区分“真流式”的检查；首块延迟（TTFT）对前端交互的影响；用“第二轮能答出第一轮的信息”验证历史确实喂给了模型。

## 2026-10 · 阶段 1（六）前置：流式输出的设计调研（decision 0007 草稿）

### 目标
在动手写 SSE 之前，先决定事件通道、Agent 契约、断线续传、事件与数据库的主从关系。和 0006 一样：先用实验把依赖事实的地方验证清楚，再写草稿，把需要用户拍板的点单列出。

### 设计思路
- **先问“这个机制要满足什么”再选技术**：需求是（1）逐字显示；（2）客户端断线能续上；（3）晚加入的客户端能看到已生成的部分；（4）阶段 4 worker 独立后依然成立；（5）出故障不能让客户端卡死。Redis Streams 的游标/回放/阻塞读恰好对应前四条，第五条靠“数据库为准、事件为视图”解决。
- **事件是视图，数据库才是事实**：终态事件在数据库提交之后才发；SSE 在每次阻塞超时查一次数据库，把“事件丢了”降级成“实时性变差”而不是“客户端永远等”。特别是已知的一个洞——启动恢复把 `running` 置为 `failed` 时不会发事件，必须靠这个兜底。
- **Agent 契约尽量不动**：把 `emit` 放进 `RunContext`，`run()` 仍返回完整文本，现有 Agent、测试、派发器主流程都不用改。

### 实验与结论
| 实验 | 结果 |
|---|---|
| 真实 Gemini + `graph.astream(stream_mode="messages")`，节点内仍用 `ainvoke` | 9 个 `AIMessageChunk`，分散在 1.08s，首块 6.79s；不用改节点代码 |
| 同样的流式调用换假模型（只有 `_generate`） | 只有 1 个整块；测试要验证逐段需要给假模型补流式 |
| Redis Streams：ID 单调、从某 ID 之后读、阻塞读被写入唤醒、先连后写、`EXPIRE` | 全部符合预期（唤醒延迟 0.31s） |
| 5 个并发阻塞读占用的连接数 | 5 个，每个客户端一个连接 |

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| Redis Streams 作事件通道 | 跨进程、游标与回放现成、阻塞读即推送、Redis 已在栈里 | 进程内队列：阶段 4 拆 worker 后失效，重启丢缓冲；Postgres 逐 token 写入：几百行写入/次，对用完即弃的事件不划算 |
| `emit` 放进 `RunContext` | `run()` 签名不变，改动面最小 | 异步生成器 `yield` 事件：更纯，但要改所有 Agent/派发器/测试，只换来风格 |
| 前端用 fetch 流式读取而非 `EventSource` | `EventSource` 不能带自定义头，而鉴权占位用的是 `X-User-Id` 头；阶段 5 的 token 同样需要头 | 把用户标识放 URL 查询串：会进访问日志和浏览器历史，不采用 |
| 15 秒阻塞超时兼作心跳与数据库巡检 | 一个机制同时解决“代理断连”和“事件丢失” | 单独的心跳定时器 + 单独的巡检任务：更多移动部件 |

### 遇到的问题
1. **我对库默认值的印象是错的**。我原本打算在 decision 里写“redis-py 连接池默认不限连接数”，写之前顺手查了一下，实际默认 `max_connections=100`。这直接改变了设计：每个 SSE 客户端占一个阻塞连接，100 就是单进程并发流的天花板，所以决定里明确要显式配置并写明这个扩展上限。教训：凡是要写进决策文档的“默认行为”，先验证再写（和 `psycopg_pool` 的 `min_size` 默认值是同一类坑）。
2. **有一个现象我没能解释**：真实模型这次给了 9 个事件，但带 `text` 内容块的只有 8 个。推测是末尾有一个只携带用量信息、没有文本的块，但我没有查证，所以文档里没有把它当结论。实现时处理方式是“取不到文本的块直接忽略”，不依赖这个推测。
3. **实验使用了用户配置在 `.env` 里的 key**，通过 compose 容器运行，脚本不读取也不打印密钥。免费档额度被消耗了几次调用，量很小。

### 验证
全部为设计阶段的一次性实验，结论逐条写入 decisions/0007。尚未实现任何代码。

### 面试可讲点
流式输出里“事件通道”与“事实来源”的分工；为什么游标要用单调 ID、续传为什么是 `Last-Event-ID`；`EventSource` 为什么与头部鉴权冲突；把“事件丢失”降级成“实时性下降”的兜底设计；每个阻塞读占一个连接带来的扩展上限。

## 2026-10 · 阶段 1（六）：流式输出（SSE + Redis Streams，决策 0007 落地）

### 目标
让浏览器逐字看到回复；断线能续上；晚加入的客户端能看到已生成的部分；事件丢了客户端也不会卡死。用户确认了 0007 的方案 B 和“失败时半截输出不入库”。

### 设计思路
- **三个世界各管一件事**：Postgres 是事实来源；内存队列只是加速；Redis Streams 只是给浏览器看的视图。任何一处设计都先问“这里以谁为准”。
- **Agent 契约不变**：`RunContext` 新增 `events`（默认空实现），`run(ctx) -> str` 照旧返回完整文本。流式只是“边执行边 emit”。回声 Agent、旧测试、派发器主流程都不用改。
- **终态事件“先提交、再发布”**：客户端收到 `run.completed` 时消息一定已经落库。
- **SSE 的结束由数据库决定**：空闲时查库，run 已终态就合成终态事件（带 `synthesized: true`、没有 id，因为它不在流里，不能作为续传游标）。把“事件丢失”降级为“实时性下降”。
- **连接时 run 已结束就不阻塞**：直接回放剩余事件；流已过期则立即合成，不让客户端白等一个轮询周期。
- **最终回复取自图的最终状态**（`stream_mode=["messages","values"]`），而不是拼接 token：状态是结果，token 是过程视图。
- **发布用的 Redis 客户端与 SSE 阻塞读的客户端分开**：每个 SSE 客户端占一个阻塞连接，共用连接池会让订阅者挤占执行方的发布。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| Redis Streams（`XADD MAXLEN~` / `XREAD BLOCK` / `EXPIRE`） | 单调 ID 即游标、从某 ID 之后读即续传、阻塞读即推送；跨进程，阶段 4 拆 worker 不用改；Redis 已在栈里 | 进程内队列：拆 worker 后失效、重启丢缓冲；逐 token 写 Postgres：写放大；Redis Pub/Sub：不保存历史，无法续传和回放 |
| FastAPI 内置 `fastapi.sse.EventSourceResponse` + `ServerSentEvent` | 框架负责 SSE 编码（多行 data 拆分、字段校验）、空闲 15 秒自动 `: ping`、自动加防缓冲响应头；底层用独立任务驱动生成器，客户端断开时取消它 | 手写 `StreamingResponse`：要自己处理编码、心跳和断开，容易漏；第三方 `sse-starlette`：多一个依赖，而框架已经内置 |
| 归属校验做成依赖 `owned_run` | 依赖在响应开始前执行，越权直接 404；放在生成器里会先发 200 响应头（变异检查验证过） | 在路由函数体里校验：对 yield 型路由，异常发生时响应已开始 |
| `emit` 放进 `RunContext` | `run()` 签名不变，改动面最小 | 异步生成器 `yield` 事件：更纯，但要改所有 Agent、派发器和测试 |
| `make_reader_client`：阻塞读专用客户端，`socket_timeout = 阻塞时长 + 5` | redis-py 8 默认 `socket_timeout=5s`，等于阻塞时长时每次空闲都会在客户端超时（真实 bug，见问题 #31） | 不设置：真实环境下 SSE 退化成查库模式；设为 `None`（无限）：网络真的挂住时读会永远不返回 |
| 测试 HTTP 层起真实 uvicorn（端口 0） | httpx `ASGITransport` 会缓冲整个响应（实测三条间隔 0.5s 的事件在 1.5s 同时到达），测不了逐条到达和中途断开 | 只测服务层：测不到线上格式、响应头、断开行为 |
| 用 Redis `CLIENT LIST` 的 `flags=b` 观察阻塞连接 | 从 Redis 服务端看“是否还有为已断开客户端阻塞的连接”，比读 redis-py 连接池的私有属性更真实 | 读连接池内部计数：依赖私有实现，且连接回到池里不等于服务端已释放 |
| 假模型实现 `_astream`（复用 `_generate` 再切块） | 测试能验证“逐段”；子类只需覆盖 `_generate`（如记录调用、模拟失败）流式与非流式行为就一致 | 单独写一套流式假模型：两套逻辑可能不一致 |

### 遇到的问题
1. **本地测试用的虚拟环境坏了**：`ModuleNotFoundError: No module named 'fastapi'`，但包明明装过。排查：`sys.prefix` 指向 `/opt/anaconda3` 而不是虚拟环境目录，`pyvenv.cfg` 不见了——系统清理临时目录时删掉了它，没有这个文件解释器就不认为自己在虚拟环境里。处理：重建。教训：临时目录里的环境随时可能被部分清理，报“包找不到”时先看 `sys.prefix`。
2. **验证了一个关键假设：`ASGITransport` 会缓冲整个响应**。原有 API 测试都用它，如果直接沿用写 SSE 测试，会测出“全部一起到达”的假结果。所以 HTTP 层改为起真实 uvicorn。
3. **我在假模型注释里写错了一句**：起初写“在 `_astream` 里再调 `on_llm_new_token` 会让 token 重复”。为了确认，又读了 `astream()` 和 `ainvoke()` 两条路径的源码：基类确实会自己调用这个回调，但它调用 `_astream` 时**根本不传 `run_manager`**，所以在 `_astream` 里拿到的是 `None`，“重复”无从谈起。已改成准确说法。教训：写进注释的因果关系也要验证。
4. **解释了 0007 草稿里留下的疑问**（真实模型 9 个事件只有 8 个带文本）：读 `langchain_core` 源码发现，流式结束时基类会补一个空的末块（`chunk_position="last"`，内容为空列表）。实现中跳过空文本即可。
5. **“客户端断开”测试第一版可能是假通过**：假模型每 0.05s 出一块，读取方大部分时间并不处于阻塞，且整段回复约 5 秒、等待循环也是 5 秒——就算服务端不取消读取，测试也可能通过。重写：用一个发完 `run.started` 就长时间不出数据的 handler，让读取方持续阻塞；断开前先断言“能观察到 1 个阻塞连接”（证明测量手段有效），断开后连续 10 次采样都必须是 0。
6. **我写的测试不稳定（3 次失败 1 次）**：失败在“断开前能观察到 1 个阻塞连接”这一步。打印 Redis 客户端列表后发现：循环里观察到了 1 并跳出，但紧接着的 `assert` **又查了一次**，恰好落在读取方“超时→查库→重新阻塞”的空隙里得到 0。这是“检查之后再断言”的竞态，出在测试代码本身。改为断言循环中实际观察到的值后，连续 15 次 + 全量 5 次无失败。
7. **变异检查有一项存活：“读取时吞掉取消”**。推测原因是 anyio 的取消是电平触发的；写了小实验验证：anyio 下吞掉一次取消，下一个 `await` 立刻又被取消；纯 asyncio 下不会自动重发。结论：在 FastAPI 的 SSE 里这个错误会被框架兜住，但如果以后在纯 asyncio 任务里复用读取逻辑就会泄漏连接，所以代码保留 `raise` 并写明原因。
8. **我把整个 `.env` 导出到了测试进程**（`set -a; . .env`），其中包括用户的 `LLM_API_KEY`。测试不需要它，也没有打印，但不应该这样做。改为脚本只导出数据库和 Redis 的连接串，并确认测试进程里没有 `LLM_API_KEY`。
9. **真实环境的 bug：SSE 退化成“一次性输出”（本步最重要的问题）**。所有测试通过后，用真实 Gemini 端到端跑：token 全部在第 170 秒同时到达，api 日志每 5 秒一条 `Timeout reading from redis:6379`。
   - 我起初猜是“计时用的 Python 读标准输入有缓冲”，并标注为推测；日志直接否定了它。
   - 根因：redis-py 8 的连接默认 `socket_timeout=5` 秒（`from_url` 不传时由连接类给默认值，在连接参数里看到的是 `None`，在容器里查实际连接对象才看到 5），而阻塞时长也是 5 秒。Gemini 首字要等 7 秒以上，每次阻塞读都在客户端先超时，被我的代码当成“Redis 不可用”而退化成查库，直到 run 结束才一次性读出所有事件。
   - 测试为什么没发现：测试里的轮询间隔只有 0.2~0.3 秒，永远碰不到 5 秒的套接字超时——测试参数绕开了生产参数的量级。
   - 修复：`make_reader_client` 设置 `socket_timeout = 阻塞时长 + 5`；并把 `redis.exceptions.TimeoutError` 按空闲处理，与连接失败区分。
   - 修复后端到端：写入到收到延迟 4~6 毫秒，token 逐段到达。
10. **回归测试第一版分辨不出修复前后**：断言“收到 token 时 run 仍在执行”，变异（回到修复前行为）后依然通过。推演时间线发现：修复前睡 1 秒后恰好读到 1.2 秒发出的 token。改为测量延迟：让 token 在 0.5 秒发出，正好落在修复前的睡眠窗口里。修复前延迟 0.82 秒（与推演的 0.8 秒吻合），修复后接近 0，断言小于 0.4 秒。
11. **一次原因不明的失败**：某次变异检查还原后，全量测试出现 1 个失败，没抓到是哪个。我怀疑是“变异与原文件字节数相同（`RedisTimeoutError` 与 `ZeroDivisionError` 都是 17 个字符）且在同一秒内写入，Python 沿用了变异版的 `.pyc`”，但复现实验显示还原后加载的就是修复版代码，**假设被否定**。之后连续 23 次全量通过，未能复现，原因不明。记录在案，若再出现要抓完整输出。
12. **Gemini 免费档延迟剧烈波动**（外部问题）：几天前首块 7 秒，今天直接调用模型非流式 83~96 秒、流式首块 34~173 秒。冒烟脚本直接调用也同样慢，所以与我们的链路无关。影响：`RUN_TIMEOUT_SECONDS=300` 离上限不远，需要在产品上考虑超时提示与重试。

### 验证
- 59 个测试通过（新增 19 个，见 decisions/0007 的验证一节）；修复不稳定测试后，SSE 文件连续 15 次、全量连续 28 次无失败（另有上面第 11 条的一次不明失败）。
- 变异检查 8 项（含回归测试的有效性），除“吞掉取消”外均被抓住，存活原因已用实验解释。
- 真实 Gemini + compose 端到端：推送延迟 4~6 毫秒；`: ping` 每 15 秒；落库内容与推送一致；日志无超时与兜底记录。

### 面试可讲点
三个世界（数据库/内存/Redis）的主从关系；“先提交再发布”；“数据库决定流何时结束”与合成终态；`Last-Event-ID` 续传；`EventSource` 与头部鉴权的冲突；两个 Redis 客户端的理由；**套接字超时 bug 的完整排查故事**；如何发现并修复自己写的不稳定测试与假回归测试；anyio 电平触发取消。学习导读见 `docs/guides/message-lifecycle.md`。

## 2026-10 · 阶段 1（七）：前端页面（Vue 3，决策 0008）

### 目标
达成阶段 1 里程碑：网页里和 LangGraph Agent 聊天，回复逐字出现，刷新页面后历史还在；生成中刷新也能接上。

### 设计思路
- **同源访问**：前端只请求 `/api/...`，开发时 Vite 代理、部署时 Nginx 转发，后端不配 CORS。
- **自己写 SSE 客户端**：原生 `EventSource` 带不了鉴权头；现成库停更多年且需求简单。拆成“解析器（纯逻辑）”和“连接与重连”两部分，前者可以对任意切块方式穷举测试。
- **界面状态以数据库为准**：发送后、完成后都重新拉消息列表；“正在生成的回复”是一个独立的临时状态，用纯函数状态机管理（waiting → streaming → completed/failed）。
- **刷新接得上**：后端新增 `active-run` 接口，前端加载对话时发现活跃 run 就重新订阅；事件流从头回放，已生成的部分立刻补齐。这是 0007 里“从 `0-0` 回放”设计在前端的直接收益。
- **等待首字要可见**：Gemini 首字实测 7~173 秒，界面显示“等待模型开始输出… N 秒”，计时从服务端 run 创建时间算起。
- **渲染安全**：Markdown 渲染禁用原始 HTML。
- **部署**：多阶段镜像，Nginx 提供静态文件并转发 `/api`，对 SSE 关闭缓冲。

### 遇到的问题
1. **我的版本筛选脚本按日期取“最新”，没区分大版本**：给 vite 选到了 6.4.4（6.x 的维护补丁），而主线已是 8.x。改为按大版本分别筛选。
2. **`vue-tsc` 报 TS7022（变量“在自己的初始化中被引用”）**：`streamRunEvents` 循环里，`lastEventId` 在循环中更新、又用于构造下一次请求，类型推断形成循环。给 `res`、`reader`、读取结果、消息数组显式标注类型解决。另一个报错是 `vite.config.ts` 的 `test` 字段需要 `/// <reference types="vitest/config" />`。
   - 顺带：我一度用 `cmd | tail; echo $?` 看类型检查结果，打印出的 `exit=0` 其实是 `tail` 的退出码。之后改为直接检查 `vue-tsc` 的退出码。
3. **SSE 解析器的真实缺陷（被测试抓到）**：为了处理“`\r\n` 被切在两块之间”，我原本让块末尾的 `\r` 先不处理、等下一块。但只用 `\r` 换行的流里，最后一个 `\r` 永远等不到下一块，最后一个事件会一直延迟。改为规范实现的通行做法：遇到 `\r` 立即结束这一行，并记住“刚才是 `\r`”，下一块若以 `\n` 开头就跳过。又补了一个边界：中间夹着空数据块时不能清掉这个标记。
4. **浏览器里第一次打开就 405**：容器里还是旧镜像，新加的 `GET /api/users` 不存在。改了后端代码要重建镜像（`up --build`）。
5. **刷新后“等待首字”计时归零**（浏览器实测发现）：恢复订阅时用的是浏览器当前时间作为起点。改为服务端的 `run.created_at`；又考虑到浏览器与服务端时钟可能有偏差，显示时不小于 0。
6. **失败时出现空的红色虚线气泡、提示语“已显示的内容没有保存”却什么都没显示**（Gemini 返回 503 时发现）：没有半截内容时不画气泡，提示语按有无内容区分。
7. **`.dockerignore` 里的 `node_modules` 只匹配根目录**，排除不了 `web/node_modules`，会把本机依赖送进构建上下文。改为 `**/node_modules`；修复后构建上下文 140KB。
8. **`docker compose up --force-recreate web` 把依赖的 api 也一起重建了**，而这条命令没带假模型的环境变量，api 回到了 `.env` 里的 Gemini，导致接下来的界面测试等了很久。我的操作失误；之后只重建需要的服务、不加 `--force-recreate`。
9. **Gemini 返回 `503 UNAVAILABLE: This model is currently experiencing high demand`**（两次，等待 37 秒、62 秒后）。这印证了上一步记录的高延迟来自 Google 侧过载；界面的“生成中断”路径因此得到了真实验证。
11. **我在更新面试文档时误删了内容**：用脚本把“前端：Vue3 + Vite”小节从标题到下一个标题整段替换，替换前没有看原文，结果删掉了原有的选型理由，还写了一句错误的指引（“选型理由见 0001”，而 0001 里并没有这段）。提交后用“替换前后的小节标题对比”和“查看原小节内容”核对时发现，已恢复原文并另行提交。教训：改文档也要先读后改，整段替换前确认被替换的内容。
10. **验证了 Nginx 配置注释里的一个说法**：临时去掉 `proxy_buffering off`，仅靠后端的 `X-Accel-Buffering: no`，SSE 仍逐段到达（25 个事件分散在 3.54 秒）。说法成立，配置随后恢复。

### 验证

## 2026-10 · 阶段 1 收尾（一）：取消、重试与错误码（决策 0009）

### 目标
补全 run 的生命周期：用户能中途停止；失败原因对用户可理解、对外不泄露内部信息，并且刷新后仍可见；失败或停止后能一键重试；等待过久时给出提示。

### 设计思路
- **原始报错给开发者，错误码给用户**：`error` 列和日志保留原始报错；API 和事件只给错误码，前端翻译成文案。
- **错误分类沿异常链找状态码**：先实测 Gemini 的异常结构（状态码在异常链下一层），再写分类器；找不到就归为 `internal`。
- **取消要先登记再动手**：执行 Agent 的任务有一个“已认领、未创建”的空档，取消请求可能落在这里。
- **用户取消与服务关停必须分开**：两者都是 `CancelledError`，用 `Task.cancelling()` 区分；否则关停时 `stop()` 会挂住。
- **重试复用输入消息**：历史里不会出现重复提问；只允许重试最后一条，避免回复顺序错乱。
- **迁移只能往后加**：历史数据的错误码用新的数据迁移 0003 回填，而不是改已执行的 0002。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| 新列 `error_code`（可空、无默认值、不加 CHECK） | 只改元数据、大表上也是瞬间完成；错误码会随供应商增加，由代码枚举约束更灵活 | 把错误码塞进 `error` 文本：无法稳定查询与统计；加 CHECK：每加一个错误码都要迁移 |
| 沿异常链查找 `status_code`/`code`/`status` | 各家 SDK 的异常类型不同，但都会在某一层带 HTTP 状态；LangChain 的包装异常本身不带 | 按异常类名匹配：每家都要写死类名，且包装层会变；按报错文字匹配：脆弱（只在无法拿到异常对象的历史数据回填里使用） |
| 每个 run 一个独立任务 + `_inflight` 登记表 | 取消只影响这个 run；worker 循环不受影响 | 直接取消 worker 任务：会把 worker 循环一起杀掉 |
| `Task.cancelling()`（Python 3.11+） | 标准库提供的“当前任务是否正在被取消”，能可靠区分外层关停与内层取消 | 自己维护“正在关停”的标志：要处理各种时序，容易出错 |
| 取消接口返回 200 / 202 / 409 | 202 明确表达“执行中的取消是异步的，结果看事件”；重复取消已取消的 run 返回 200（幂等） | 一律 200：客户端分不清“已取消”和“已请求取消” |
| 重试 = 同一输入消息新建 run | 不产生重复的用户消息；复用已有的“至多一个活跃 run”约束 | 前端重新发一遍消息：历史里出现两条相同的提问 |
| 数据迁移 0003（按文本、整词匹配、幂等） | 历史记录只剩文本；`\m…\M` 整词边界避免把“5003 ms”误判为 5xx | 修改 0002：已执行的迁移不会重跑，各环境不一致 |
| 迁移测试：独立新库上 `upgrade 0002 → 插数据 → upgrade head` | 迁移是会改生产数据的代码，必须像业务代码一样测 | 只在开发库上手工跑：无法复现，也测不到边界 |

### 遇到的问题
1. **我的补丁脚本又改了一半（与 #12、#14 同类）**：前端组件的多处替换里，第一处成功、第二处没匹配上就中断，留下“脚本部分已改、模板未改”的半成品，被类型检查抓到。根因是上一轮插入的一行没有缩进，这次按带缩进的原文匹配失败。处理：按实际内容重做替换。**改进：之后的文档脚本改成“全部在内存里替换成功，最后统一写回”**（本条记录所在的脚本就是这样写的）。
2. **测试断言太宽松**：“任务创建前收到取消”的测试一开始写成“没调用处理函数 **或** 没有输出消息”。实际上任务在开始运行前被取消，函数体一行都不会执行，应严格断言“从未调用”。
3. **漏掉的组合场景：用户取消与服务关停同时发生**。推演发现：若把所有 `CancelledError` 都当用户取消吞掉，worker 收到的那次关停取消就被消耗了，之后它回到 `queue.get()` 上永远等待，`stop()` 挂住。补测试后，变异检查确认去掉 `cancelling()` 判断时 `stop()` 确实挂住（被 3 秒超时抓到）。
4. **历史数据没有错误码，被显示成“内部错误”**：浏览器里看到前一天的 Gemini 503 失败被标成“服务内部错误”。原因是那条记录产生于加列之前。用数据迁移 0003 按原始报错文本回填，并为迁移写了独立新库上的测试；变异检查（去掉整词边界）证明“5003 ms”这条边界用例有效。
5. **开发库一直停在 0002**：没有重建镜像，新迁移文件不在镜像里（与 #38 同类：改了后端要 `--build`）。
6. **Ant Design 会在两个汉字的按钮文字中间插入空格**：按钮实际文字是“重 试”，用“重试”去查找元素会找不到。写端到端测试或自动化脚本时要注意。
7. **网络记录里事件流请求显示 `ERR_ABORTED`**：不是错误。前端收到终态事件后主动 `reader.cancel()` 关闭连接，浏览器就记为“已中止”。

### 验证
- 后端 83 个测试（新增 22 个）、前端 23 个（新增 6 个）、类型检查通过。
- 变异检查 6 项全部被抓住（详见 decisions/0009）。
- 浏览器实测：等待 21 秒出现“较慢”提示；点“停止”返回 202，显示“已停止生成（已显示的部分没有保存）”与“重试”；刷新后标注仍在、半截内容不在；点“重试”返回 202 并得到回复，历史中只有一条用户消息；开发库升级到 0003 后，旧的 Gemini 503 失败显示为“模型服务暂时不可用”。

### 面试可讲点
错误码与原始报错的分离（信息泄露）；沿异常链分类；用户取消与服务关停的区分及 `stop()` 挂住的风险；取消请求的空档；取消接口的 200/202/409 语义；重试为什么复用输入消息、为什么只能重试最后一条；“迁移只能往后加”与数据迁移的测试方法。

## 2026-10 · 阶段 1 收尾（二-1）：checkpoint 清理与存储测量（决策 0010）

### 目标
0006 留下的“checkpoint 清理与存储增长未测量”：先量清楚问题有多大，再实现清理。

### 设计思路
- **先测量后设计**：推测“每个 run 的 checkpoint 存了整段历史 → 总量随轮数平方增长”，用真实聊天图和 PostgreSQL 实测验证。
- **自己记账**：`agent_runs.checkpoint_purged_at` 记录已清理，不查询 LangGraph 管理的表。
- **部分索引 + EXPLAIN 测试**：保证“找待清理的 run”始终便宜，而且确认查询真的用上了索引。
- **先删后记账、单个失败不影响整批、积压连续处理**。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| 保留 24 小时后清理 | checkpoint 只对进行中的 run 有用；24 小时足够排查当天的问题 | 永久保留：平方增长；结束即删：失去排查手段 |
| `checkpoint_purged_at` 列 + 迁移 0004 | 不依赖 LangGraph 内部表结构；可以按我们自己的条件高效查询 | 直接 `JOIN checkpoints`：耦合第三方表结构，且那张表很大 |
| 部分索引 `WHERE finished_at IS NOT NULL AND checkpoint_purged_at IS NULL` | 只索引待处理的行，索引始终很小 | 普通索引：随表无限增长；不建索引：每轮全表扫描 |
| `adelete_thread`（LangGraph 提供） | 官方接口、幂等、删除三张表的对应行 | 自己写 SQL 删三张表：耦合内部结构 |
| 后台协程放在 api 进程里（与派发器同一 lifespan） | 当前是单进程部署，简单 | 独立定时任务容器：阶段 4 拆 worker 时可以一起迁过去 |

### 遇到的问题
1. **第一次测量严重低估了问题**：用 `"测" * 340` 作为消息，第 20 轮单个 run 只有 11KB，看起来增长很慢。怀疑是 PostgreSQL 对大字段的 TOAST 压缩把重复文字压没了；换成随机中文后第 20 轮是 66KB，20 轮累计 756KB（对话文字本身 41KB 的 18 倍）。教训：**测量数据的可压缩性要接近真实数据**，否则结论可能差一个数量级。
2. **删除后磁盘占用没变**：清理 16 个线程后三表仍占 384KB。这是 PostgreSQL 的正常行为——`DELETE` 只产生死行，autovacuum 回收后供复用；手动 `VACUUM` 后降到 216KB，要还给操作系统需 `VACUUM FULL`。记录在决策里，避免以后误以为清理没生效。
3. **容器日志里看不到清理器的 INFO 日志**：应用从没配置过日志，Python 默认只输出 WARNING 及以上，所有 INFO 都被丢弃（在容器里查到 `agentnexus` 日志的生效级别是 WARNING）。这一点在下一步“请求日志”里一并解决。

### 验证
- 测试 4 个、变异检查 4 项均被抓住；全量 87 个测试通过。
- 容器实测：保留期临时设为约 4 秒，16 个 checkpoint 线程全部清除，19 个已结束 run 全部记账，没有对应 run 的残留线程为 0。

### 面试可讲点
“每个 run 都存一份完整历史”的平方增长是怎么被测出来的（以及第一次测量为什么错）；为什么用自己的列记账而不查第三方表；部分索引的适用条件与 EXPLAIN 验证；先删后记账的理由；DELETE 不立即释放磁盘。

## 2026-10 · 阶段 1 收尾（二-2）：统一错误格式、request-id 与结构化日志（决策 0011）

### 目标
让“出错了”可以被定位：错误响应格式统一且带请求编号；日志能按请求编号、执行编号检索；应用自己的 INFO 日志不再被丢弃。

### 设计思路
- **一个编号贯穿一次请求**：中间件生成 request-id，写进响应头、错误体和日志；用户报错时提供它即可。
- **再用 run_id 贯穿一次执行**：提交时一条日志同时带两个编号，把请求和后台执行连起来；执行开始、结束各一条。
- **错误对外统一、对内完整**：对外只有错误码、简短说明和请求编号，500 不露内部细节；对内日志带完整堆栈。
- **不破坏流式**：中间件写成纯 ASGI，只透传消息。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| 纯 ASGI 中间件 | 只透传消息，不影响 SSE 流式和 contextvars | `BaseHTTPMiddleware`：包裹响应体、在独立任务里跑下游，对流式响应和上下文传递有已知问题 |
| contextvars 保存 request_id / run_id | asyncio 下多个请求在同一线程交替执行；contextvars 随协程传递，`create_task` 会复制当前上下文 | 线程局部变量：在 asyncio 里会串号；层层传参：每个函数签名都要改 |
| 标准库 logging + 自写过滤器与 JSON 格式化器 | 需求只是“加两个字段 + 一行一个 JSON”，几十行就够 | structlog / loguru：更强大，但多一个依赖和一套用法，目前用不上 |
| 外部 request-id 仅在 `^[A-Za-z0-9._-]{1,64}$` 时沿用 | 网关或前端可以传入自己的编号以便跨系统追踪；同时防止日志注入 | 无条件沿用：可被注入换行、伪造日志；从不沿用：无法与上游系统关联 |
| 错误体 `{"error": {code, message, request_id, details?}}` | 嵌套一层，与正常响应体不会混淆；`code` 稳定可判断 | FastAPI 默认的 `{"detail": ...}`：不同来源格式不同，没有错误码 |
| 只记路径不记查询串；`/health` 降为 DEBUG；关闭 uvicorn 访问日志 | 查询串可能含敏感参数；健康检查会刷屏；避免同一请求两行日志 | 全量记录：噪声与泄露风险 |

### 遇到的问题
1. **（发现于本步开头）11 个 iCloud 冲突副本被误提交并已推送**，详见上一节“版本库维护”。
2. **错误响应里 `X-Request-ID` 出现两次**（值为“a, a”）：500 发生在中间件之外，所以错误处理器自己设置了这个头；而其他错误经过中间件时又被追加了一次。改为中间件只在响应还没有这个头时才追加。
3. **测试参数“中文”测的不是服务端**：httpx 客户端不允许请求头里出现非 ASCII 字符，在发请求前就抛 `UnicodeEncodeError`。换成 ASCII 范围内的不安全值（`a/b;c`、`<script>`）。
4. **我写了一条没有意义的断言**：在测试任务里断言 `run_id_var.get() is None`，但 run_id 只在 worker 的任务里设置，测试任务里永远是空的——无论代码对错都会通过。删除它，避免虚假的信心。
5. **变异检查“失败的原因不对”**：把查询串记进路径后，测试是失败了，但失败在“按完全相等的路径找日志记录”这一步（`next()` 在异步函数里抛 `StopIteration`，被转成 `RuntimeError`），而不是“不应记录查询串”的断言。改为按前缀查找、再单独断言路径，重做变异确认失败落在目标断言上。教训：变异检查不只看“有没有失败”，还要看“失败在哪”。
6. **按 run_id 只查得到一条日志**：成功执行的路径上本来就没有任何日志，上下文里的 run_id 无处可带。补上“开始执行”“执行结束（结局 + 耗时）”两条生命周期日志，链路才完整。
7. 小坑：在 shell 单引号里写带转义引号的 Python f-string 会出错，改为把脚本写进文件再执行。

### 验证
见 decisions/0011：后端 14 个新测试（全量 101 个）、前端 3 个新测试（共 26 个）、5 项变异检查、容器内按 request_id → run_id 串起完整链路。

### 面试可讲点
request-id 的生成、沿用与防注入；为什么用纯 ASGI 中间件；contextvars 如何跨 `create_task` 传递；错误对外统一、对内完整；从一次请求追到一次后台执行；变异检查要看“失败在哪”。

## 2026-10 · 阶段 1 收尾（三）：对话管理（决策 0012）

### 目标
对话能改名、归档 / 恢复；列表按最近活动排序；新对话自动起标题；长对话的消息分页加载。

### 设计思路
- **归档而非删除**：可逆、不必连带清理关联数据；已归档的对话只读。
- **最近活动时间与消息同事务更新**：列表顺序与消息内容不会不一致；存量数据在迁移里回填。
- **游标分页**：按 `seq` 往前翻，稳定且快；响应体保持列表，`X-Has-More` 放响应头，不破坏调用方。
- **前端合并而不是覆盖**：刷新只拉最近一页，与已加载的旧消息按 `seq` 合并。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| `archived_at` 软隐藏 | 可逆；不用连带清理消息、run、checkpoint、事件流 | 硬删除：不可恢复，且要做级联清理 |
| `last_activity_at` 列 + 同事务更新 | 排序查询只读一张表、走索引 | 每次用子查询算 `max(messages.created_at)`：对话多了很慢 |
| 部分索引 `(user_id, last_activity_at DESC) WHERE archived_at IS NULL` | 只收未归档的对话，并按列表需要的顺序排好 | 普通索引：包含大量已归档的行 |
| `seq` 游标分页 | 新消息插入时不会错位；翻到多早都一样快 | 偏移量分页：会重复或漏消息，越往后越慢 |
| `X-Has-More` 响应头 | 响应体仍是列表，已有调用方不受影响 | 改成 `{items, has_more}`：更直观但破坏兼容 |
| Pydantic `model_fields_set` | 区分“没传 title”和“title 传了 null” | 用特殊值或两个接口：更别扭 |

### 遇到的问题
1. **我的变异检查脚本把一个源文件覆盖了**：备份时用 `basename` 生成备份名，`repositories/conversations.py` 与 `routers/conversations.py` 同名，后备份的路由文件覆盖了仓储文件的备份；第一轮还原时仓储文件被写成了路由的内容，之后的变异全部“未应用”、全量测试 10 个报错。处理：从 git 取回仓储文件上一次提交的版本，再重新应用本次的两处修改（修改内容在记录里完整可查），全量 116 个通过；备份名改用完整路径重跑变异。教训：任何“批量备份 / 还原”都要保证键唯一；还原后用测试确认状态。
2. **索引测试第一版测的不是生产查询**：变异“列表查询去掉归档条件”只让归档功能测试失败，索引测试仍然通过——因为索引测试 `EXPLAIN` 的是我在测试里另写的一条查询。改为把生产查询抽成 `conversations_list_stmt` 并对它做 `EXPLAIN`，重做变异后两个测试都失败。（清理器那一批本来就是这样做的，这次没有照做。）
3. **点“加载更早的消息”后视图被拉回底部**（浏览器实测发现）：侦听器写成 `watch(() => [最后一条 id, 回复文本])`，getter 每次返回新数组，Vue 按引用比较总认为“变了”，于是每次消息列表变化都滚到底部。改为多个源的写法 `watch([() => a, () => b, () => c])`；并在只是“前面多了消息”时，用插入前后的内容高度差修正滚动位置。实测加载前后“第 6 轮提问”在视口中的位置都是 60 像素。
4. **点“显示已归档”文字不能切换开关**（浏览器实测发现）：文字和开关没有关联。用 `<label>` 包住，Ant Design 的开关本身是 `<button>`，label 会把点击转发给它。
5. **浏览器自动化的小坑**：“⋯”按钮和下拉菜单项在无障碍树里查不到，只能截图后按坐标点击。

### 验证
见 decisions/0012：后端 15 个新测试（全量 116 个）、6 项变异检查、前端 3 个新测试（共 29 个）、浏览器实测分页 / 位置保持 / 重命名 / 归档 / 恢复。

### 面试可讲点
归档 vs 删除；为什么排序字段要冗余存一列并同事务更新；部分索引与“测生产查询”；游标分页 vs 偏移量分页；`X-Has-More` 的兼容性取舍；Vue 侦听器的引用比较陷阱。

## 2026-10 · 接入 DeepSeek：两种兼容格式对比与思考模式（决策 0013）

### 目标
用户改用 DeepSeek（OpenAI / Anthropic 官方太贵）。顺带完成“openai / anthropic 分支用真实 key 验证”；在保证体验的前提下尽量省 API 费用。

### 设计思路
- **先查文档再填配置**：展示名“DeepSeek-V4.1-Flash-1017”不是 API 模型 ID，官方文档写明 ID 是 `deepseek-flash`。
- **两种格式都测，用数据选**：同一个 key、临时覆盖环境变量（不改 `.env`），对比思考内容的表示、首字延迟、缓存、工具往返。
- **省钱**：所有自动化测试用假模型；真实调用只在验证时做，整轮约 25 次；发现思考 token 按输出计费后，加开关并默认关闭。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| DeepSeek `deepseek-flash` | 用户选择；价格低；实测首字 < 1 秒 | Gemini 免费档：延迟波动大、过载 503；OpenAI / Anthropic 官方：价格高 |
| Anthropic 兼容格式为默认 | 思考内容是标准 `thinking` 内容块，ChatAnthropic 原样保留，阶段 4 多轮工具调用能传回 | OpenAI 格式：思考在非标准字段 `reasoning_content`，ChatOpenAI 丢弃（仍可作备选） |
| `LLM_THINKING` 开关，聊天默认 `disabled` | 思考 token 按输出计费；关闭后“1+1”的输出从 ~30 token 降到 1，首字快 3~4 倍 | 一直开启：费用与延迟高；写死关闭：阶段 4 的推理型 Agent 无法开启 |
| OpenAI 格式的开关放 `extra_body` | `thinking` 不是 OpenAI 标准参数，只能透传 | — |
| 开关对 Gemini 分支显式报错 | Gemini 的思考配置是另一套参数，没接入；宁可报错也不“设置了却不生效” | 静默忽略 |

### 遇到的问题
1. **冒烟脚本的“首块延迟”对思考模型失真**：长文本只有三百多字却来了 613~881 个分块；细查发现大部分是思考块（不含正文）。原脚本把第一个任意块当“首字”，于是 Anthropic 格式显示 0.16 秒，而真正的第一个正文字在 2.66 秒。修正为分开统计正文块 / 非正文块，首字按第一个**正文**块计，并输出用量（输入、输出、其中思考、命中缓存）。这是同一个脚本第二次因“判据不贴合实际”被修正（第一次见 #21）。
2. **我的推测在实测中没有复现**：我预计 OpenAI 格式在“开着思考做工具往返”时会因丢掉 `reasoning_content` 而 400，实测两种格式都成功。结论只能写成“这个场景没复现”，把“什么条件下触发”留到阶段 4 的多轮工具调用再测；默认格式仍选 Anthropic，因为它不依赖“恰好不触发”。
3. **意外发现：两种格式共享前缀缓存**：先用 Anthropic 格式发过的长前缀，OpenAI 格式第一次请求就命中了 2176 个 token。说明缓存是按账号和内容、而不是按接口格式划分的。
4. **思考 token 计费是从用量明细里发现的**：OpenAI 格式的 `output_token_details.reasoning` 显示“1+1”的 30 个输出 token 里 28 个是思考；Anthropic 格式的用量没有单独列出思考 token。

### 验证
- 后端测试 120 个（新增 4 个：思考开关进入请求体 ×2、非法取值与 Gemini 分支报错）。
- 真实调用：两种格式 × 开启 / 关闭思考的冒烟脚本，缓存与工具往返实验，完整服务链路一次（首个 token 0.72 秒）。

### 面试可讲点
展示名与 API 模型 ID；同一模型两种兼容格式在“思考内容表示”上的差异及对工具调用的影响；思考 token 的成本与开关设计；前缀缓存如何抵消“每次重发全量历史”的成本；推测没复现时如何如实下结论。

## 2026-10 · 阶段 2 前置：RAG 选型调研（decision 0014 草稿）

### 目标
在写 RAG 代码之前定三件事：embedding 模型、要不要重排、向量库（pgvector 还是 Qdrant）。约束：尽量不花 API 费用（DeepSeek 没有 embedding 接口）、中文、阶段 5 的多租户过滤检索。

### 设计思路
- **先建评测集**：自写 30 篇客服知识条目（含近似主题）和 30 个换说法的问题，放进仓库 `backend/eval/`，以后调分块、换模型都能重跑。
- **只用本地模型**：fastembed（ONNX、CPU、不需要 PyTorch），零 API 费用。
- **向量库用基准测试比**：重点测“带过滤条件的检索”，因为多租户下每次检索都带过滤。
- **所有实验脚本进仓库、可复现**；结论写进决策草稿，开放问题等用户确认。

### 结论摘要（详见 decisions/0014）
- embedding：bge-small-zh-v1.5 —— R@1 0.90、R@3 1.00、查询 1.3ms、模型 90MB；关键词基线只有 0.43；Qwen3-Embedding 0.97 但慢 100 倍以上（30 题的差距只有 2 题，不足以定论）。
- 重排：bge-reranker-v2-m3（int8）把 R@1 从 0.90 提到 1.00，每题多约 300ms。
- 向量库：同延迟下 Qdrant 的近似检索召回明显更高（ef=400 时 0.912 vs 0.515，随机数据）；强制 pgvector 走 HNSW 做过滤检索会复现“只返回 0.5 条”的经典问题，迭代扫描能补足条数但召回 0.62；但**租户内精确检索又快又准**（1.2ms、1.000）。建议 Qdrant，PostgreSQL 仍为事实来源、Qdrant 为可重建的派生索引。
- PostgreSQL 内置全文检索不切分中文；第一版不做混合检索。

### 技术选型明细（候选，待确认）
| 候选 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| fastembed（ONNX）跑本地模型 | 不需要 PyTorch，镜像小；CPU 上 bge-small 查询 1.3ms | sentence-transformers：要装 PyTorch（数百 MB 到 GB）；付费 embedding API：用户要求省钱 |
| bge-small-zh-v1.5 | 中文、90MB、够快、本评测集 R@3=1.00 | Qwen3-Embedding：更强但 CPU 上 165ms/查询、1.1GB；jina-v2-base-zh：与 bge 同分但慢 3~4 倍（优势是 8192 长输入） |
| bge-reranker-v2-m3 int8 | 把第一名提到全对；能少放几段进提示词、省 DeepSeek 输入费用 | 不重排：省 300ms，但第一名有 10% 不对 |
| Qdrant（派生索引） | 带过滤的近似检索成熟；不用迁移现有 PostgreSQL 镜像 | pgvector：少一个服务、同事务一致，但规模大后过滤检索不理想，且换镜像有排序规则风险 |

### 遇到的问题
1. **基准测试脚本的输出被缓冲，跑了 10 分钟什么也看不到**：Python 的输出经管道交给 `tee` 时是块缓冲。以后长时间的脚本用 `python -u`。
2. **我的等待条件写错，Qdrant 部分死等**：要求“已索引数量 ≥ 95%”，但 Qdrant 对小于阈值的数据段故意不建 HNSW、直接精确扫描，已索引数量停在 46000 / 50000，永远达不到。从 Qdrant 的状态（green）和已索引数量的组合判断出原因；改为只等状态 green。因为输出缓冲，pgvector 部分已跑完的结果也随之丢失，只能停掉重跑——两个问题叠加的代价。
3. **第一轮 pgvector 结果“看不到问题”**：带过滤时召回全是 1.000，因为规划器根本没走向量索引，而是选了全表扫描 + 精确排序。没有就此下结论，而是补测“强制走 HNSW”，才复现了“只返回 0.5 条”的经典问题，并测了迭代扫描的效果。教训：实验结果“太好”时先看执行计划，确认测到的是自己以为在测的东西。
4. **不过滤时 pgvector 0.076 vs Qdrant 0.361，差距可疑**：单个参数点比较不公平，补测了召回随 ef 变化的曲线（40~400），并在决策里写明两边的结构差异（Qdrant 分段建图、小段精确扫描）。
5. **`docker exec` 没加 `-i`，heredoc 没传进容器**，SQL 一条都没执行、也没有任何报错。
6. **核实了自己写进决策的一个说法**：“换 pgvector 镜像会有排序规则风险”。查了当前数据库：`en_US.utf8` 运行在 musl 上，已有文本唯一索引；musl 不提供排序规则版本号，PostgreSQL 检测不到变化。说法成立，并补充了具体依据。
7. 部署隐患：fastembed 默认把模型下到系统临时目录（已占 2.5GB），会被清理；上线要在构建镜像时下载或挂持久化卷。

### 验证
三个实验脚本与评测集均在 `backend/eval/`，可复现；全程没有调用付费 API；两个基准容器测完已删除。

### 面试可讲点
如何为 RAG 建一个小而有区分度的评测集（近似主题 + 换说法）；本地 embedding 的性价比；重排与 token 成本的关系；pgvector 过滤检索的经典问题及迭代扫描；为什么“租户内精确检索”在小规模下是最优解；派生索引与事实来源；musl 与 glibc 的排序规则陷阱。

## 2026-10 · 阶段 2.1：知识库的数据模型、上传、解析与分块（决策 0015）

### 目标
把“文档进来”这一段做扎实：知识库 / 文档 / 分块三张表、原件存储、上传接口、解析（txt / md / pdf / docx）、中文分块。向量化与 Qdrant 在 2.2。

### 设计思路
- **原件不进数据库**，用 `BlobStore` 接口 + 本地数据卷，以后换 MinIO 只加实现。
- **上传顺序**：校验（归属、类型、空、大小）→ 写原件 → 事务插入记录；插入失败删原件。
- **分块以“不被模型截断”为硬约束**：目标 300、上限 480 token；按句子切、整句重叠。
- **处理沿用 claim 模式**：pending → processing 原子抢占；分块与 ready 同事务。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| pypdf 6.19.0（固定版本） | 纯 Python、无系统依赖；6.21.x 发布不足两周 | unstructured：依赖重、体积大；PyMuPDF：更快但 AGPL 许可 |
| python-docx | docx 事实标准，能读表格 | 转成 PDF 再解析：多一层失真 |
| UTF-8 → GB18030 依次解码 | 覆盖 Windows 上常见的 GBK 中文文件；GB18030 是 GBK 的超集 | chardet 自动探测：多一个依赖，短文本上不可靠 |
| 本地数据卷 + `BlobStore` 接口 | 单机部署够用、少一个服务；接口与 S3 一致 | MinIO：路线图原定，等拆 worker 或需要对象存储特性时再加 |
| 应用生成文档 id | 写原件时就需要 id 作为 key | 数据库生成：得先插记录再写文件，顺序不对 |
| 内容 SHA-256 去重（知识库内唯一） | 同一内容不会被检索两遍；数据库约束兜底并发 | 按文件名去重：改名就绕过了 |
| token 计数可注入（2.1 用估算器） | 2.2 换成 bge 分词器即可，分块逻辑不变 | 直接按字符数：英文、数字混排时偏差大 |

### 遇到的问题
1. **分块函数第一版的收尾逻辑写得很绕**：判断“最后一块是否只剩重叠”的条件里有恒为真的部分，还用文本包含关系近似。写完自查时发现，重写为记录“带过来几句”。之后变异检查又发现**这个记录本身就是多余的**：因为只在“追加新句子之前”才输出，循环结束时最后一句一定是新内容——第二次简化，删掉变量。
2. **测试假设错了而不是实现错了**：“相邻块必须有重叠”的断言在随机句长下失败。原因是重叠只取整句，上一块最后一句超过重叠上限时就不重叠（有意为之）。把规则写进测试与注释。
3. **我的替换脚本把断言插进了循环体中间**，导致缩进错误、测试无法加载；按实际结构重写那段测试。
4. **测试漏洞，变异检查发现两处**：“重叠 + 下一句超过硬上限时放弃重叠”从未被触发（数据太小）；“重叠不能整块带过上一块”也没被测到。各补一个专门构造场景的测试；后者第一版构造错误（3 + 96 没超过目标 100，根本不触发），改成 3 + 99 才对。
5. **“标记 ready 失败时分块要回滚”这条路径一开始没有实现**：写完服务后自查发现，与 run 的 `complete` 不一致，补上回滚并用替身让“标记完成”返回失败来测试。
6. **服务层的大小校验在接口测试里走不到**：接口层已用“读上限 + 1 字节”拦住了超大文件，变异把服务层校验挪到写文件之后，测试仍通过。补了直接调用服务层的测试。
7. **（预先怀疑并证实）Nginx 默认请求体上限 1MB**：3.2MB 的文件经 Nginx 被拒、返回 HTML 错误页，直连 api 则成功。设为 12m，并实测 3.2MB / 10.5MB / 13MB 三种情况都符合设计。
8. 小坑：命令行里内联的 Python 打印语句括号写错，把测试文件也在同一条命令里删掉了，只能重新生成；之后改为脚本文件。

### 验证
见 decisions/0015：新增 40 个测试（全量 159 个）、两轮变异检查、容器内迁移 0006 与上传实测（含 Nginx 上限）。

### 面试可讲点
原件为什么不进数据库、上传的写入顺序；按内容哈希去重；分块为什么要按模型分词器算 token、为什么只用整句重叠；处理时的 claim 与同事务；变异检查如何发现“多余的代码”（等价变异）；Nginx 默认 1MB 上限这类“只在部署形态才出现”的问题。

## 2026-10 · 阶段 2.2：入库流水线（后台处理、向量化、Qdrant）与依赖锁文件（决策 0016）

### 目标
上传后自动完成“解析 → 分块 → 向量化 → 写入 Qdrant → ready”；进程崩溃不丢不重；索引可以从数据库重建。

### 设计思路
- **沿用“先落库再投递”**：pending 落库即代表必须处理；内存队列加速，扫描兜底；原子抢占防重复。单独写一个 `IngestDispatcher`，不和 `RunDispatcher` 抽成通用类（重复很少，阶段 4 会一起换掉）。
- **启动恢复改回 pending 而不是标失败**：文档处理幂等、不花钱；run 重跑要花钱，所以 run 是标失败。同一个“中断恢复”问题，因为代价不同而选了不同策略。
- **先写索引（wait=True）再提交“分块 + ready”**：ready 一定可检索；反向失败留下的孤儿点无害（检索按 id 回库取原文），且重做前按文档 id 清理。
- **一个集合 + 租户 payload 索引 + 别名**：别名让重建可以“建新集合 → 原子切换 → 补录 → 删旧”。
- **计数用模型自己的分词器（复制一份关掉截断）+ 字符下限**。
- **模型在构建镜像时下载，运行时离线**。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| fastembed 0.8.1 + onnxruntime（锁文件确定版本） | 0014 评测选定；ONNX 不需要 PyTorch，镜像小很多 | sentence-transformers：要装 PyTorch（数百 MB 到数 GB）；代价：镜像变大（解包约 0.77GB；`docker images` 显示的 1.01GB 口径不对，见 2.3 的更正） |
| qdrant-client 1.19.1（AsyncQdrantClient） | 与服务端 1.19.2 同一小版本；有异步客户端；`location=":memory:"` 进程内模式可用于测试，不用起服务 | 直接调 REST：要自己写模型和重试；代价：进程内模式不支持 payload 索引，租户索引只能在真实服务上验证 |
| qdrant/qdrant:v1.19.2（固定版本、数据卷、健康检查） | 0014 基准用的就是它；固定版本避免意外升级 | `latest`：不可复现 |
| 单集合 + `is_tenant` payload 索引 | Qdrant 推荐的多租户做法，集合数不随知识库增长 | 每个知识库一个集合：集合有固定开销，知识库多了管理困难 |
| 集合别名 + 带时间戳的集合名 | 重建时原子切换，检索不中断 | 直接删了重建：重建期间检索不可用 |
| 点 id = 分块主键，payload 只放 kb_id / document_id | 原文只有一份（在 PostgreSQL），不会两边不一致 | 原文也放进 payload：检索少一次回库查询，但多一份要同步的数据 |
| `tokenizers` 复制分词器并关闭截断 | 计数与模型实际看到的一致，且不会被截断到 512 | 直接用 fastembed 内部那份：开着截断，超长文本永远数出 512 |
| 字符下限 `max(token 数, 字符数/6)` | WordPiece 把超过 100 个字符的词记成 1 个 [UNK]，不加下限会生成几 MB 的块 | 只按 token 数：被异常输入击穿；只按字符数：中英文差异大，不准 |
| 构建镜像时下载模型 + `HF_HUB_OFFLINE=1` | 启动不联网、可复现；改代码不重下（放在拷贝代码之前） | 运行时下载到数据卷：首次启动依赖外网，离线环境起不来 |
| uv pip compile `--universal --exclude-newer` 生成 requirements.lock | 连间接依赖一起只取发布满两周的版本；每次构建一致 | 手动给每个间接依赖加上限：管不过来；pip-tools：没有按日期过滤；poetry / uv 项目模式：要改项目结构 |
| Nginx `resolver 127.0.0.11` + 变量 proxy_pass | api 容器重建、IP 变化后仍能连上 | 每次重建 api 都重启 web：容易忘，而且部署时会中断前端 |

### 遇到的问题
1. **间接依赖不满两周，手动限版本管不过来**：装 fastembed 时带进了 numpy 2.5.4、onnxruntime 1.31.0、tokenizers 0.23.3，都是不到两周前才发布的。我先手动加了两个上限，接着又发现 numpy 也是新版——这是在打地鼠。改为用 uv 生成锁文件，并用 `--exclude-newer` 按发布日期过滤，顺带完成了“贯穿”里的“后端没有锁文件”这一项。副作用：fastembed 从评测时用的 0.9.0（刚好 14 天）降到 0.8.1；用到的接口相同，真实模型测试在 0.8.1 上通过。
2. **fastembed 内部的分词器开着截断（写代码前查到的）**：打印分词器配置，看到 `truncation.max_length=512`。拿它计数，超长文本永远只数出 512，分块的“强制切开超长句子”就失效了。解法是复制一份，关掉截断和补齐；变异检查（去掉关闭截断这一步）确认测试能发现。
3. **【重点】一个 3.3MB 的文件只切出 1 块**：容器实测时，2.1 遗留的测试文件（330 万个连续的 `a`）处理结果是 ready、1 块。定位过程：查库发现这一块的 token_count=1、长度 3355443；用分词器直接试，`"a"*100` 是 50 个 token，`"a"*101` 却只有 1 个。根因是 bge 的 WordPiece 有一条规则：超过 100 个字符的单个“词”整体记成 1 个 `[UNK]`。真实文档里的 base64、长 URL、哈希、压缩过的 JSON 都可能触发；这样的块向量没有意义，被检索到还会把几 MB 文本塞进模型上下文（按 token 计费）。解法是计数加字符下限 `max(token 数, 字符数/6)`；存进库的 token_count 仍用模型的真实计数。
   - **顺带发现一个性能问题**：`_hard_split` 每切一段都要对**剩下的全部文本**重新计数，一句 1MB 没有标点的文本，耗时随长度平方增长。解法是二分查找的上界取 `limit × 6` 个字符（超过这个长度一定超限）。测试用一个会记录“被要求计数的最长文本”的假计数器，确定性地证明每次计数都不超过 2880 个字符，不依赖计时。
   - 修复后同一个文件：1166 块，每块最多 2880 个字符，用时 4.5 秒。
   - 反思：2.1 时我验证过这个文件“能上传”，却没看它被切成了什么样。验证不能只看状态码。
4. **api 单独重建后，经 Nginx 访问全部 502**：Nginx 日志显示 `connect() failed ... upstream: http://172.18.0.4:8000`。`proxy_pass` 写死主机名时，Nginx 只在启动时解析一次；这次新增了 qdrant 服务，api 重建后 IP 变了，Nginx 还在连旧地址。以前每次都是整套一起重建，所以没暴露出来。解法是 Docker 内置 DNS 加变量形式的 proxy_pass。验证：重建 web 后再单独强制重建 api（IP 从 .4 变为 .6），经 Nginx 访问仍返回 201。当时我的验证脚本把 502 的 HTML 交给 JSON 解析，打出一大串报错；应该先检查状态码。
5. **httpx 日志刷屏**：qdrant-client 用 httpx，每个请求记一行 INFO，处理一个文档就有几十行，淹没了业务日志。在日志配置里把 httpx / httpx2 调到 WARNING。
6. **看不出大文件处理了多久**：run 结束有“结局 + 耗时”日志，文档处理没有。补上“document … processed: ready, 4667 chunk(s), 109.1s”，JSON 格式另带结构化字段。之后才量出 3.3MB 中文文件处理用时 109 秒。
7. **我写的一个测试一开始不能稳定地发现问题**：测“重建期间完成的文档要补录”，第一版是在重建写完第一批点后处理另一个文档。但分块 id 是随机 UUID，按 id 翻页时这个文档的分块有一定概率排在后面，会在第一遍里就被带上——去掉补录的代码，测试也可能通过。改为在“切换别名之前”那一刻处理文档，确定性地制造“写进旧集合”的情形；变异检查（删掉补录）能稳定发现。
8. **一次全部通过要警惕**：入库流水线的 12 个测试第一次就全过。检查后补上了上面那个补录测试，再做变异检查（9 项全部被发现）。
9. 小坑：
   - macOS 没有 `timeout` 命令，脚本报 127；
   - Qdrant 进程内模式对 payload 索引会发 UserWarning，在 pytest.ini 里只过滤这一条，并注明原因；租户索引在容器里对真实服务核对（`is_tenant: true`，点数 14）。

### 验证
- 测试全量 174 个（新增 14 个），变异检查 13 项全部被发现。
- 镜像能在 `--network none` 下加载模型；Qdrant 健康检查与 `/health/ready`（含 qdrant）正常。
- 经 Nginx 上传 3.3MB 中文文件：接口 60ms 返回 202，后台 109 秒完成 4667 块；处理期间 `/health` 响应 10~20ms。
- Qdrant 点数与数据库 ready 分块总数一致（10514）。
- 重建索引（容器内、真实 Qdrant）：15181 块用时 7 分 30 秒（约 30ms 一块，比上传处理慢一些，因为同时在跑的 api 也在占 CPU）；别名从 `chunks_20261021114719…` 切到新集合，旧集合已删除，集合列表里只剩新的一个；新集合点数 15181 = 数据库 ready 分块数；`knowledge_base_id` 的 payload 索引为 `is_tenant: true`。

### 面试可讲点
- 同一个“中断恢复”问题，run 标失败、文档改回重做：取决于重做的代价和是否幂等。
- 双写一致性：哪边是事实来源、写入顺序怎么排、反方向失败为什么无害。
- 别名切换做零停机重建，以及剩下的那一点空档如何承认和处理。
- WordPiece `[UNK]` 的故事：分词器的边界行为会击穿“按 token 限长”的假设。
- Nginx 静态解析 upstream 的坑；锁文件与供应链“冷却期”。

## 2026-10 · 阶段 2.3：检索（向量召回 + 回库 + 重排）与检索测试页面（决策 0017）

### 目标
给一个问题，返回最相关的片段，附来源、分数和各步耗时；前端提供知识库管理与检索测试页面。2.4 的 `knowledge_search` 工具复用同一个服务。

### 设计思路
- **召回 → 回库 → 重排**：Qdrant 只给出 id 和相似度；原文从 PostgreSQL 取，只保留 ready 文档、并在数据库这边再按知识库过滤一次。这样派生索引里的脏数据不会出现在结果里，权限也不单靠索引里的 payload。
- **重排默认开启、可调**：候选数可配置，部署级开关可以完全不加载模型，请求级参数可以单次关闭；返回各步耗时，用来调参。
- **页面以接口为准**：轮询状态（有文档在处理时才轮询），切换知识库时丢弃过期响应；按错误码显示中文提示。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| fastembed 0.9.0 的 `TextCrossEncoder` + bge-reranker-v2-m3-int8 | 0014 评测选定；0.9.0 才有这个模型，今天满两周 | 全精度版（2.27GB）：慢、大；代价：int8 也有 570MB，进程内存约多 0.8GB |
| 回库时 `IN (ids)` + ready + 知识库过滤 | 派生索引的脏数据被自然过滤；权限两道检查 | 原文放进 Qdrant payload：少一次查询，但两边可能不一致 |
| 重排候选 10 个（`RERANK_CANDIDATES`） | 实测 10 个约 1~2 秒，20 个翻倍 | 20 个：理论上召回更全，但在现有评测上 10 个已是 R@3=1.00 |
| 线程数默认不限（`EMBEDDING_THREADS` 可调） | 容器实测：限制线程是“入库速度换检索延迟” | 默认限制到 4：本机实验看起来两边都更快，容器里入库反而慢一倍 |
| Ant Design Vue 的 Segmented / Table / Drawer / Upload | 现有前端已用这套组件库，页面风格一致 | 引入路由（vue-router）：只有两个视图，暂时不需要 |
| 端到端评测脚本只用标准库（urllib） | 在宿主机直接运行，不需要装依赖 | requests / httpx：要装包 |

### 遇到的问题
1. **锁文件里的 fastembed 不支持选定的重排模型**：0014 的评测在 fastembed 0.9.0 上做的；2.2 生成锁文件时 0.9.0 还不满两周，锁到了 0.8.1，而 `bge-reranker-v2-m3-int8` 是 0.9.0 才加的。今天满两周，升级。
2. **只改 `--exclude-newer` 的日期，锁文件一个包都没变**：uv 会把输出文件里已有的版本当作优先选择；要加 `--upgrade-package fastembed`。已写进 requirements.txt 顶部的说明。
3. **0014 的重排耗时偏乐观**：0014 写“约 300ms”，那是在评测集的短条目（中位数 66 字）上测的。真实分块约 200~300 字，10 个候选约 1 秒（本机）到 2 秒（容器）。已在 0014 里加更正说明，并把候选数做成可配置项。教训：性能数字要用和生产相同形状的数据测。
4. **镜像大小看错了口径**：`docker images` 显示 2.03GB，看起来比预期多了 1GB。查下来，containerd 存储模式下这个数字是“压缩包 + 解包内容”的合计；实际是压缩后 0.67GB、解包后 1.36GB（重排模型层 588MB）。2.2 记的“1.01GB”也是这个口径，已在 0016 和 dev-log 里更正。
5. **【重点】分块把空白吃掉了（2.1 留下的问题）**：在检索测试页面上看到 Markdown 的标题和正文粘成一行（`## return_policy退货政策…`），英文 `Really? Yes` 会变成 `Really?Yes`。根因是切句时对每句 `strip()`，拼接时用空字符串连接。2.1 的测试只用了没有空白的中文句子，所以没发现。修复：切句时保留句间空白，整块输出时才去掉首尾空白，跨页处补换行。新增 2 个测试，4 项变异都被发现。已入库的文档不会自动重新分块，记为待办（“全部重新处理”的管理命令）。
6. **【重点】本机的性能结论在容器里不成立**：入库期间重排变慢一倍。本机实验显示，把入库线程限制到 4 个后两边都更快，我据此把默认值改成了 min(4, 核数/2)。随后在容器里复测，发现入库期间重排仍然慢一倍，于是进容器确认线程设置确实生效（ONNX 会话的线程数是 4），再把同一个实验脚本放进容器里跑。结论相反：容器里线程越多入库越快（10 线程 28ms/块 vs 4 线程 38ms/块），争用时限制线程会让入库慢约一倍，换来重排快 26%。最终把默认值改回不限，参数保留可调。这是我判断失误、又被实验纠正的一次。
7. **一个过滤条件正常流程测不到**：“回库时只要 ready 文档”这条，按设计非 ready 文档在数据库里根本没有分块，所以测试里的 pending 文档测不到它。改为直接在数据库里把一个已有分块的文档改成 processing，再验证它不会出现在结果里；变异检查确认能发现。
8. **观察到的分块质量问题（未改）**：块的结尾可能是一个孤立的标题，正文在下一块；重叠内容也可能跨越章节。是否改成按标题切分，留到 2.4 用评测数据决定，不凭感觉调。
9. 小坑：
   - “结果不按召回顺序排列”的变异依赖随机 UUID 顺序，约 1/6 的概率漏检；
   - 浏览器自动化没法操作系统文件选择框，上传改用 curl，以同一个用户身份完成，页面负责展示状态。

### 验证
- 后端测试全量 184 个（新增 10 个），前端 32 个（新增 3 个）；变异检查 12 项全部被发现。
- 端到端检索评测（经 Nginx，完整链路）：仅向量 R@1 0.90、MRR 0.95、接口 17ms；加重排 R@1 1.00、MRR 1.00、接口 541ms，与 0014 直接调用模型的结果一致。
- 容器内：重排模型离线加载；入库期间检索仍可用（重排约 4 秒）；线程数实验数据见 0017。
- 浏览器：知识库视图、状态轮询、失败原因与重新处理、查看分块（段落结构正确、英文空格保留）、检索结果展示。

### 面试可讲点
- 派生索引 + 回库：为什么原文不放 Qdrant；脏数据和权限各靠什么兜底。
- 重排的收益和代价都要量化，而且要用真实形状的数据量（0014 的数字被更正）。
- 线程数实验：本机和容器结论相反，性能结论要在部署环境里测。
- 端到端评测：模型评测好不等于系统好，要走一遍完整链路确认没有损失。

## 2026-10 · 阶段 2.4：知识库问答——预检索 + 检索工具、引用快照、按标题切分（决策 0018）

### 目标
对话 Agent 用上知识库：回答有依据、标注引用，没有相关内容就说没有。达成阶段 2 的里程碑。

### 设计思路
- **范围由服务端决定**：对话关联知识库（新表），执行时读取后放进 RunContext / `configurable`。工具参数只有 query，防止提示注入导致越权。
- **预检索 + 工具**：`prefetch → model → (tools → model)*`。用评测比较了“模型自己决定是否检索”和“预检索”，按数据选了预检索。
- **引用存快照**：落库时连原文一起存，文档以后重新处理也不影响历史回答。
- **前端**：“正在检索”的状态提示；来源标签，悬停显示原文；对话顶部选择关联的知识库。
- **顺带**：用评测数据决定了 2.3 留下的“按标题切分”问题。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| 预检索 + `knowledge_search` 工具 | 评测：引用正确 1.00、模型调用减半、耗时 2.9s → 1.7s、费用约少 30% | 只让模型决定：约 3% 不检索就反问；强制工具调用（`tool_choice=any`）：仍要两次调用，且与思考模式不兼容；只预检索不给工具：追问时没有补救手段。代价：闲聊也检索 |
| 关联表 `conversation_knowledge_bases`（主键是两个 id，级联删除） | 一个对话可以关联多个知识库；删除知识库时自动解除关联 | 在对话表里存一个数组：没有外键约束，删除时会留下脏 id |
| 范围放进 LangGraph 的 `configurable` | 工具节点能拿到，模型看不到；值都是字符串，可以序列化 | 让模型在工具参数里传知识库 id：存在注入越权风险 |
| `messages.citations`（JSONB）存快照 | 历史引用不受文档变更影响；一次查询就能拿到消息和引用 | 单独建一张引用表：多一次连表查询；只存分块 id：重新处理后引用就失效了 |
| 用正则识别回答里的 [n]，标出 `cited` | 简单、确定；前端只展示被引用的来源 | 让模型输出结构化引用（JSON）：流式显示和可读性都更差 |
| `updates` 流 → `tool.started/finished` 事件 | 不改图的结构，Agent 侧统一发送 | 在节点里直接发事件：要把事件出口传进图里（不可序列化） |
| 假模型支持工具调用 | 不用密钥就能跑通“检索 → 引用”的整条链路，测试和演示都不花钱 | 只用剧本模型：本地演示不了 |
| Markdown 按标题切分（只对 .md 生效） | 合并文档的第一名命中率 0.73 → 0.90（加重排 0.90 → 1.00） | 对所有文件都按 `#` 切：txt 里以 `#` 开头的行不一定是标题 |

### 遇到的问题
1. **【重点】模型偶尔不检索、直接反问用户**：30 题里有 1 题（“怎么关掉每个月自动扣费”）模型回答“您指的是哪项服务？”，没有检索。我先在提示词里加上“先检索再追问”，重跑后这题对了，另一题（“钱什么时候能退回我卡里”）又出现同样的情况——这是随机波动，提示词压不住。于是实现了预检索方案，用同一套评测对比，结果 30/30，模型调用减半。教训：只看一轮评测，判断不了改动有没有效果；遇到“偶发”问题，优先从结构上解决。
2. **模型说“没找到”，却还标注了 [1]~[4]**：用来列举“检索到的资料都无关”，前端会把这些当成来源展示。改了提示词：没有找到时不标注编号、也不罗列。改后知识库外的 3 个问题中有 2 个不再标注；剩下一个标注的是知识库里确实写明的付款方式，属于合理引用。
3. **测试替身返回同一个消息对象，图提前结束了**：剧本模型每次都返回同一个 AIMessage 对象，第一次返回后它被分配了 id；再返回时 LangGraph 的 `add_messages` 按 id 原地替换，而不是追加，于是最后一条消息变成了工具结果，“死循环”的模型被当成只说了一句。解法是替身每次返回一个去掉 id 的副本。真实模型不会这样，但这让我搞清楚了 `add_messages` 的合并语义。
4. **前端事件状态机没有 default 分支**：收到不认识的事件类型会返回 `undefined`，把状态弄坏。加新事件时读代码发现的，补上 default 并写了测试。
5. **Markdown 合并文档的检索效果明显变差**：0.73 vs 0.90。用 `eval_chunking_md.py` 量化后实现了按标题切分；变异检查 5 项都被发现，包括“对所有文件都切”和“md 不切”。
6. **派发器在 Agent 创建之前就引用了它**：把 Agent 改成依赖检索服务后，启动顺序要调整（Agent 要在检索服务之后创建，派发器要在 Agent 之后创建）。语法检查和测试都发现不了这个问题（测试不走 lifespan），是读代码时发现的。
7. **浏览器自动化的悬停没有触发弹出框**：用脚本派发 `mouseenter` 后弹出框正常，说明组件没问题，只是自动化工具没有触发这个事件。
8. **观察到但没改**：内容几乎相同的两份文档（客服政策.md 和 v2）会被同时引用，重复的片段白白占用上下文。可以在交给模型前按相似度去重，待做。

### 验证
- 后端测试全量 200 个（新增 16 个），前端 35 个（新增 3 个）；变异检查 16 项全部被发现。
- 迁移 0007 在容器里自动应用。
- 评测（真实 DeepSeek）：

  | 方案 | 引用正确 | 模型调用 | 耗时中位数 | 费用 |
  |---|---|---|---|---|
  | 模型自己决定 | 0.97 | 65 | 2.9s | ~$0.011 |
  | 预检索 + 工具 | 1.00 | 33 | 1.7s | ~$0.008 |

  逐题结果在 `backend/eval/results/`。
- 多轮追问手动测 3 组，全部答对。
- 浏览器：
  - 假模型：关联知识库、“正在检索”提示、来源与原文；
  - 真实 DeepSeek：里程碑问题回答正确并带引用。
- 真实模型调用总花费约 $0.034。

### 面试可讲点
- 用评测数据在“模型自己决定检索”和“预检索”之间做选择：数字、失败方式、代价都说得出来。
- 工具参数为什么不能有知识库 id（提示注入与越权）。

## 2026-10 · 阶段 3：知识图谱——抽取、合并、Neo4j 派生存储、图谱浏览（决策 0019）

### 目标
选一个知识库，能看到自动抽取的实体关系图，点击节点展开关联，并能追溯到原文。

### 设计思路
- **用户确认的三件事**：引入 Neo4j，作为派生存储；按知识库手动构建，先显示预估费用；先只做浏览与溯源。
- **PostgreSQL 是事实来源**：抽取缓存、实体、关系、出处、构建记录都在 PostgreSQL；Neo4j 只存节点和边，每次构建的最后一步整体同步，可以用命令重建。和 Qdrant 同一个模式。
- **省钱三道关**：按内容去重、按“文本哈希 + 提示词版本”缓存、单次构建有上限（确认框里写明金额）。
- **后台任务通用化**：图谱构建是 `IngestDispatcher` 的第二个使用者，所以改成按协议工作的 `JobDispatcher`——有了第二个真实用例再抽象。
- **提示词迭代用数据说话**：v1 → v2 用同样两份语料重测，噪声和成本下降，关系准确率不变，如实记录。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| neo4j:2026.08.1-community（固定版本，堆 512m、页缓存 256m，关闭统计上报，数据卷，wget 健康检查） | 用户确认引入；发布满两周；demo 规模够用 | 只用 PostgreSQL（草稿时的建议，见 0019）；代价：容器内存约 1.0GB |
| neo4j Python 驱动 6.4.0（异步） | 官方驱动，发布满两周；`AsyncGraphDatabase` 与整个栈的 async 一致 | py2neo：已停止维护 |
| `with_structured_output`（强制工具调用）+ Pydantic | 输出可以校验；超过上限时截断而不是报错 | 自由 JSON：更容易出现格式错误；代价：与思考模式不兼容，抽取用单独的关闭思考的模型实例 |
| 抽取缓存表 `kg_extractions`（主键：知识库, 文本 SHA-256, 提示词版本） | 重复内容只抽一次；失败重试和再次构建不花钱；改提示词后旧缓存自然失效 | 不缓存：每次构建都全额付费 |
| 每次构建整体重写图（PostgreSQL 事务内删除再插入；Neo4j 先删后写） | 简单、不会产生增量合并的错误 | 增量合并：要处理实体改名和删除，复杂；代价：Neo4j 侧不是原子的，失败后需要重新同步 |
| `TaskGroup` 并发抽取 | 任何一个失败就取消其余的，不再继续花钱 | `gather`：一个失败了，其余的还会继续跑完、继续花钱 |
| 部分唯一索引“一个知识库同时只能有一个进行中的构建” | 两次构建同时重写同一张图会互相覆盖；由数据库保证 | 在应用层加锁：多进程下不可靠 |
| cytoscape.js 3.34.3（固定版本，没有其他依赖） | 节点图交互成熟，内置力导向布局，MIT 协议 | ECharts：打包后约 1MB；AntV G6 v5：偏重 |

### 遇到的问题
1. **自动生成的迁移漏了外键列的索引**：`kg_mentions.chunk_id`（删除分块时会级联删除提及，没有索引就要扫全表）、`kg_mentions.knowledge_base_id` 和 `kg_relations.knowledge_base_id`（重建时按知识库整体删除）。审读迁移文件时发现，在模型里补上后重新生成。教训：autogenerate 只会照抄模型，模型里没声明的索引它不会补。
2. **测试想构造“内容重复的分块”，第一版没构造出来**：重复 60 次只切出 2 块，而且因为有重叠，两块内容并不相同；改成 400 次后，中间的块才完全一样。
3. **费用断言用了相对误差**：服务里把费用四舍五入到 6 位小数，测试却用相对误差比较，不能用于验证；改成绝对误差 1e-6。
4. **合并测试测不出“多数投票”和“取第一次出现”的区别**：输入顺序恰好让两者结果相同。调整顺序后，变异检查（改成取第一次出现）能被发现。
5. **【浏览器才发现】详情栏宽度为 0**：点击节点后数据已经加载（DOM 里有“Qdrant 技术组件”），但看不见。查元素尺寸，宽度是 0——cytoscape 给内部 canvas 设了固定宽度，flex 布局里的画布不肯收缩，把详情栏挤没了。解法是画布加 `min-width: 0`、详情栏设 `flex: none`，并在详情栏出现后调用 `cy.resize()`。
6. **提示词 v2 没有提高关系准确率**：噪声实体和成本都下降了（费用 -28%），但抽样的关系正确率仍然约 76%（v1 是 78%），偶尔还会出现代码标识符。如实记录；图上的错误关系靠“出处原文”核对。
7. **Neo4j 实际内存比堆大小多一倍**：堆设 512m，容器占用约 1.0GB（JVM 的元空间、直接内存、线程栈等）。与选型时“约 1GB”的估计一致，但配置值不等于实际占用，要实测。
8. **设计上要说清的取舍**：Neo4j 侧“先删后写”不是原子的（`CALL IN TRANSACTIONS` 不能放进显式事务）。中途失败会留下半张图，构建记为失败，重试只需重新同步；派生存储接受这个代价。

## 2026-10 · 阶段 4.1 选型：worker 崩溃接管实验，ARQ vs PostgreSQL 租约队列（决策 0020 草稿）

### 目标
在实现独立 worker 之前，用实验回答里程碑的核心问题：杀掉或卡住 worker 时，任务多久被接手、会不会重复执行。

### 做了什么
- `backend/eval/queue_exp/arq_exp.py`：真实的 ARQ 0.28.0 worker，任务分 8 步，每步写台账；分别对 worker 做 `kill -9` 和 `SIGSTOP` / `SIGCONT`，记录接手时间和重复的步骤数。
- `backend/eval/queue_exp/pg_exp.py`：PostgreSQL 租约队列原型（`SKIP LOCKED` + 租约 + 心跳 + fencing token + 按进度续做 + `LISTEN/NOTIFY`），跑同样的场景，外加入队延迟测试。
- 不调用模型，零费用。

### 技术选型明细（实验用，正式选型待确认）
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| arq 0.28.0（只用于实验） | 路线图原计划；发布满两周 | — |
| `SKIP LOCKED` 认领 | 多个 worker 并发认领不重复、不互相阻塞 | `FOR UPDATE` 不加 `SKIP LOCKED`：worker 之间会排队等锁 |
| fencing token（版本号） | 被接管后旧 worker 的写入一定失败 | 只靠租约时间：旧 worker 恢复后仍可能写回 |
| `LISTEN/NOTIFY` 唤醒 + 1s 轮询兜底 | 唤醒延迟约 20ms；轮询用来发现租约过期的任务 | 只轮询：延迟取决于轮询间隔，间隔调小又增加数据库负载 |

### 遇到的问题
1. **超时取消 `anext()` 会关掉异步生成器**：原型 worker 用 `asyncio.wait_for(anext(notifies), 1)` 等通知，第一次空等超时后，生成器就被关闭了，下一次读取直接是 `StopAsyncIteration`，worker 进程退出。现象是 B 一行台账都没有（stderr 被丢掉了，看不到报错）。我先根据代码推断了原因、改了实现，又补了一个最小复现确认根因（第二次读取得到 `StopAsyncIteration`）。改用 psycopg 自带的 `notifies(timeout=…, stop_after=1)`。教训：实验脚本也应该保留子进程的错误输出；先确认根因再下结论。
2. **psycopg 游标没有 `.scalar()`**：把 SQLAlchemy 的习惯带到了 psycopg 上，脚本报错一次。
3. **ARQ 暂停场景的结果需要读懂**：A 恢复后没有继续写，不是 ARQ 能防重复，而是 A 自己的 `job_timeout` 先到期、取消了任务。ARQ 把“进行中”标记的过期时间设为“超时 + 10 秒”，就是为了让旧 worker 先超时——代价是接管时间与任务时长绑定。

### 验证 / 面试可讲点
- 数据见 decisions/0020：kill -9 后 ARQ 34 秒接手、重复 3 步；租约原型 6 秒接手、0 重复；暂停后恢复的旧 worker 被 fencing 拒绝。
- 可讲：租约 + 心跳 + fencing token 为什么缺一不可；“至多重复一步”的边界；为什么接管时间要和任务时长解耦。

## 2026-10 · 阶段 4.1：独立 worker 与 PostgreSQL 租约队列（决策 0020）

### 目标
把对话 run、文档入库、图谱构建从 api 进程搬到独立的 worker 进程（可以多副本）。worker 崩溃、卡住或被关停时，任务被正确接管：既不卡死，也不重复执行；对话从断点续做。

### 设计思路
- **用户确认**：PostgreSQL 租约队列（不用 ARQ）、run 从 checkpoint 续做、一个 worker 服务执行所有任务。
- **业务表就是任务表**：三张表加租约字段，一个按表参数化的 `LeaseQueue` 负责认领（SKIP LOCKED）、续约、放弃、写回条件（fencing）。
- **保留接口、替换实现**：`RunDispatcher` 和 `JobDispatcher` 的对外接口不变（`enqueue` / `cancel` / `start` / `stop`），内部从“内存队列 + 启动恢复”换成租约。大部分现有测试不用改，只有依赖旧语义的 6 个需要改写。
- **api 只提交、worker 只执行**：通知在提交任务的事务里发（`pg_notify`），取消“写数据库 + Redis 广播”。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| PostgreSQL 租约队列（自己实现，约 120 行） | 实验：kill 后 6 秒接手、0 重复，fencing 挡住旧 worker；数据库仍是唯一的事实来源 | ARQ：接管时间和任务超时绑定、从头重做；代价：队列代码要自己维护 |
| 租约字段放在业务表上（`LeaseMixin`） | 一套状态机，不需要对齐两份状态 | 统一的 `jobs` 表：任务状态和业务状态要对齐 |
| `pg_notify` 在提交任务的事务里发 | 事务提交时才送达，回滚就不送达；没有“通知到了任务却不存在” | 提交后再发：中间崩溃就丢通知（虽然有轮询兜底） |
| Redis Pub/Sub 广播取消 | 只对此刻在线的进程有意义，不需要历史；丢了有数据库标记兜底 | Redis Streams：要保存历史和消费位置，对这种信号是浪费 |
| LangGraph checkpoint 续做 | 已完成的检索、模型调用不重做；图已跑完就直接用最终状态 | 中断即失败：已花的模型费用白费 |
| 存活文件 + compose 健康检查 | worker 没有 HTTP 端口；30 秒没更新说明事件循环卡住了 | 给 worker 加一个 HTTP 健康端点：多一个监听端口 |
| `os._exit` 绕过测试进程退出时的原生库崩溃 | 有证据定位到 C++ 析构阶段，在代码之外 | 不处理：CI 会偶发失败；代价：测试进程跳过 atexit |

### 遇到的问题
1. **【重点】fencing token 管不到外部系统**：改造文档入库时，推演“旧 worker 卡住 → 新 worker 接管并完成 → 旧 worker 恢复”这条时间线，发现原来“按文档删除 Qdrant 向量点”的做法，会让旧 worker 把新 worker 写好的点全删掉——文档显示 ready，却检索不到，而且没有任何报错。改为“只删自己写的；只有成功提交的赢家才清理不属于本次结果的点”，并写了专门的测试。
2. **同一事务里写入顺序错了**：上面那个测试第一次跑时，旧 worker 先插分块、后做版本校验，撞上了接管者分块的唯一约束，直接抛异常，走不到“删自己的点”那一步。改为先做带版本号的状态更新，通过了再写分块。
3. **取消后紧接着关停，任务可能被重新执行**：改写“关停时取消”的测试时想到：取消请求还没被处理，worker 就放弃了租约，接手者会把它当作普通任务再执行一遍。修复：认领后先检查 `cancel_requested_at`。
4. **`TaskGroup` 把“租约丢失”包成了异常组**：图谱构建的并发抽取里抛出的 `_LeaseLost`，外层 `except _LeaseLost` 接不住，因为它被包成了 `ExceptionGroup`。在 TaskGroup 外面用 `subgroup()` 拆出来。
5. **测试场景设计错误：旧 worker 自己接管了自己的任务**：模拟“旧 worker 卡住”时，旧 worker 默认有 4 个执行槽，卡住的只是其中一个，其他槽发现租约过期就把它接管了（版本号变成 3）。这是正确行为；测试要模拟的是整个进程被暂停，所以把并发设为 1。
6. **用 `KeyboardInterrupt` 模拟崩溃，把 pytest 自己打断了**：改用普通异常，checkpoint 里的进度是一样的。
7. **前端：第一次执行的 token 不带 attempt，过滤被绕过**：后端只在接管后才给事件加 attempt，前端写成“有 attempt 才比较”，旧 worker 第一次执行的残余 token 就漏过去了。改为缺省按 1 处理，补了测试。
8. **优雅关停后要 5.2 秒才被接管**：放弃租约时没有发通知，另一个副本要等下一轮轮询（5 秒）。在放弃租约的事务里发 NOTIFY 后，降到 0.9 秒。
9. **变异检查有 2 项存活**：去掉“续约校验版本”和“写回校验版本”后，测试仍然通过——测试里新 worker 很快就执行完了，状态已不是 running，状态条件先挡住了，版本号没有机会起作用。改为让新 worker 保持执行中再检查，两项都能被发现。
10. **测试进程退出时偶发 SIGABRT（134）**：所有测试都已通过、汇总也已打印，之后在 C++ 层报 `recursive_mutex lock failed`。排查过程：
    - 开启 faulthandler 抓不到 Python 调用栈，说明发生在解释器清理完成之后；
    - 全量运行 6~8 次中出现 1 次；排除真实模型的测试后 12 次 0 次；单独跑任何一组 30 次 0 次。
    - 结论：onnxruntime 与其他原生库（grpc、数据库驱动等）在同一个进程里时，全局对象的析构顺序有问题。
    - 先尝试在 fixture 里主动释放模型，没有用（8 次中仍有 1 次）。最终在测试里加载过真实模型时，于 pytest 收尾的最后一刻用 `os._exit` 带着结果退出。
    - 生产 worker 优雅关停时退出码为 0，没有观察到这个问题。
11. **【我的失误】两个后台测试循环重叠，产生大量假失败**：我把第一轮循环开头 `rm -f flaky_*.log` 在 zsh 下报的 `no matches found` 当成了“已经结束”，于是又启动了第二轮。两个 pytest 会话同时删除、重建同一个测试库，日志里全是“测试库不存在”、死锁、外键冲突。这些失败不能说明任何问题，全部作废，停掉后单独重跑。教训：测试共用一个测试库，同一时间只能有一个 pytest 会话；判断后台任务是否结束，要看任务通知，不能看输出的片段。
12. **重跑后的结论**：停掉干扰后，单独跑全量 15 次：14 次通过，1 次失败——`test_sse_http.py` 的“断开连接后释放阻塞读”测试，在 1.5 秒的采样窗口里没观察到恰好 1 个阻塞的 SSE 读连接。之后单独跑这个文件 40 次、全量再跑 20 次，都没有复现（合计全量 35 次失败 1 次）。这个测试此前就因不稳定修过一次，message-lifecycle 导读里也记着一次“原因不明、之后连续 23 次通过”的失败，所以大概率是 4.1 之前就存在的偶发问题。没有为了变绿而放宽断言：改成失败时打印每一次的采样值，下次出现时能直接看出是“一直是 0”（读取方没在阻塞）还是“出现 2”（别的测试留下的同名连接）。最早那次“12 次中 2 次失败”没留日志，无法确认是不是同一个测试。

### 验证
- 后端测试 219 个，前端 39 个；变异检查 15 项全部被发现。
- compose 里 2 个 worker 副本：`kill -9` 后 24.8 秒接管、1 条回复、事件 started → resumed → completed；`docker stop` 后 0.9 秒接管，退出码 0；从 api 取消 0.02 秒生效。
- 真实 DeepSeek，单个 worker：入库、带引用的对话、图谱构建都正常。

### 面试可讲点
- 租约、心跳、fencing 各自解决什么，缺一个会怎样（有实验数据）。
- “fencing 管不到外部系统”：Qdrant 的点如何避免被旧 worker 删掉。
- 取消为什么写两份（数据库 + 广播），以及取消与关停交错时的边界。
- 接管后从 checkpoint 续做，以及前端怎么避免两次执行的文字混在一起。
- 排查一个只在进程退出时出现的原生库崩溃：怎么定位到 C++ 析构阶段、怎么用对照实验缩小范围。

## 2026-10 · 阶段 4.2 选型：沙盒隔离、Docker socket 风险、MCP 与 SSRF（决策 0021 草稿）

### 目标
在让 Agent 执行代码、联网、接入 MCP 之前，用实验确定安全边界：容器加固能挡住什么、谁能持有 Docker socket、联网工具怎么防 SSRF。

### 做了什么
- `backend/eval/sandbox_exp/isolation.py`：11 个“恶意或失控”的代码用例，在加固后的容器里运行，并测启动延迟。
- `backend/eval/sandbox_exp/socket_risk.py`：演示持有 socket 能做什么；验证 volume subpath 的按 run 隔离。
- `backend/eval/mcp_exp/fetch_stdio.py`：通过 langchain-mcp-adapters 接入 mcp-server-fetch，演示 SSRF。
- `backend/eval/mcp_exp/egress.sh` + `squid.conf`：internal 网络 + Squid 出口代理，验证防 SSRF 的规则（含重定向），以及 fetch 服务的 `--proxy-url`。
- 不调用模型，零费用。

### 技术选型明细（实验用，正式选型待确认）
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| docker SDK 7.2.0 | 官方 Python SDK，支持 volume subpath | 调用 docker 命令行：要解析输出，参数注入风险 |
| python:3.12-slim 作为沙盒基础镜像 | 与 api 镜像一致 | alpine：musl 和很多科学计算 wheel 不兼容 |
| langchain-mcp-adapters 0.3.2 + mcp 1.30.0 | 适配库要求 `mcp<2`；均满两周 | mcp 2.3.0：与适配库不兼容 |
| mcp-server-fetch 2026.8.18 | 官方参考实现；满两周（2026.10.19 版不足两周） | 自己写抓取工具：接入 MCP 生态正是这一步的目标 |
| ubuntu/squid:6.6-24.04_edge | Canonical 维护，基于 LTS；按解析后的 IP 做 ACL | smokescreen：要自己构建；只在应用里校验 URL：防不住重定向和 DNS 重绑定 |

### 遇到的问题
1. **只换网络挡不住 SSRF**：把 fetch 放到独立网络后，服务名解析不到了，但 `host.docker.internal:6333` 仍然可达。必须靠出口代理按 IP 过滤。
2. **第三方 MCP 服务的依赖在运行时执行 `npm install`**：mcp-server-fetch 的依赖 readabilipy 检测到 Node.js 就会运行 npm，输出混进了 stdio 协议流（一条 JSON 解析错误），还绕过了锁文件。读源码确认后，结论是第三方 MCP 服务必须跑在构建时装好依赖、不带 Node、只读的专用镜像里。
3. **`mcp` 2.x 与适配库不兼容**：pip 直接报 ResolutionImpossible。适配库和 fetch 服务都要求 `mcp<2`。
4. **【实验失误】代理没在运行，结果却像“全部拦下了”**：Squid 以 proxy 用户运行，没权限写 `/dev/stdout`（我配置的 access_log），启动即退出；又因为用了 `--rm`，容器被自动删除。第一轮所有探测都因“找不到代理”失败，与“规则生效”的表现一样。是从清理时的 `No such container` 发现的。改为探测前先确认代理在运行。教训：安全测试里“被拦下”必须确认是被**规则**拦下的（看代理的访问日志），而不是因为环境坏了。

### 验证 / 面试可讲点
- 数据见 decisions/0021：加固容器 11 个用例全部符合预期，新建容器 126ms；持有 socket 等于宿主机 root；SSRF 在独立网络下仍能经 `host.docker.internal` 发生，Squid 按 IP 过滤后全部拦下（含重定向）。
- 可讲：威胁模型（模型的工具参数由攻击者决定）；为什么“socket 代理”不够；SSRF 为什么要按解析后的 IP 过滤；第三方工具服务的供应链风险。

## 2026-10 · 阶段 4.2：工具、沙盒执行、MCP 网关与 Skills（决策 0021）

### 目标
让 Agent 能执行代码、读写文件、抓取网页，并通过 MCP 接入外部工具服务；同时守住 0021 定下的安全边界：模型能触发的执行，即使被提示注入完全控制，也碰不到宿主机、内部服务、密钥和别人的文件。

### 设计思路
- **用户确认**：独立 sandbox 服务独占 Docker socket；MCP 网关 + Squid 出口代理；Skills 用 Markdown + `load_skill`。
- **三个进程各管一件事，worker 只是客户端**：
  - sandbox 服务：唯一持有 socket，只开放“在某个工作空间、用写死的加固参数执行代码”和读写该工作空间文件；
  - MCP 网关：唯一运行第三方代码的地方，只接入 internal 网络，经代理出网；
  - worker：通过 HTTP 调用两者，自己既不持有 socket，也不运行第三方服务。
- **“在哪执行、以谁的身份”由服务端决定**：工作空间 id（= 对话 id）和用户 id 放在图的配置里，工具参数里没有它们——和 0018 里“检索哪些知识库由服务端决定”是同一个原则。
- **工具由技能启用，执行前再检查**：模型平时只看到 `load_skill`；加载技能后才绑定它列出的工具。执行时再检查一遍，模型“猜”着调用或被诱导调用没启用的工具，直接拒绝。
- **工具失败不让回答失败**：沙盒拒绝、超时、网关不可用都以错误结果告诉模型，由它修正代码或如实告诉用户。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| docker SDK 7.2.0（只在 sandbox 服务里用） | 官方 SDK，支持 volume subpath 挂载 | 调用 docker 命令行：要拼参数、解析输出 |
| 每次执行新建容器 | 实验 126ms，没有残留进程和状态 | 复用容器 + exec（41ms）：上一次调用可能影响下一次 |
| 沙盒镜像 python:3.12-slim + pandas 2.3.3 / numpy 2.5.3 / matplotlib 3.11.2（锁文件） | 数据分析的常用组合；构建时装好，运行时无网络也不能装包 | 运行时 pip install：要开网络，供应链不可控 |
| 工作空间按对话划分 | 后续提问要用到上一轮的文件；对话只属于一个用户 | 按 run 划分（草稿）：每轮都要重新上传数据 |
| mcp 1.30.0 SDK 直接做客户端和网关 | 我们的工具层是自己的 `AgentTool`；客户端约 60 行 | langchain-mcp-adapters（实验用过）：转成 BaseTool 用不上，还要再拆它的内容块和错误包装；已从依赖中移除 |
| 网关：lowlevel Server + 无状态 streamable HTTP（JSON 响应） | 网关重启不影响 worker；每次请求独立 | 有状态会话：要处理会话过期、重连 |
| 网关每次调用新起上游子进程 | 调用之间不共享状态；上游崩了不用重连 | 常驻子进程：快几百毫秒，但不同用户的调用共享一个进程 |
| mcp-server-fetch 2026.8.18（`--proxy-url` 指向 Squid） | 官方参考实现；满两周 | 自己写抓取：接入 MCP 生态正是目标 |
| ubuntu/squid:6.6-24.04_edge | 按解析后的 IP 拒绝私有地址，挡住重定向和 DNS 重绑定 | 只在应用里校验 URL：挡不住重定向 |
| compose 三个专用网络（sandbox / tools 为 internal，egress 出外网） | 网关连不到 sandbox 服务和数据库；sandbox 服务只和 worker 相通 | 都放默认网络：第三方代码能直连没有鉴权的 Redis / Qdrant / Neo4j |
| PyYAML 6.0.3（显式声明） | 技能文件头；原本是 langchain-core 的间接依赖，直接使用就显式声明 | 自己解析 `key: value`：列表、引号都要处理 |
| 工具结果截断 8000 字符 | 打印整张表、整个网页会挤爆上下文、白花 token | 不截断：一次 python_exec 就可能几万 token |

### 遇到的问题
1. **应用级鉴权把健康检查也拦了**：第一版用 `FastAPI(dependencies=[Depends(authorized)])`，`/health` 也要令牌，compose 的健康检查会失败。路由上写 `dependencies=[]` 去不掉应用级依赖。改为把需要鉴权的接口挂在一个带依赖的子路由上。
2. **【重点·安全】文件路径拼进 URL，能读到别的对话的文件**：第一版客户端是 `GET /workspaces/{ws}/files/{path}`，path 由模型给出。写测试时想到：httpx 会规范化 URL 里的 `..`，`../../<别的对话>/files/secret.txt` 发出去就变成了 `/workspaces/<别的对话>/files/secret.txt`——服务端的路径校验根本看不到 `..`。用一行代码确认了规范化行为，然后把路径改放到查询参数和请求体里，补了“通过点段到达别的工作空间”的测试。教训：服务端校验的前提是“看到的就是对方发的”，而 URL 路径在客户端就可能被改写。
3. **非法的工作空间 id 得到 404**：同一个原因，`../../etc` 作为工作空间 id 也在 URL 里被规范化了，请求打到了不存在的路由。客户端拼 URL 前先校验 id 是 UUID（服务端也校验，两层）。
4. **网关发现重名工具时抛出的是 ExceptionGroup**：检查写在 mcp 会话里面，会话是一个 anyio 任务组，里面抛出的异常被包装了。把检查移到会话外面。
5. **网关测试的 fixture 报“在不同任务里退出 cancel scope”**：网关的 lifespan 开了 anyio 任务组，必须在同一个任务里进入和退出；pytest-asyncio 的 async fixture 准备和清理不在同一个任务里。改为在每个测试里用上下文管理器启动网关。
6. **沙盒每次画图都在 stderr 打警告**：我在构建时把 matplotlib 的字体缓存预生成到了 `/opt`，运行时目录只读，matplotlib 警告“不可写、改用临时目录”。实测 slim 镜像字体很少，在 tmpfs 上现建缓存加画图只要约 0.3 秒，于是去掉预生成，把配置目录放到 `/tmp`。教训：优化之前先测，预生成在这里没有收益。
7. **加了技能上限后，普通问答的兜底步数也变宽了**：图的 `recursion_limit` 一开始按“检索上限 3”和“技能上限 8”的较大值算，原有的“失控模型在有限步后停下”测试失败（10 次调用 > 5）。改为只有配置了技能才用较大值。原测试正好守住了这一点。
8. **list_files 工具读错字段名**：服务端返回 `size`，我在工具里写成了 `bytes`，单测发现。
9. **fetch 内网地址的报错是“robots.txt 返回 403”**：fetch 服务先取 robots.txt，这一跳就被代理拦了。为了确认是**规则**拦下的而不是别的原因，核对了 Squid 的访问日志（5 条 `TCP_DENIED/403`，外网是 `TCP_TUNNEL/200`）——和实验时“代理没在运行却像全部拦下”的教训一致。
10. **【我的失误】端到端脚本多跑了一遍**：本想只看 worker 日志里的用量，命令里却带上了跑脚本那一段，两个问题又跑了一次，多花约 $0.002。以后“查看结果”和“执行脚本”分成两条命令。
11. **测试辅助函数的参数名冲突**：`_call(name, **args)` 里工具参数也叫 `name`（load_skill 的参数），调用时报“参数重复”。改名为 `tool`。

### 验证
- 后端测试 243 个，前端 42 个；变异检查 7 项全部被发现（见 0021 第五节）。
- compose 里不调用模型的隔离检查：工作空间隔离、沙盒断网、无 socket、无密钥；fetch 外网正常，5 个内部地址全部被代理拒绝；网关容器连不到任何内部服务、也直连不了外网。
- 真实 DeepSeek：数据分析（加载技能 → 写文件 → 执行三次 → 回答并保存图表）与网页问答（加载技能 → fetch → 带出处的回答）都正常，4 次 run 合计约 $0.005。

### 面试可讲点
- Docker socket 等于宿主机 root：为什么让一个小服务独占它、只开放窄接口，而不是让 worker 直接调用。
- URL 规范化导致的跨工作空间读取：发现过程、为什么服务端校验不够、怎么改。
- SSRF：为什么只换网络不够，出口代理按解析后的 IP 过滤，以及怎么确认“是规则拦下的”。
- 工具由技能启用、执行前再检查：把“模型能做什么”变成服务端可检查的许可，而不是写在提示词里的请求。
- 第三方工具的供应链风险：运行时 npm install 的发现过程，专用只读镜像 + 每次调用一个新进程。

## 2026-10 · 阶段 4.3 选型：多 Agent 并行、审批中断与报告产物（决策 0022 草稿）

### 目标
在实现“深度调研”Agent 之前，用实验回答：子任务怎么并行、worker 崩溃时已完成的子任务会不会重做；审批中断恢复时有什么陷阱；等待审批时 run 和 worker 处于什么状态。

### 做了什么
- `backend/eval/multiagent_exp/fanout.py`：LangGraph `Send` 扇出 4 个子任务，测并行加速和 `max_concurrency`；执行中 `kill -9`，用同一个 thread_id 在新进程里续做，数哪些子任务被重做；对照组是“一个节点里循环执行”。
- `backend/eval/multiagent_exp/interrupt_exp.py`：`interrupt()` + `Command(resume=...)`，每一步一个新进程；对比“计划和审批分两个节点”与“写在同一个节点”；拒绝后带修改意见重新制定计划。
- 用真实的 AsyncPostgresSaver，模型调用用 sleep 模拟，零费用。

### 技术选型明细（实验用，正式选型待确认）
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| LangGraph `Send`（langgraph 1.2.14，已在用） | 动态扇出，同一步并行的任务各自写 pending write，已完成的不重做 | 自己用 `asyncio.gather` 在一个节点里并行：崩溃后整个节点重做（实验对照组） |
| `interrupt()` + `Command(resume=...)` | 暂停状态存在 checkpoint 里，任何 worker 都能恢复 | 自己在 run 表里存“待审批”的中间状态：要自己保存和还原图的位置 |
| 实验台账用 JSONL 文件 | 多个进程追加写、按进程号区分，足够数重复执行 | 数据库台账：多一张表，这里没必要 |

### 遇到的问题
1. **【实验发现】恢复时含 `interrupt()` 的节点从头执行**：反例里模型调用和 `interrupt()` 在同一个节点，恢复时模型又被调用了一次。我让模拟模型每次输出带上进程号（模拟真实模型输出不确定），结果是**用户批准的计划和实际执行的计划不一样**——审批形同虚设。规则：有成本或副作用的步骤放在审批节点之前的独立节点里。
2. **并行的粒度是“任务”**：同样的 4 个子任务，`Send` 扇出时崩溃只重做未完成的 2 个；在一个节点里循环则 4 个全重做。想要“已完成的不重做”，每个子任务必须是独立的任务。

### 验证 / 面试可讲点
- 数据见 decisions/0022：并行 4 个 1 秒任务 1.02 秒，并发上限 2 时 2.03 秒；kill -9 后只重做未完成的子任务；等待审批 1.6KB、不占 worker。
- 可讲：pending writes 让并行分支“部分完成”也能续做；interrupt 的重放语义和“批准的 ≠ 执行的”陷阱；为什么等待审批要释放租约、但仍算活跃 run。

## 2026-10 · 阶段 4.3：深度调研 Agent、计划审批与报告产物（决策 0022）

### 目标
给 Agent 一个复杂任务，能看到它拆成子任务、经用户确认后并行执行、汇总成可下载的报告；执行中 worker 崩溃，已完成的子任务不重做、只有一份结果。

### 设计思路
- **用户确认**：同一 run 内 Send 扇出、调研计划审批、产物表 + 下载接口、对话级 Agent 类型。
- **审批复用接管机制**：等待审批 = 结束这次执行、放弃租约；答复 = 回到 queued。之后任何 worker 认领都从 checkpoint 继续，和 4.1 的崩溃接管是同一条路径，不需要新的“恢复”逻辑。
- **Agent 只判断“从哪里开始”**：图里有待答复的中断就 `Command(resume=答复)`，图没跑完就从断点继续，图跑完了就直接用最终状态，否则是新任务。这一个判断同时覆盖“审批后继续”“接管续做”“答复前被接管”三种情况。
- **两条来自实验的规则**：子任务必须是独立的任务（Send）；模型调用和 interrupt 分在两个节点。
- **子 Agent 的上下文隔离**：每个子 Agent 只看到自己的子任务，汇总只拿结论。工具只有检索和 fetch：网页内容可能有提示注入，子 Agent 不能执行代码、写文件。
- **产物先写原件、后落元数据**：元数据和助手消息同一事务、带租约版本校验，被接管的旧执行者写不进来；它可能留下的孤儿原件不可下载，记为已知局限。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| LangGraph `Send` + `max_concurrency=3` | 已完成的子任务结果存进 checkpoint，崩溃只重做未完成的；并发上限控制同时调用模型的数量 | 独立子 run：要新做父子状态机、事件汇总、级联取消；代价是单个调研受一个 worker 的并发约束 |
| `interrupt()` + `Command(resume)` | 暂停位置存在 checkpoint 里，任何 worker 都能恢复 | 自己在表里存“图走到哪了” |
| run 新状态 `awaiting_approval` + 放弃租约 | 等待可能几小时，不能占执行槽；仍算活跃 run，同一对话不会并发写 checkpoint | worker 挂着等：一个等待就占一个槽 |
| SSE 在审批处“暂停”（结束响应） | 不让连接挂几个小时；答复后带 Last-Event-ID 续订 | 一直挂着：占连接，代理还可能超时断开 |
| 计划用结构化输出（关闭思考的模型），子 Agent / 汇总用聊天模型 | 计划要结构化才能审批和估算；思考模式与强制工具调用不兼容（0019 已验证） | 让模型自由文本列计划：要解析，数量无法强制 |
| `artifacts` 表 + 已有原件存储（数据卷） | 和对话、知识库一样按用户鉴权；api 不需要接触 sandbox | 写进沙盒工作空间：api 要接入 sandbox 网络 |
| 下载用 `Content-Disposition: attachment` + `filename*` + `nosniff` | 报告内容来自模型，不能在页面里当 HTML 渲染；中文文件名用 RFC 5987 | inline 显示：模型输出可能被当成 HTML |
| 前端带鉴权头 fetch 成 Blob 再下载 | `X-User-Id` 头普通链接带不上（阶段 5 换成 cookie 后可以直接用链接） | 把用户 id 放进 URL：不安全，也违背“敏感信息不进 URL” |

### 遇到的问题
1. **status 列放不下新状态**：`awaiting_approval` 有 17 个字符，列是 varchar(16)。写迁移时对着模型逐列核对发现的，没等到运行时报错。顺手补了一个测试：迁移升级到最新后，用 Alembic 的 `compare_metadata` 对比库和 ORM 模型（列、类型、索引、外键）。
2. **这个测试第一次就通过**：它到底能不能发现问题？故意改坏模型 3 处（status 改回 16、改索引列、多加一列），3 次都失败，才算确认有效。它比较不了部分索引的 WHERE 条件，所以“等待审批算活跃”另外由接口测试覆盖。
3. **模拟崩溃时，模型抛出的 BaseException 变成了 AttributeError**：我想用一个 BaseException 模拟“进程死掉”（子 Agent 的 `except Exception` 接不住），结果 LangChain 的 `agenerate` 没能正确传播它，变成了 `AttributeError: 'Crash' object has no attribute 'generations'`，被当成普通失败处理了。改为在检索工具里抛出。
4. **【前端，4.1 就有的问题】接管后的生命周期事件被丢掉**：前端会忽略“比当前尝试更早”的事件（防止旧 worker 的残余 token 混进来），但派发器发的 `run.completed`、`run.failed` 都不带 attempt，接管后（attempt=2）就被当成残余丢了。4.1 没发现，是因为流在终态事件处结束后页面会从数据库重新加载，碰巧掩盖了；审批卡片则会直接不显示。补“接管后进入审批”的测试时发现。改为只过滤 Agent 产生的事件。
5. **浏览器里点“取消”，审批卡片不消失**：后端已经取消了，但等待审批时事件流是暂停的，没有人收 `run.cancelled`。单元测试覆盖不到，在浏览器里点了才发现。改为取消后本地更新状态并从数据库刷新。
6. **旧审批事件会让事件流提前结束**：设计 SSE 暂停时推演“批准后用户刷新页面”：从头回放会先读到那条旧的 `run.awaiting_approval`，如果直接结束，用户就看不到后面的进度。改为遇到暂停事件先查数据库，run 已不在等待就跳过。测试覆盖。
7. **接管后日志里的用量偏少**：用量记在图状态里，被 kill 的那次执行中“在途”的模型调用没有提交，日志里看不到。实际花费比日志多一点，记为已知局限（准确计量放到阶段 5 的用量表）。

### 验证
- 后端 254 个、前端 47 个测试；变异检查 11 项全部被发现。
- 真实 DeepSeek：计划 → 修改意见 → 新计划 → 批准 → 并行子 Agent → 报告 → 下载；计划每版只生成一次（恢复时没有重新生成）。约 $0.004。
- 里程碑：并行中 `kill -9` worker，约 30 秒后接管，只重做未完成的 2 个子任务，1 条回复、1 份报告。约 $0.004。
- 浏览器：审批卡片、刷新恢复、取消、下载按钮。本阶段真实模型合计约 $0.009。

### 面试可讲点
- 审批复用崩溃接管的机制：等待 = 放弃租约，答复 = 重新排队；Agent 用一个“从哪里开始”的判断覆盖审批、接管、答复前被接管三种情况。
- interrupt 的重放语义与“批准的计划 ≠ 执行的计划”。
- 并行子任务为什么用 Send 而不是 gather：崩溃后的重做粒度（有 compose 里 kill -9 的实测）。
- 4.1 遗留的前端事件过滤问题：为什么之前没暴露、怎么被新测试发现。

## 2026-10 · 阶段 5 选型：登录、部门隔离与用量看板（决策 0023 草稿）

### 目标
在把 `X-User-Id` 占位换成真实登录、加上部门与角色、做用量 Dashboard 之前，用实验回答：密码哈希怎么选、会不会卡住服务；只靠应用代码隔离够不够、数据库行级安全（RLS）的价值和代价；用量明细能不能直接聚合；用量怎么采集才不漏。

### 做了什么
- `backend/eval/tenancy_exp/hashing.py`：argon2id / bcrypt 不同参数的耗时；8 个并发登录时普通请求的等待（事件循环里算 vs 线程池）。
- `rls.py`：5 万知识库、30 万文档的原型，对比应用层 WHERE 与 RLS 的耗时；“漏写过滤条件”时两者的结果；超级用户绕过、会话级 SET 串号、未设置用户、写入检查四个陷阱。
- `usage.py`：100 万行用量明细的写入与聚合耗时。
- `callback_capture.py`：图配置里挂一个回调，能否捕获节点内部的所有模型调用（结构化输出、bind_tools、Send、流式）。
- 不调用模型，零费用。

### 技术选型明细（实验用，正式选型待确认）
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| argon2-cffi 25.1.0（argon2id） | 抗 GPU 的内存困难型哈希，OWASP 首选；OWASP 参数下 15ms | bcrypt：cost 12 要 168ms，且没有内存困难性；pwdlib：多一层封装，这里用不上 |
| bcrypt 5.0.0（只用于对比） | — | — |
| PostgreSQL RLS（实验原型） | 数据库层默认拒绝，漏写 WHERE 也不泄露 | 只靠应用层：漏写就全部泄露 |
| LangChain 回调采集用量 | 每次调用结束触发，和图是否提交无关；节点内部的调用都能捕获 | 写进图状态（4.3 的做法）：崩溃时在途调用丢失 |

### 遇到的问题
1. **【实验失误】测量“登录卡不卡事件循环”，两种方式都是 0ms**：计时写在普通请求的任务内部，而阻塞发生在这个任务开始运行之前，根本没被测到。改为从请求到达（创建任务）时开始计时：254ms vs 3ms。又一次“结果太好先怀疑测量”（阶段 2 也遇到过）。
2. **【实验发现】现在的部署下直接加 RLS 完全不生效**：compose 里应用连接数据库用的是 postgres 镜像创建的超级用户，超级用户和表所有者都绕过 RLS（实测看到全部 5 万行）。要用 RLS 必须拆分数据库角色。
3. **【我的误判】以为只写 USING 的策略不检查新写入的行**：我在脚本里预设了“以别人身份插入会成功”，实测被拒——没写 `WITH CHECK` 时 `USING` 同时用于写入检查。脚本按实测改了说明。
4. **回调实验里结构化输出解析成 None**：假模型的 `bind_tools` 直接返回自己，丢掉了 tools 和 tool_choice 参数，结构化输出拿不到工具调用。是测试替身的问题，改成 `self.bind(tools=..., **kw)` 后正常。

### 验证 / 面试可讲点
- 数据见 decisions/0023：argon2id 15ms，事件循环里算会让并发请求等 254ms；RLS 在漏写过滤条件时把 5 万行泄露挡成 705 行，列表多约 0.4ms；百万行明细上个人 / 部门聚合 5~21ms、全站 30 天 261ms；回调捕获了全部 5 次调用。
- 可讲：会话 vs JWT 的取舍（撤销、XSS、CSRF）；RLS 的四个陷阱（尤其“超级用户绕过”和“连接池串号”）；为什么用量用回调采集。

## 2026-10 · 阶段 5：登录、部门隔离（RLS）与用量看板（决策 0023）

### 目标
把 `X-User-Id` 占位换成真实登录；加上部门和角色，知识库可以部门共享；数据隔离在应用层之外再加数据库层的第二道防线；做用量 Dashboard。里程碑：不同角色、不同部门的账号互相看不到对方的数据，Dashboard 有真实的用量曲线。

### 设计思路
- **用户确认**：服务端会话 + HttpOnly Cookie；应用层 + RLS；三个固定角色 + 知识库部门共享；回调写明细 + 查询时聚合。
- **只换“当前用户”这一个依赖**：阶段 1 就把鉴权做成了一个依赖（`current_user_id`），这次换成“Cookie → 会话 → 用户”，路由和服务层的签名都没动。
- **两道防线**：服务层显式检查（返回清楚的 404 / 403）；RLS 让漏写过滤条件的查询也只看到该看的行。身份通过上下文变量传到数据库会话：认证依赖设置，SQLAlchemy 在每个事务开始时用事务级 `set_config` 写进连接。
- **按进程分角色**：api（用户直接触达）受 RLS 约束；worker 执行的任务按 run / 文档的归属取数据，用 BYPASSRLS 角色，保持原逻辑；迁移用表所有者。角色和授权不进迁移（实例级的部署配置，密码来自环境变量），由 migrate 服务最后执行 `storage/roles.py`。
- **读写分开**：共享知识库对同部门“只读”。看得见但不是所有者 → 403；看不见 → 404（不泄露是否存在）。
- **用量从源头采集**：模型调用用回调（调用结束就写，崩溃前已花的也记得到）；请求与 run 同一事务写；检索、图谱抽取也写。Dashboard 查询时聚合，范围按角色检查，RLS 策略也按同样的规则限制。

### 技术选型明细
| 选了什么 | 为什么 | 否掉了什么 / 代价 |
|---|---|---|
| argon2-cffi 25.1.0（argon2id，m=19MiB / t=2 / p=1） | 内存困难型、OWASP 首选；单次 15ms；放线程池不卡事件循环 | bcrypt：cost 12 要 168ms 且不抗 GPU；passlib：已多年未维护 |
| 服务端会话（`user_sessions`，存 SHA-256）+ HttpOnly / SameSite=Lax Cookie | 退出、禁用即刻生效；脚本读不到令牌；下载可以直接用链接 | JWT：撤销要黑名单，令牌在 JS 里可被 XSS 拿走；代价：每个请求一次主键查询、要防 CSRF |
| CSRF：Origin 与 Host 比较 + `Sec-Fetch-Site` | 同源部署下最简单有效；没有 Origin 的非浏览器请求放行（CSRF 的前提是受害者的浏览器） | CSRF 令牌（双提交）：前端每个写请求都要带，收益不大 |
| PostgreSQL RLS（17 条策略）+ 事务级 `set_config` | 漏写过滤条件也不泄露；事务级设置不会在连接池里串号 | 只靠应用层：漏写就全部泄露；会话级 SET：会串到下一个请求 |
| 三个数据库角色（所有者 / api / worker） | 超级用户和表所有者绕过 RLS；worker 的后台任务不是“以某个用户的身份”查询 | api 继续用超级用户：策略完全不生效（实验 a） |
| 上下文变量 + SQLAlchemy `after_begin` 事件 | 服务层大部分方法只收 user_id，不用为了 RLS 改所有签名；流式响应在子任务里也能拿到身份 | 每个服务方法显式传身份：改动面大、容易漏 |
| LangChain `AsyncCallbackHandler`（`on_llm_end`）采集用量 | 节点内部的所有调用都能捕获（实验 4）；与图是否提交无关 | 写进图状态（4.3）：崩溃时在途的调用丢失 |
| ECharts 6.1.0（按需引入 + 懒加载的页面） | 折线 / 柱状、堆叠、提示框都现成；按需引入后单独一个 182KB（gzip）的包，只在打开“用量”时下载 | vue-echarts：多一层封装，最新版刚满两周；Chart.js：堆叠面积和中文场景的例子少 |

### 遇到的问题
1. **Nginx 转发的 Host 不带端口，所有写请求都会被当成跨站**：CSRF 检查比较 `Origin`（`localhost:8080`）和 `Host`；Nginx 原来写的是 `proxy_set_header Host $host`，`$host` 不带端口，转发后是 `localhost`。部署前核对配置时发现，改成 `$http_host`。开发服务器的 Vite 代理 `changeOrigin: true` 会把 Host 改成后端地址，同样改成 false。compose 里经 Nginx 实测：同源写请求正常、跨站 403。
2. **几百个接口测试都依赖 X-User-Id**：给测试一个鉴权替身——只在测试里覆盖“当前用户”依赖，按请求头取用户，并保留一个创建用户的测试接口。真实的登录、Cookie、CSRF、角色由单独的测试覆盖。这样已有断言一个都没改。
3. **新写的测试第一次就全部通过**：登录、越权矩阵都是一次通过。按惯例做变异检查，14 项里 3 项存活：
   - 会话校验里“用户已禁用”的检查：禁用时本来就会删会话，这层是冗余的防线，没有测试单独覆盖它。补测试：直接在库里禁用（会话还在），请求被拒；
   - **把身份设置从事务级改成会话级，测试仍然通过**：我写的“连接池不串号”测试，第一个事务只读、结束时回滚，而**回滚会连会话级的设置一起撤销**，所以根本测不出泄漏。真实请求里写操作会提交，泄漏就会发生。改成提交的事务后，变异被发现；
   - 执行 run 时按可见性重新过滤知识库：没有测试覆盖“关联之后被取消共享”。补测试。
4. **【我的失误】批量建演示账号时参数全乱了**：用 `for spec in "...": set -- $spec` 拆参数，zsh 默认不按空格拆分变量，`--role` 拿到了整串。改成逐条命令。
5. **ECharts 6 的图例压住了横轴标签**：ECharts 6 把图例的默认位置从顶部改到了底部，我按以前的习惯没写位置。浏览器里看到后显式放到顶部。
6. **测试里把 UUID 直接放进 JSON**：越权矩阵里关联知识库的请求体用了 UUID 对象，httpx 序列化报错。测试代码的问题，改成字符串。

### 验证
- 后端 286 个、前端 51 个测试；越权矩阵用两种数据库角色各跑一遍；变异检查 14 项全部被发现。
- compose 经 Nginx 的端到端（见 0023 第七节）：登录、CSRF、部门共享与只读、对话隔离、带引用的问答、按角色的用量范围、退出、api 角色下“漏写 WHERE”只看到 17 个知识库中的 1 个。

### 面试可讲点
- 为什么选会话而不是 JWT：撤销、XSS、下载链接；代价是 CSRF，怎么防（以及 Nginx `$host` 这个差点让所有写请求失败的细节）。
- RLS 作为第二道防线：价值（漏写 WHERE 的实测）、陷阱（超级用户绕过、连接池串号、回滚撤销会话级设置导致测试测不出泄漏）、按进程分角色。
- 只换一个依赖就接入真实认证：阶段 1 的分层设计在这里兑现。
- 用量为什么用回调采集，以及为什么请求与 run 同一事务写。
