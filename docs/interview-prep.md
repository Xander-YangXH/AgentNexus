# 面试拷打准备

> 面试官深挖项目细节时用这份文档打底。核心原则：每一个技术选型都要能从"要解决什么问题"倒推出来——讲清楚问题、约束、方案、权衡，而不是甩一个技术名词。随开发推进持续补充，不要只写结论。

## 项目一句话介绍

AgentNexus 是一个面向团队私有部署的多租户知识智能体平台：把 RAG 知识库检索、知识图谱、多智能体任务编排、可扩展的工具/MCP 接入、隔离的工具执行环境和团队权限管理整合进同一套系统。核心能力可复用，具体业务以"场景包"形式插拔接入，完整落地的场景是**智能客服与工单自动化**，其余场景先留接口占位。

## 业务价值与应用场景

技术选型讲得再清楚，面试官问"这东西对业务有什么用"答不上来，说明只理解了"怎么做"没理解"为什么做"。分几层说：

**平台层面：为什么做"中台"而不是单点工具**——企业里做 AI 应用经常遇到的问题是，每个业务部门都想要一个智能客服/知识问答，如果每个场景单独立项开发，RAG、权限、Agent 编排这些通用能力会被重复造好几遍，维护成本随场景数量线性增长。做成"核心能力平台化、业务场景插件化"的中台架构，新增一个场景理论上只需要接插件层，不用重新搭一遍知识库和执行引擎——这是"共享基础设施摊薄边际成本"的平台经济学逻辑，直接对应项目"核心能力可复用、场景包插拔接入"的设计。

**智能客服与工单自动化场景的具体业务价值**（目前唯一完整落地的场景）：首次响应不依赖人工排队，覆盖大部分有标准答案的重复性问题；知识库覆盖不到或判断为高风险的问题，Agent 自动生成结构化工单并路由，而不是简单"答不了就转人工"，减少人工筛选和录入工单的重复劳动；涉及退款、账号变更这类高风险操作，interrupt 人工审批机制保证不会被 Agent 单方面自动执行——"自动化 + 人工兜底"是这类场景真正能落地的形态，完全自动化在多数企业场景里是不被信任的。

**其他能力域各自的业务意义**：知识图谱解决的是"知识管理"而不只是"知识检索"，能发现文档/政策之间没被显式写出来的关联，典型场景是合规审查（这条新规和哪些旧规则冲突）；多租户权限是"能不能对多个部门/外部客户规模化提供服务"的前提，没有它只能自己内部小范围用；可观测性 Dashboard 让管理者看到 token 成本和请求量，这是 AI 项目在企业内部持续拿到预算的基本要求——领导要看得到"花了多少钱、解决了多少问题"。

**怎么衡量、怎么在面试里讲**：业务价值不能靠嘴说，要有能拿出来的量化依据——阶段 2 的 RAG 评估集能给出检索召回率/回答相关性，阶段 6 录 demo 时可以专门录一段"Agent 独立解决 vs 需要转人工"的对比，Dashboard 的用量曲线本身就是"系统被实际使用"的证据。这些比空说"降本增效"有说服力得多，而且**千万不要编造具体百分比数字**（比如"降低了 40% 成本"），除非真的测过——编造的数字一旦被追问"怎么测的、基线是什么"很容易露馅，不如老实说"这是模拟 demo 数据，量化指标框架已经搭了，真实业务数据需要接入实际系统后才能跑出来"。

## 需求分析 → 架构设计（设计过程，不是技术清单）

从系统要满足的核心需求出发，一步步推出架构：

1. 团队多人共用，不同用户/部门看到的数据要隔离 → 需要多租户权限模型，且权限必须在后端强制执行（前端只是体验层）。
2. 用户上传文档，希望 Agent 能基于文档内容准确回答 → 需要完整 RAG 链路：解析 → 切片 → 向量化 → 检索 → 生成。
3. 不只是"回答问题"，还要让 Agent"干活"（调用工具、生成文件、跑多步骤任务）→ 需要工具调用循环 + 任务可能耗时很久 → 必须异步执行，前端不能同步阻塞等待。
4. 任务耗时长意味着进程随时可能崩溃重启 → 执行状态必须持久化，且要有幂等/恢复机制，不能"重启后任务丢了"或"重启后任务跑两遍"。
5. 除了"这段文本相关"，还想知道"这些概念/实体之间是什么关系" → 需要知识图谱能力，做多跳关系查询。
6. Agent 能接入的工具要能持续扩展，不能每加一个工具就改一遍核心代码 → 需要标准化的能力接入协议。
7. Agent 生成的命令/代码不能直接在宿主机上跑（可能被恶意输入诱导执行危险操作）→ 需要隔离的执行环境。
8. 系统要能被运维和管理者监控（用了多少 token、跑了多少请求、哪里出错）→ 需要可观测性和管理看板。

以上八条需求，两两之间会互相制约（比如"异步执行"和"团队权限"叠加起来，就要求异步任务本身也要能做权限校验；"知识图谱"和"多租户"叠加，就要求图查询也要考虑数据隔离），这也是为什么架构会分层设计而不是一个单体脚本。

## 技术选型依据（第一性原理，不是"因为流行"）

### 后端 API 框架：FastAPI
系统里大量操作是"发起请求后等待外部响应"（等 LLM API、等数据库、等文件解析），这是 I/O 密集型场景，原生 async/await 支持是硬需求而不是加分项。FastAPI 基于 Starlette + Pydantic，异步是一等公民，且用类型注解自动生成请求校验和 OpenAPI 文档，减少前后端联调的沟通成本。对比：Flask 的异步支持是后补的，生态不是围绕异步设计的；Django 的 ORM 和全家桶功能在这个场景里大部分用不上，异步能力也还在追赶。

### Agent 编排：LangGraph
核心诉求是"可中断、可恢复、可观测的多步骤状态机"——不是简单的一问一答，需要支持工具调用循环、人工审批打断（human-in-the-loop）、多个子任务并行。LangGraph 用图结构表达 Agent 的执行流程，内置 checkpoint（可以持久化到数据库）和 interrupt 机制，直接对应这三个需求。如果自己手写状态机，checkpoint/恢复逻辑要重新造轮子；如果只用最基础的"工具调用链"，对分支、循环、中断的表达能力不够。

### 关系型存储：PostgreSQL
业务事实（谁在什么时候发起了请求、Agent 跑到哪一步、有没有跑完）必须有强一致性和事务保证——这类数据不能丢、不能乱序，关系型数据库 + ACID 事务是最稳妥的底座。选 PostgreSQL 而不是 MySQL，主要看中 JSONB（可以灵活存 Agent 中间状态，不用频繁改表结构）和 advisory lock（可以做跨进程互斥，比如迁移脚本、后台任务的串行化）。

### 缓存与异步队列：Redis + 基于 asyncio 的任务队列
Agent 任务异步、耗时不定（几秒到几分钟），前端不能同步等 HTTP 响应，需要"提交任务 → 后台执行 → 状态推送"这套模型。Redis 适合做这层：轻量、支持 Stream 结构化事件流（前端用 SSE 直接消费）、支持轻量信号做取消通知。选基于 asyncio 原生实现的队列库而不是 Celery：整个技术栈（FastAPI、LangGraph、数据库驱动）都是异步优先的，队列这一层如果是同步模型，会在同步/异步之间来回切换上下文，增加不必要的复杂度。

### 为什么"先落库再投递队列"而不是直接发消息
如果先投递队列再落库，消费者可能在数据库记录还没提交时就先执行了；或者进程刚好在两步之间崩溃，导致"消息丢了但库里没记录"这种不一致状态。反过来，"先在同一个事务里落库，提交成功后才投递"，能保证"数据库里有这条记录"是"任务一定会被执行"的充分必要前提——队列只是一个"加速执行"的信使，不是事实来源，丢了可以靠定期扫描数据库补发。这是分布式系统里"事务性发件箱"模式的简化应用，解决的是"业务状态"和"消息投递"这两件事不能原子发生的问题。

### 租约（lease）/心跳机制
多个 worker 实例并发运行，必须防止同一个任务被两个 worker 同时执行（比如一个 worker 处理慢被判定"可能失联"，另一个接过来跑，如果前者其实还活着，就会跑两遍，产生重复副作用）。用租约模式解决：worker 抢到任务时写入自己的身份和过期时间，定期续租证明自己还活着；只有租约真正过期（前任确认失联）才允许别的 worker 接管。这保证了任意时刻只有一个合法执行者，是分布式互斥锁的具体应用。

### 对象存储：先用接口 + 本地数据卷，MinIO 暂缓
文档原件、Agent 生成的文件产物这类二进制大文件不适合塞进关系型数据库（会拖慢备份、事务、索引效率），需要单独的存储层。代码里定义了与 S3 语义一致的 `BlobStore` 接口（按 key 存取）；当前单机部署用本地数据卷实现，少一个服务。需要多实例共享（阶段 4 拆 worker）或切云端对象存储时，新增一个 MinIO / S3 实现即可，业务代码不用改（decisions/0015）。

### 向量检索：Qdrant（派生索引）+ 本地 embedding
语义检索的本质是"高维向量的近似最近邻搜索"。选型做了实验（decisions/0014）：多租户下每次检索都带过滤，pgvector 强制走 HNSW 后再过滤会丢结果；Qdrant 的带过滤检索在数据增长后更可靠，而且不用迁移现有 PostgreSQL 镜像。**但 PostgreSQL 仍是事实来源**：分块原文、文档状态都在数据库，Qdrant 只存向量和两个过滤字段，丢了可以重建（decisions/0016）。embedding 用本地 bge-small-zh-v1.5（fastembed / ONNX），零 API 费用，模型在构建镜像时下载、运行时不联网。

### 依赖管理：锁文件 + 发布满两周
`requirements.txt` 只写直接依赖和版本范围；`uv pip compile --exclude-newer` 生成 `requirements.lock`，连间接依赖一起只取发布满两周的版本，镜像和开发环境都按它安装。为什么要“冷却期”：刚发布的版本更可能有回归，供应链投毒通常也在几天内被发现并撤下。为什么必须用锁文件：间接依赖才是大头——装一个 fastembed 就带进了三个不满两周的新版本，靠手动限版本管不过来。

### 图数据库：Neo4j
知识图谱的核心操作是"多跳关系遍历"（比如找"A 相关的概念"的"相关概念"）。这类查询用关系型数据库要写多层自连接 JOIN，性能和可读性都差；图数据库把"节点-关系"作为一等公民存储，用 Cypher 能直接表达"路径"查询，是为这类问题专门设计的存储引擎。

### 分层架构：路由薄、服务层厚、仓储层独立
**请求/响应模型为什么和 ORM 模型分开**：对外字段由 schema 显式声明，数据库加列不会意外泄露到接口，改表也不会破坏接口；入口处统一做校验。
**落地方式**（阶段 1 已实现）：路由（`server/routers`）只做参数解析和调用；服务（`services/`）一个方法一个事务，承载业务规则（归属校验、同事务写入）；仓储（`repositories/`）只做单表读写、不管事务。服务只抛领域异常，HTTP 状态码在入口统一映射——服务层因此不依赖 HTTP，后面 worker 直接复用同一套服务。
**为什么越权返回 404 而不是 403**：403 等于告诉对方"这个资源存在但你没权限"，会泄露 id 是否存在；统一 404 让"别人的"与"不存在"不可区分。
**鉴权占位如何不留技术债**：现在用 `X-User-Id` 头 + 单个依赖函数 `current_user_id`；路由只依赖 `CurrentUser` 这个类型，不关心身份怎么来。阶段 5 换成 token 认证时只改这一个依赖。

这是关注点分离的直接应用：路由层只做网络协议适配（校验请求、装配响应），业务规则变化不应该牵动路由代码；仓储层封装"怎么查数据库"，以后换存储方案（比如读写分离、分库分表）不需要改业务逻辑；服务层是业务规则真正发生的地方。分层的直接收益是可测试性——服务层的单元测试不需要真的起一个 HTTP server 或数据库连接（可以 mock 仓储层）。

### 前端：Vue3 + Vite
页面里有大量可复用的状态逻辑（流式消息接收、审批状态、多线程会话状态），Vue3 的组合式 API 对这类逻辑的复用（抽成 composable）比较自然；Vite 的冷启动和热更新速度直接影响开发效率。这个选型更多是工程效率上的权衡，不是说 React 做不到——只是团队/个人的技术路线选择。

**落地方式**（接入设计见 decisions/0008，已实现；实际上流式回复的状态逻辑就抽成了 `pendingReply.ts` 纯函数 + `useChat.ts` 组合式函数，印证了上面的选型理由）：
- **同源而不是 CORS**：前端只请求 `/api/...`，开发时 Vite 代理、部署时 Nginx 转发。少一份跨域配置，也避免阶段 5 带凭据跨域请求的复杂规则。
- **为什么不用原生 EventSource**：不能带自定义请求头，而鉴权在头里；用户标识也不放 URL（会进日志、浏览器历史）。改用 fetch + 流式读取，自己写约 150 行的解析与重连，每个边界都有单测。
- **SSE 解析要处理的边界**：数据块可能在任意位置被切断（逐字符喂入与一次性喂入结果必须相同）；`\r\n` 可能跨块；中文等多字节字符可能被切开（用 `TextDecoder` 的 stream 模式）；`: ping` 注释行要忽略；多行 `data` 要用换行拼接。
- **重连**：网络错误或服务端在终态前断开时重连，带 `Last-Event-ID`；401/404 不重试；连续失败有上限。
- **刷新页面接上正在生成的回复**：后端提供 `active-run`，前端发现活跃 run 就重新订阅；事件流从头回放，已生成的部分立刻补齐（浏览器实测：刷新前 27 字，刷新后 0.6 秒补到 39 字，并继续增长）。
- **界面以数据库为准**：发送后、完成后都重新拉消息列表，临时回复只在生成中显示。
- **XSS**：模型输出用 Markdown 渲染但禁用原始 HTML。模型输出等同于不可信的用户输入——它可能复述用户粘贴的内容，也可能被提示注入诱导输出脚本。
- **部署**：多阶段镜像（Node 构建，Nginx 运行，不含 node_modules）；Nginx 默认会缓冲上游响应，SSE 必须关闭——后端响应头 `X-Accel-Buffering: no` 已足够（实测），`proxy_buffering off` 是兜底。

### 工具执行隔离（沙盒）
Agent 能读写文件、执行命令，如果直接在宿主进程里跑，一旦输入被诱导（prompt injection）生成了危险操作，会直接影响宿主系统。用容器级隔离限定文件系统范围和资源上限，是纵深防御的基本操作——不可信输入（模型生成的工具调用参数）只应该在真正的信任边界内被隔离执行，这条原则不因为"调用方是 AI 而不是用户"就可以放松。

### 标准化工具协议（MCP）
如果每接入一个新工具或新数据源都要写一套定制的绑定代码，扩展性会越来越差。用标准化协议定义"能力发现 + 调用"的接口，工具提供方只需要实现一次协议 server，不同的 Agent 应用都能直接复用——这是"面向接口而不是面向实现编程"这条设计原则在多工具生态里的应用。

### ORM 与数据库访问：SQLAlchemy 2.0 异步 + psycopg3 + Alembic
**需求**：（1）要用部分唯一索引、CHECK 约束、`UPDATE … WHERE` 条件更新这类细粒度控制；（2）表会随阶段 2~5 不断增加，模型与迁移要联动；（3）整个栈是 async 的。
**为什么是 SQLAlchemy 而不是别的**：直接写 SQL 灵活，但表多了之后重复代码和迁移同步成本高；SQLModel 封装更薄，但对复杂约束的支持不如原生 SQLAlchemy；2.0 的 `Mapped[]` 类型注解风格与 FastAPI 的类型驱动风格一致。
**为什么驱动选 psycopg3 而不是更快的 asyncpg**：LangGraph 的 `PostgresSaver` 用的就是 psycopg3，选它项目里只维护一套驱动和一种连接串；asyncpg 的性能优势在 LLM 调用动辄数秒的场景里不是瓶颈。
**为什么 Alembic 而不是 `create_all()`**：`create_all()` 只能建新表，不能演进已有表；Alembic 有版本链、可回滚，autogenerate 出草稿后人工审核。迁移用同步引擎，因为它是一次性脚本，异步无收益。
**主键为什么用 UUID**：id 会出现在 URL 里，自增整数可被枚举并泄露数据量；UUID 不可猜、多实例无需协调；PG13+ 自带 `gen_random_uuid()`。代价是索引更大、插入不如自增有序，所以需要顺序的 `messages` 单独加 `seq` 自增列排序。
**为什么测试要跑真实 Postgres**：部分唯一索引、条件更新的 rowcount、事务回滚，SQLite 模拟不出来，会出现"假通过"；测试库由真实迁移建表，顺带验证了迁移脚本。

### 模型供应商：DeepSeek（Anthropic 兼容格式）
**为什么不是 OpenAI / Anthropic 官方**：价格。**为什么不继续用 Gemini 免费档**：实测首字延迟 7~173 秒、多次 503 过载。
**同一个模型、两种兼容格式，怎么选**：实测对比。Anthropic 格式里思考过程是标准的 `thinking` 内容块，LangChain 原样保留；OpenAI 格式里是非标准字段 `reasoning_content`，LangChain 会丢掉。阶段 4 的工具调用要求把思考内容传回，所以默认选 Anthropic 格式。
**思考模式的成本**：思考 token 按输出计费。回答“1+1”，开启思考时 30 个输出 token 里 28 个是思考；关闭后只有 1 个，首字也从约 2.5 秒降到 0.4~0.7 秒。所以聊天默认关闭，需要推理的 Agent 再单独开启。
**前缀缓存**：每次执行都带完整历史（决策 0006），这部分是相同前缀，能命中缓存，命中的输入价格低 50 倍——“全量历史”的成本因此大幅下降。

### 可观测性：request-id + 结构化日志（标准库）
**需求**：用户报“出错了”时能定位到这次请求的日志；一次请求触发的后台执行也能追到。
**做法**：中间件为每个请求生成 request-id（写进响应头、错误体、日志）；派发器在执行期间设置 run_id；提交消息时一条日志同时带两个编号。上下文用 contextvars，因为 asyncio 下多个请求在同一线程交替执行，线程局部变量会串号，而 contextvars 随协程传递、`create_task` 时自动复制。
**为什么不用 structlog / loguru**：需求只是“每条日志加两个字段、可选 JSON 输出”，标准库加一个过滤器和一个格式化器几十行就够；多一个日志库就多一套用法。
**为什么中间件写成纯 ASGI**：Starlette 的 `BaseHTTPMiddleware` 会包裹整个响应体并在独立任务里运行下游，对 SSE 和 contextvars 都有已知问题；纯 ASGI 中间件只透传消息。

### 流式输出：SSE + Redis Streams
**需求**：逐字显示；断线能续上；晚加入的客户端能看到已生成的部分；阶段 4 worker 独立成进程后依然成立；出故障不能让客户端卡死。
**为什么是 SSE 而不是 WebSocket**：数据是服务端到客户端的单向推送，SSE 基于普通 HTTP，天然支持事件 id 与断线续传语义（`Last-Event-ID`），经过代理和负载均衡更省心；WebSocket 的双向能力在这里用不上。
**为什么事件通道是 Redis Streams**：进程内队列在 worker 拆分后无法跨进程；Redis Pub/Sub 不保存历史，做不了续传和回放；逐 token 写 Postgres 对用完即弃的数据是写放大。Streams 的单调 ID、范围读取和阻塞读恰好对应推送、续传和回放。
**为什么用 FastAPI 内置的 SSE**：0.151 版本内置 `EventSourceResponse`，负责编码、空闲保活和防缓冲响应头，并用独立任务驱动生成器、在客户端断开时取消它；不必手写，也不必引入第三方库。

### 本地开发环境：Docker Compose + healthcheck
需求是"新人 `git clone` 后一条命令跑起全部依赖，且启动顺序不出错"。Compose 用声明式 yml 描述服务拓扑，容器间靠服务名 DNS 互通，数据放命名卷。关键细节是 `depends_on` 默认只等容器"启动"而非"就绪"——Postgres 进程起来到真正接受连接之间有窗口期，api 在窗口期内连库会崩。所以每个有状态服务配 healthcheck（`pg_isready`、`redis-cli ping`），api 用 `condition: service_healthy` 等待。`/health` 与 `/health/ready` 也刻意分开：前者是存活探针（不查依赖，依赖挂了重启 api 无意义），后者是就绪探针（真去连库，失败返回 503）。宿主机端口只绑 127.0.0.1，避免开发机上的数据库暴露到局域网。

## 模块问答（随开发填充）

### Agent 运行链路
**数据模型**：users → conversations（LangGraph 的 thread_id 用 run_id，见 decisions/0006）→ messages；agent_runs 记录一次执行（queued → running → succeeded/failed/cancelled）。

**为什么 submit 要把"用户消息 + queued run"放同一事务**：两者要么都在要么都不在。只存消息没有 run，用户发了话但永远没人处理；只存 run 没有消息，执行时找不到输入。返回成功就等价于"这个任务一定会被执行"，之后投递队列失败也能靠扫描 `status=queued` 补发。测试 `test_failed_submit_leaves_no_orphan_message` 验证了回滚后不留孤儿消息。

**并发正确性放在数据库里**：
- 抢占执行权用条件更新 `UPDATE ... SET status='running' WHERE id=? AND status='queued'`，看 rowcount 判断是否抢到。先 SELECT 再 UPDATE 在并发下有竞态。测试用 8 个协程同时 claim，只有 1 个成功。
- "同一对话同一时刻最多一个活跃 run" 用部分唯一索引（`WHERE status IN ('queued','running')`）实现，而不是应用层先查再插。原因：两个 LangGraph run 并发写同一个 thread 的 checkpoint 会互相覆盖。应用层检查有竞态，唯一索引由数据库串行化保证。
- 终态不可覆盖：`finish()` 只允许从 running 转出，已 failed/succeeded 的 run 不会被迟到的结果改写。

**消息排序为什么不用 created_at**：同一事务内 `now()` 返回事务开始时间，多条消息时间相同；uuid 无序。所以加自增 `seq` 列专门排序。

**为什么迁移用独立的 migrate 服务**：多个 api/worker 实例同时启动时各自跑迁移会互相抢；一次性服务跑完退出，其余服务用 `service_completed_successfully` 等待，迁移只执行一次。
**发消息接口为什么返回 202**：此时消息和 run 已落库但还没执行，202 Accepted 的语义就是"已受理、尚未处理完"。响应体返回 run（`status=queued`），客户端用 run id 查进度。
**派发与执行（阶段 1 单机版）**：
- **队列不是事实来源**：提交成功后入队，但队列丢了没关系——周期扫描 `status=queued` 补投。所以“提交成功 ⇒ 一定会被执行”不依赖任何内存状态。
- **为什么还要 claim**：入队会重复（提交时入队 + 扫描补投），执行前统一先原子抢占，抢不到就跳过。去掉内存去重集合测试依然通过，说明保证来自数据库而不是队列。
- **所有失败路径都要收尾到终态**：异常、超时、优雅关停、强杀后的启动恢复。否则 run 永远 `running`，“同一对话最多一个活跃 run”的唯一索引会把这个对话永久锁死。
- **被打断的 run 为什么标失败而不是自动重试**：没有幂等保证（工具可能已有副作用），重新入队还可能让“毒任务”反复拉垮进程。等 checkpoint 接入后再做断点恢复。
- **为什么不一开始就上 ARQ**：ARQ 解决多 worker 的分发与存活判定，那是阶段 4 的问题。先把单机链路语义测透，换传输层时只改派发器。
- **单进程假设与 lease 的关系**：启动恢复会把所有 running 置 failed，多实例会互相误杀。这正是阶段 4 要 lease + heartbeat 的原因：只有租约过期才允许接管。
**业务表与 LangGraph checkpoint 两份消息，谁是事实来源**（对照实验得出，详见 decisions/0006 草稿）：
- 只传新消息、checkpoint 为准：能跑，但历史藏在框架的二进制状态里，失败轮次的残留也在里面，我们的表对不上。
- 混合（表的全量历史 + checkpoint 已有历史）：消息会翻倍；给消息加稳定 id 只能让用户消息去重，助手消息由图自己生成 id，仍重复，除非把库里的 id 回写进 checkpoint，两个存储更耦合。
- 倾向方案：表为准，图对会话无状态，checkpoint 按 **run** 划分——它只存“一次执行的进行中状态”。实测同一 run 的 thread 失败后 `invoke(None)` 可从失败节点续跑，已完成节点不重做，正好对应阶段 4 的中断审批和崩溃接管。
**LangGraph 接入的落地方式**：
- Agent 对外只是 `RunContext -> str` 的函数，派发器不知道 LangGraph 的存在；换 Agent 或加多 Agent 时派发层不动。
- 数据库消息与 LangChain 消息的互转集中在一个模块，也只在那里测；`tool` 角色出现在历史里直接报错（决策 0006 规定工具中间结果不入库，出现说明数据异常），不静默丢弃。
- 系统提示词只在调用模型时拼接、不写进 state：checkpoint 不重复存它，改提示词不用迁移历史状态。
- checkpoint 表由 LangGraph 的 `setup()` 建，放在一次性 `migrate` 服务里、Alembic 之后；不抄进自己的迁移，因为那套表的升级由 LangGraph 维护。
- 模型走工厂 + 环境变量：`openai` 分支通过 `base_url` 覆盖所有 OpenAI 兼容接口，`anthropic` 单独处理（content 可能是块列表）；默认假模型，所以没有密钥也能测整条链路。**Gemini（`gemini-3.8-flash`）已用真实 key 验证**：非流式与流式都通，完整服务路径两轮对话通过，第二轮能答出第一轮的信息（证明历史取自 messages 表并确实喂给了模型）；content 是块列表（所以需要 `message_text`）。openai 兼容与 anthropic 分支仍未用真实 key 验证。供应商分支：`openai`（兼容接口）、`anthropic`、`google`（Gemini）。Gemini 虽有 OpenAI 兼容端点，仍选原生集成，因为后续流式和工具调用在原生集成里行为更可预期；key 一律显式传入，不依赖库去读 `GOOGLE_API_KEY` 等环境变量。
**流式输出**（decisions/0007，已实现；完整走读见 `docs/guides/message-lifecycle.md`）：
- **三个世界的主从关系**：Postgres 是事实来源；内存队列只是加速；Redis Streams 只是给浏览器看的视图。
- **事件走 Redis Streams**：单调递增的流 ID 直接作为 SSE 的 `id`；`XREAD` 从某 ID 之后读就是断线续传，从 `0-0` 读就是晚加入回放；`XREAD BLOCK` 被新写入立刻唤醒，实测推送延迟 4~6 毫秒。Pub/Sub 不保存历史，做不了续传。
- **终态事件“先提交、再发布”**：客户端收到 `run.completed` 时消息一定已落库（测试在收到事件那一刻查库断言）。
- **数据库决定流何时结束**：SSE 空闲时查库，run 已终态而流里没有终态事件，就按数据库合成一个（带 `synthesized`、没有 id）。事件丢了只损失实时性，不会让客户端卡死。启动恢复也会补发 `run.failed`，查库是第二道保险。
- **Agent 契约不变**：`RunContext` 加一个 `events` 出口，`run()` 仍返回完整文本；最终回复取自图的最终状态而非拼接 token。
- **归属校验放在依赖里**：依赖在响应开始前执行，越权返回 404；放在生成器里会先发出 200。
- **为什么前端不用原生 EventSource**：不能带自定义请求头，而鉴权在头里；用户标识也不放 URL（会进日志）。
- **两个 Redis 客户端**：每个 SSE 客户端占一个阻塞连接；与发布共用连接池时，订阅者一多会挤占执行方的发布。阻塞读客户端的 `socket_timeout` 必须大于阻塞时长（真实 bug，见排错故事）。
- **扩展上限**：并发 SSE 流约等于阻塞读连接池大小（默认 200）；更大规模改为“每个 run 一个读取协程 + 进程内扇出”。
**取消、重试与错误码**（decisions/0009）：
- **错误信息分两层**：原始报错写进数据库和日志，只给开发者；API 和事件只给错误码（timeout / llm_rate_limited / llm_unavailable / llm_config / interrupted / internal），前端翻译成文案。原因：原始报错可能带供应商内部信息和请求细节，对用户也没有意义。
- **怎么分类**：沿异常链找 HTTP 状态码。Gemini 的状态码不在 LangChain 包装的异常上，而在异常链下一层——这是先用错误的 key 实际触发、看了异常结构才确定的。找不到一律归为 internal，宁可保守。
- **取消的三种情况**：排队中直接在库里改状态（与 claim 同一个条件，并发时只有一个成功，返回 200）；执行中取消执行 Agent 的独立任务（返回 202，结果看事件）；已结束返回 409。
- **取消的两个难点**：一是“已认领、任务还没创建”的空档，所以先登记再取消；二是用户取消和服务关停都是 `CancelledError`，用 `Task.cancelling()` 区分——如果都当用户取消吞掉，关停时 worker 收不到第二次取消，`stop()` 会永远挂住。
- **重试**：对同一条输入消息新建 run，不新增用户消息；只允许重试最后一条，否则回复会被追加到后面消息之后，顺序就乱了。
- **历史数据**：加列之前的失败记录没有错误码，用一个新的数据迁移按原始报错文本回填。不改已执行的迁移，因为它不会再次运行，各环境会不一致。
**checkpoint 的存储代价与清理**（decisions/0010）：
- “历史以 messages 表为准、每次把整段历史喂给图”的代价：每个 run 的 checkpoint 都存了一份完整历史，单个 run 随轮数线性增长，一个对话总量随轮数平方增长。实测（随机中文、每轮约 1KB）：第 20 轮单个 run 66KB，20 轮累计 756KB，是对话文字的 18 倍。
- 解法：checkpoint 只对进行中的 run 有用，结束 24 小时后清理。用自己的 `checkpoint_purged_at` 列记账、部分索引找候选、LangGraph 的 `adelete_thread` 删除；先删后记账，单个失败不影响整批。
- 这也是 0006 当时“未测量”的待办，测量之后才知道清理是必需的，而不是可选的优化。
> 待补：租约机制（阶段 4）、worker 崩溃后的恢复怎么测。

### 对话管理
（decisions/0012）
- **归档而不是删除**：删除要连带清理消息、run、checkpoint、事件流且不可恢复；归档只是隐藏、可恢复。已归档的对话只读，恢复后才能继续发消息。
- **排序字段冗余存一列**：`last_activity_at` 在发消息的同一事务里更新，配部分索引 `(user_id, last_activity_at DESC) WHERE archived_at IS NULL`。如果每次用子查询算最后一条消息的时间，对话一多就慢。
- **游标分页而不是偏移量**：偏移量在新消息插入时会错位（重复或漏消息），翻得越深越慢；按 `seq` 游标翻页稳定，走 `(conversation_id, seq)` 索引，多早都一样快。多取一条判断是否还有更多，省一次 count。
- **兼容性取舍**：“是否还有更多”放响应头 `X-Has-More`，响应体仍是列表，已有调用方不受影响。
- **前端合并而非覆盖**：刷新只拉最近一页，与已加载的旧消息按 `seq` 合并；加载更早的消息后保持滚动位置。

### RAG 知识库
**选型调研**（decisions/0014 草稿，实验脚本与评测集在 `backend/eval/`）：
- **评测集怎么建**：30 篇自写客服知识条目，刻意放入近似主题（退货 / 退款、普票 / 专票）；30 个问题换一种说法、避开原文用词，测的是语义理解。关键词基线只有 0.43，说明“换说法”确实有区分度。
- **embedding**：本地 bge-small-zh-v1.5（fastembed / ONNX），R@1 0.90、R@3 1.00、查询 1.3ms、90MB，零 API 费用。Qwen3-Embedding 0.97 但慢 100 倍以上；30 题只差 2 题，不足以说明谁更强——小评测集的结论要谨慎。官方推荐的查询前缀在这里反而降分。
- **重排**：cross-encoder 把 R@1 提到 1.00，多约 300ms；和成本直接相关——第一名更准，就能少放几段进提示词、少花输入 token。
- **向量库**：多租户下每次检索都带过滤。强制 pgvector 走 HNSW 再过滤，只返回约 0.5 条（先取 40 个近邻再过滤掉 99%）；0.8 的迭代扫描能补足条数但召回 0.62。而租户数据量小时，规划器选择“租户内精确检索”，1.2ms 且完全精确——小规模下不需要近似索引。规模增长后 Qdrant 的带过滤近似检索更可靠。
- **倾向 Qdrant，但 PostgreSQL 仍是事实来源**：Qdrant 只是可随时从 PostgreSQL 重建的派生索引（和 Redis 事件流是“视图”同一思路），写入 / 删除向量走“先落库再投递”的后台任务。
- **一个迁移陷阱**：现有 PostgreSQL 是 Alpine（musl）上的 `en_US.utf8`，pgvector 官方镜像是 Debian（glibc），同名排序规则排序不同，直接复用数据目录会让文本索引与数据不一致，而且检测不到。

**文档入口与分块**（decisions/0015，已实现）：
- **原件不进数据库**：大文件拖慢备份、事务和复制；用 `BlobStore` 接口（与 S3 语义一致）+ 本地数据卷，以后换 MinIO 只加实现。
- **上传顺序**：校验（归属、类型、空、大小）→ 写原件 → 事务插入记录；插入失败删原件。反过来会留下“找不到原件”的记录，比孤儿文件更糟。接口层只读“上限 + 1”字节，不把大文件读进内存。
- **按内容哈希去重**：同一知识库内唯一，避免同一段内容被检索两遍；按文件名去重改个名就绕过了。
- **分块的硬约束**：bge-small-zh 只读 512 token，超出静默截断。目标 300、上限 480；按中文句子边界切，不切断句子；相邻块整句重叠约 50 token——宁可不重叠也不带半句话。token 要按模型自己的分词器计数。
- **处理一致性**：pending → processing 原子抢占；“写入全部分块”与“标记 ready”同事务；分块序号唯一约束是第二道防线。
- **部署细节**：Nginx 默认请求体上限只有 1MB，实测 3.2MB 文件被拦且返回 HTML；设为略大于应用上限，让应用返回统一格式的错误。

**入库流水线**（decisions/0016，已实现）：
- **后台处理沿用“先落库再投递”**：pending 落库即“必须处理”，队列只加速，扫描兜底，原子抢占防重复。
- **中断恢复为什么和 run 不一样**：run 中断标失败（重跑花模型费用，用户在等）；文档中断改回 pending 重做（幂等、本地模型不花钱）。幂等的前提是重做前先按文档 id 清掉索引里的旧点，而分块和 ready 在同一事务，中断不会留下分块。
- **两个存储怎么保证一致**：先写 Qdrant（等写入完成），再在一个事务里写分块并标记 ready → ready 的文档一定可检索。反方向失败（索引多了点）无害：检索按点 id 回数据库取原文，没有对应分块的点自然被过滤；失败路径和重做前都会清理。
- **Qdrant 怎么组织**：一个集合放所有知识库，按 `knowledge_base_id` 过滤（`is_tenant` 租户索引）；应用只认别名。重建时“建新集合 → 灌数据 → 原子切换别名 → 补录重建期间完成的文档 → 删旧集合”，检索不中断；剩下的极小空档写在代码注释里，需要时再跑一次。
- **为什么向量不存数据库**：本地模型重算只花 CPU；存一份就多一份要同步的数据。
- **token 计数**：用模型自己的分词器（复制一份关掉截断）；再加字符下限防 `[UNK]` 击穿（见“开发中遇到的问题”）。
- **CPU 密集任务放在 Web 进程里行不行**：放进线程，并发 1（ONNX 自己用满多核）。实测处理 3.3MB 文档期间 `/health` 仍是 10~20ms；但它和对话争 CPU，阶段 4 拆出 worker。
- **失败可见、可重试**：错误码 `index_unavailable` 等；`POST /documents/{id}/reprocess` 只允许 failed → pending，不做自动重试，避免坏文件无限循环。

**检索**（decisions/0017，已实现）：
- **流程**：问题转成向量 → Qdrant 带知识库过滤做近邻搜索（过滤和搜索一起做，条数不会被过滤掉）→ 用 id 回 PostgreSQL 取原文 → cross-encoder 重排 → 取前 k 个。
- **为什么要回库**：原文只在数据库里有一份。只保留 ready 文档，派生索引里的脏数据（处理失败没清掉的点）自然被过滤；数据库这边再按知识库过滤一次，权限不单靠索引里的 payload。
- **重排的量化**：端到端评测（经 Nginx 走完整链路）R@1 从 0.90 提到 1.00，接口从 17ms 变成约 540ms。真实分块更长，10 个候选约 1~2 秒。默认开启，因为第一名更准就能少往提示词里放片段；候选数可配置，也能按请求关闭。
- **可解释**：返回来源（文件、页码、第几块）、两种分数（向量相似度、重排原始分数）、各步耗时；测试页面直接展示，用于调参。
- **为什么要做端到端评测**：模型评测好不等于系统好——分块、过滤、回库任何一步出错都会掉点。这次端到端结果与模型评测一致，说明链路没有损失。

**知识库问答**（decisions/0018，已实现，阶段 2 里程碑达成）：
- **图**：`prefetch → model → (tools → model)*`。预检索先用用户的原话检索，结果以“工具调用 + 结果”的形式放进上下文；模型可以用补全后的检索词再查；最多 3 轮，`recursion_limit` 兜底。
- **为什么是预检索（用数据说话）**：只让模型决定时，约 3% 的问题它不检索、直接反问用户（两轮失败的题不同，是随机现象，提示词压不住），而且每题要调用两次模型。预检索后引用正确 1.00、模型调用 65 → 33、耗时 2.9s → 1.7s、费用约少 30%。代价：闲聊也检索；弱点：追问时原话检索可能不准（模型可以补查，多轮样本还少）。
- **安全**：工具参数只有 `query`。检索哪些知识库、以谁的身份检索，来自对话的关联与归属（`RunContext` → `configurable`），模型改不了，防止提示注入导致越权。检索服务内部还会再校验一次。
- **引用**：片段编号 [n]，同一片段重复检索到时沿用编号；回答里的 [n] 由正则识别；落库的是**快照**（原文 + 来源 + 分数 + 是否被引用），文档重新处理后历史引用依然有效。
- **怎么评估**：三层——模型层（选型）、检索系统层（经 HTTP 走完整链路，看有没有损失）、问答层（是否检索、引用是否指向正确文档，每轮约 $0.01）。引用精确度 0.65 偏低，主要是模型补充引用了相关条目（例如退货问题顺带引用换货政策），不一定是错误；回答完整性没有评估，这是局限。
- **按标题切分**：30 篇条目合成一个 Markdown 文件时，每块混入约 4 个主题，第一名命中率 0.73；Markdown 按标题切分后 0.90（加重排 1.00），和每篇一个文件时一样。

## 开发中遇到的问题（排错故事）

> 面试官常问"项目里遇到过什么问题，怎么解决的"。这里按"现象 → 定位 → 根因 → 解法 → 学到什么"整理，完整过程见 [dev-log.md](dev-log.md)。随开发持续追加。

### compose 里 shell 命令 YAML 解析失败
- **现象**：`docker compose config` 报 `mapping values are not allowed in this context`。
- **根因**：`command: sh -c "echo 'x: y'"` 中的 `: ` 被 YAML 当成映射的键值分隔符；换外层引号后内外引号又冲突。
- **解法**：`command` 改成列表形式，不依赖引号转义。
- **学到**：带冒号和引号的 shell 命令，在 YAML 里用列表形式最稳。

### 环境不具备时如何区分"写完了"和"验证过了"
- **现象**：写 compose 时 Docker daemon 没启动，镜像构建和 `up` 无法执行。
- **做法**：只声称做过的验证（配置校验、应用层单测），把里程碑明确标记为"待本机验证"，环境就绪后补测，并加了反向用例（停掉 postgres 看两个探针的区别）。
- **学到**：交接文档里已验证与未验证必须分开写；只测正常路径不够，故障路径才能证明探针设计是对的。

### SQLAlchemy 共享列对象报错
- **现象**：`Column object 'id' already assigned to Table 'users'`。
- **根因**：把 `mapped_column(...)` 的返回值存成模块变量，被多个模型复用；一个列对象只能属于一张表。
- **解法**：改成每次调用新建的工厂函数。
- **学到**：SQLAlchemy 的列定义是有"归属"的对象，不是可共享的配置。

### 对"事务内手动回滚"这类不确定行为，用测试而不是凭印象
- **疑问**：`session.begin()` 块里手动 `rollback()` 后再退出块，会不会报错或留下脏数据？
- **做法**：针对"run 不在 running 时 complete 失败"写测试，断言助手消息没有落库、run 状态未变。测试通过，才保留这种写法。
- **学到**：事务边界相关的行为用真实数据库的集成测试验证；这类行为 mock 或 SQLite 都模拟不了。

### 验证时过早过滤输出导致误判
- **现象**：`up -d --build` 后看到 api 仍是旧容器、`migrate` 不在列表里，一度以为配置没生效。
- **根因**：镜像还在构建，我又用 `grep` 过滤了输出，丢掉了关键信息。
- **解法**：等构建结束、看完整输出和 `ps -a` 状态，确认 `migrate` 退出码 0。
- **学到**：排查时先拿全量信息再缩小范围；耗时操作要等它真正结束再下结论。

### 容器镜像选型：为什么 slim 而不是 alpine
- **背景**：依赖里有 `psycopg-binary`、`uvloop` 等带 C 扩展的包。
- **判断**：alpine 用 musl libc，很多包没有预编译 wheel，要现场编译，构建慢且容易失败；slim 基于 glibc，有现成 wheel。镜像体积是次要成本。
- **没解决的差异（如实说明）**：本机 venv 是 Python 3.13，容器是 3.12。代码需要 ≥3.11（`StrEnum`），两者都满足；若依赖出现版本差异再统一。

### 连接串格式与特殊字符
- **背景**：应用统一用 `postgresql://`（psycopg 直连、LangGraph 都认），SQLAlchemy 要 `postgresql+psycopg://`；Alembic 的配置文件又会把 `%` 当插值。
- **做法**：集中在一个函数 `to_sqlalchemy_url()` 里转换格式；写入 Alembic 配置时转义 `%`。
- **学到**：连接串在多个库之间流转，格式转换集中在一处，比到处临时拼接更不容易出错；密码含特殊字符是真实场景，不是边角情况。

### 小坑合集（工具链层面）
- 用 `make_conninfo` 想替换库名，结果它返回的是 `key=value` 串而不是 URL，SQLAlchemy 解析失败 → 改用 `make_url().set(database=...)`，全程保持 URL 形式。
- macOS 的 BSD `sed -i` 要写成 `-i ''`，Linux 的 GNU sed 不需要，脚本跨平台时要注意。
- Alembic 新版本对路径分隔符的旧推断方式已弃用，出现 `No path_separator` 警告 → 配置 `path_separator = os`。
- 仓库里残留的 0 字节 `.git/HEAD.lock` 导致提交失败 → 先确认没有 git 进程持有，再删除；不要一遇到锁文件就盲删。

### 类里的方法名遮蔽内置名
- **现象**：import 时报 `TypeError: 'function' object is not subscriptable`，位置指向另一个方法的返回类型注解 `list[Message]`。
- **根因**：同一个类里定义了名为 `list` 的方法，类体内后面的 `list[...]` 解析到的是这个方法而不是内置类型。
- **解法**：方法改名为 `list_for_user`。
- **学到**：类体是一个独立的命名空间，先定义的名字会遮蔽内置名；`list`/`dict`/`type`/`id` 不要用作方法名。

### 测试一次全过，怎么证明它有效（变异检查）
- **背景**：派发器的 8 个测试第一次运行全部通过，但“全过”不等于“有效”。
- **做法**：故意破坏实现再跑测试——去掉启动恢复、去掉补投、关停时不收尾、并发数翻倍、去掉超时，分别有对应测试失败；去掉内存去重集合则测试仍然通过。
- **结论**：前几项证明测试在保护真实行为；最后一项反过来证明“内存去重只是优化，数据库的原子 claim 才是不重复执行的保证”。
- **边界**：我没有把“连 claim 一起去掉导致测试失败”当成重复执行的证据，因为那是我把状态转换一并破坏了，失败原因不同。变异检查的结论要看失败的原因，而不只是失败的数量。

### 多步脚本中途出错，改动处于“一半”状态
- **现象**：一个脚本分两段改多个文件，第二段因目录错误报 `FileNotFoundError`，第一段已生效。
- **做法**：不重来、不盲目补写，先 `git status` 确认哪些文件已改，再只补跑未完成的部分。
- **学到**：脚本里用绝对路径，不依赖 `cd` 的相对位置；出错后先确认现状再动手。

### 自动化脚本失败后仍继续往下执行
- **现象**：批量更新文档的脚本因正则写错而崩溃，但紧随其后的 `git commit` 照常执行，提交了一半新一半旧的状态。
- **根因**：脚本和提交是两条独立命令，没有“前一步成功才继续”的依赖；统计脚本分母为 0 时没有显式断言，只是碰巧以除零报错的方式暴露。
- **处理**：不凭印象，逐个文件检查标志性内容是否已写入，只补缺的部分，并追加修复提交。
- **学到**：（1）关键脚本里对“不可能为 0”的量加断言；（2）要求原子性的操作用 `&&` 串起来，或先确认输出再提交；（3）这是同一天第二次出现“多步操作做了一半”，说明应该把多文件更新做成幂等、可重跑的形式。

### 自己的论断被实验推翻了一半
- **现象**：我先断言“以业务表为准，失败的 run 不会污染历史”，并用实验支撑。
- **根因**：实验里我在代码里人为把失败那条消息排除了，等于预设结论；真实系统中失败 run 的用户消息提交时就已落库，两种方案的下一轮都会看到它。
- **发现与处理**：设计下一个实验时对照真实数据流推演，发现不一致；在 decision 里公开更正，并改写真正的优势——策略握在我们手里、可见、可调整。
- **学到**：实验必须复刻真实数据流，不能替自己倾向的方案挑输入；发现自己错了就在文档里直接更正，面试里讲这个比讲“一直都对”更可信。

### 第三方库的默认值在生产里才会炸
- **现象**：连接池写 `max_size=1`，报 `max_size must be greater or equal than min_size`。
- **根因**：`psycopg_pool` 的 `min_size` 默认是 4，我只设了 `max_size`。
- **为什么值得讲**：这段代码有两个调用点——测试里的夹具和生产里的 migrate 建表。测试先炸，所以生产的同一个 bug 被提前抓住了；如果只在生产路径里用这个函数且没有测试，就会在部署时才发现。
- **学到**：只设一个参数时去看库里与之相关的其他默认值；让每条生产代码路径至少被一个测试走到。

### 配置“写了”不等于“生效了”
- **现象**：`.env.template` 里列了 `WORKER_CONCURRENCY` 等变量，用户改了却没有任何效果。
- **根因**：docker compose 只把 `environment:` 里列出的变量传进容器；`.env` 里多写的只用于 compose 文件内部的 `${}` 替换。我在做上一步时没发现，因为默认值恰好等于代码默认值，行为看不出差别。
- **发现方式**：这一步要加 LLM 变量，核对“`.env` → compose → 容器 → 代码”整条路径时发现少了一环。
- **学到**：配置要验证到“进程内实际读到的值”（我用 `os.environ` 在容器里打印确认），不能只检查配置文件；默认值相同会掩盖传递链路的缺失。

### 没有凭据时，如何验证对外调用的路径
- **问题**：想确认服务确实能请求到第三方 API，但手上没有真实密钥。
- **做法**：用故意错误的密钥调用，看返回的错误是否来自目标服务（这里是 Google 的 `API_KEY_INVALID`）。能证明网络可达、请求格式被接受到“校验密钥”这一步、我们的错误处理能给出可读信息。
- **边界**：这不等于调用成功。模型名是否存在、返回内容的真实形状、流式是否逐段，都只有真实调用才能确认。库的构造函数也不校验模型名，所以“能构造”不代表“模型存在”。
- **配套做法**：写一个只依赖模型层的冒烟脚本，把“key/模型名/网络/额度”的问题与“我们服务代码”的问题隔离开，并输出流式的分块数，提前暴露“其实不是流式”的情况。

### 流式检查：如何避免“看起来通过了”
- **现象**：冒烟脚本的流式检查，用一个字的回复得到了“3 个分块”，我原先的判据（分块数 > 1）会判定为流式。
- **发现**：对着数字看，首块延迟 2.85s 与总耗时 2.85s 几乎相等——所有分块是同时到的，并不是逐段。回复太短，模型内部瞬间生成完，分块只是传输层的切分，其中还可能有空文本块或带用量信息的末块。
- **处理**：加一个长回答的测试，判据改为“分块数足够多，且首块与末块之间有可观的时间间隔”。重跑得到 12 个分块、间隔 1.87s，才确认真的是逐段到达。
- **附带发现**：首块延迟约 7.6s（推测是模型先思考，未查证）。前端要处理“等待首字”的状态。
- **学到**：检查的判据要能区分“真正的行为”和“碰巧相似的现象”；只会在好情况下通过的检查，通过了也没有信息量。

### 写进决策文档的“默认行为”要先验证
- **现象**：我准备在流式设计里写“redis-py 连接池默认不限连接数”。
- **做法**：写之前顺手用代码查了一下，实际 `max_connections` 默认是 100。
- **影响**：每个 SSE 客户端占一个阻塞连接，100 就是单进程并发流的天花板，设计里因此必须显式配置并把这个上限写明。
- **学到**：决策文档里的“默认值/默认行为”是日后别人最容易照着相信的内容，必须验证；这与 `psycopg_pool` 的 `min_size` 默认值是同一类坑。

### 【重点故事】测试全过，真实环境里“流式”却变成了“一次性输出”
- **现象**：SSE 相关测试全部通过。用真实 Gemini 端到端跑时，所有 token 在第 170 秒同时到达，api 日志每 5 秒一条 `Timeout reading from redis:6379`。
- **定位**：日志显示每次 `XREAD BLOCK 5000` 都在客户端抛 `TimeoutError`，我的代码把它当成“Redis 不可用”，退化成查库模式，直到 run 结束才一次性读出全部事件。我一开始猜是计时脚本的输出缓冲，日志直接否定了这个猜测。
- **根因**：redis-py 8 的连接默认 `socket_timeout=5` 秒。在连接参数里看到的是 `None`（`from_url` 没传），要在容器里查实际的连接对象才看到 5。阻塞时长也是 5 秒，而 Gemini 首字要 7 秒以上，所以每次空闲都是客户端先超时。
- **为什么测试没发现**：测试里的轮询间隔只有 0.2~0.3 秒，碰不到 5 秒的套接字超时。测试参数和生产参数不在一个量级，正好绕开了 bug。
- **修复**：阻塞读专用客户端设置 `socket_timeout = 阻塞时长 + 5`；同时把“套接字读超时”按空闲处理，与“连接失败”区分开，以后配置再错也只是多一次重连。
- **回归测试差点也是假的**：第一版断言“收到 token 时 run 仍在执行”，变异回到修复前的行为后依然通过。推演时间线后改为测延迟：让 token 恰好在修复前会“睡眠”的窗口里发出，修复前延迟 0.82 秒，修复后接近 0。
- **结果**：真实环境推送延迟 4~6 毫秒。
- **学到**：默认值要查实际对象而不是看配置；测试参数要覆盖生产参数的量级；“全部通过”之后必须用真实依赖端到端验证；回归测试本身也要用变异检查证明它能抓住 bug。

### 自己写的测试不稳定：检查之后再断言
- **现象**：SSE 断开测试 3 次失败 1 次，失败在“断开前能观察到 1 个阻塞连接”这一步。
- **定位**：打印 Redis 客户端列表时发现，循环里已经观察到 1 并跳出，紧接着的 `assert` 又重新查询了一次。读取方每 0.3 秒会“超时→查库→重新阻塞”，第二次查询恰好落在空隙里。
- **修复**：断言循环中实际观察到的值，而不是再查一次。之后连续 15 次 + 全量 28 次无失败。
- **学到**：不稳定的测试比没有测试更糟，它会教人忽略失败；对一个会变化的状态，“检查”和“断言”必须基于同一次观察。

### 测试也会“假通过”：如何证明测量手段有效
- **问题**：第一版“客户端断开后释放连接”的测试，即使服务端不释放连接也可能通过——读取方大部分时间本来就不阻塞，回复时长又和等待时长相同。
- **改法**：让 handler 发完第一个事件就长时间不出数据，使读取方持续阻塞；断开前先断言“确实能观察到 1 个阻塞连接”（证明测量手段能看到我们要找的东西），断开后连续 10 次采样都必须是 0。
- **观察方式**：从 Redis 服务端看（`CLIENT LIST` 的 `flags=b`），而不是读客户端连接池的私有计数——连接回到池里不等于服务端已经释放。

### 框架的取消语义：anyio 的电平触发
- **背景**：变异检查里，“读取时吞掉取消、继续读”这一项没有被测试抓住。
- **推测与验证**：FastAPI 的 SSE 用 anyio 的取消作用域驱动生成器。写实验对比：anyio 下吞掉一次取消，下一个 `await` 会立刻再次被取消（电平触发）；纯 asyncio 的 `task.cancel()` 只投递一次（边沿触发）。
- **结论**：在 FastAPI 里这个错误被框架兜住了，但读取逻辑以后可能在纯 asyncio 的 worker 里复用，所以代码仍然必须把取消向上抛。变异检查“存活”时要找出原因，而不是简单认为测试有漏洞或可以忽略。

### 测试工具的隐含行为：ASGITransport 会缓冲响应
- **背景**：原有的 API 测试都用 httpx 的 `ASGITransport` 在进程内调用应用。
- **验证**：写一个每 0.5 秒输出一条的流式接口，用它读取，三条数据在 1.5 秒时同时到达。
- **结论**：流式接口的“逐条到达”和“中途断开”用它测不出来，SSE 的 HTTP 层测试改为在测试里起真实的 uvicorn（端口 0，测完关闭）。

### 小坑合集（阶段 1.5）
- 临时目录里的虚拟环境被系统清理删掉了 `pyvenv.cfg`，解释器不再认为自己在虚拟环境中，报“找不到包”。先看 `sys.prefix`。
- 写进注释的因果关系也要验证：我写“在 `_astream` 里调回调会重复”，读源码后发现基类根本不把 `run_manager` 传进 `_astream`。
- 流式结束时 `langchain_core` 会补一个空的末块，处理 token 时要跳过空文本。
- 不要把整个 `.env` 导出到测试进程：里面有不需要的密钥。

### SSE 解析器：为修一个边界引入了另一个 bug
- **背景**：SSE 的行结束符可以是 `\r\n`、`\r` 或 `\n`，而网络数据块可能恰好把 `\r\n` 切在两块之间。
- **第一版做法**：块末尾是 `\r` 时先不处理，等下一块看看是不是 `\n`。
- **测试抓到的问题**：如果流只用 `\r` 换行，最后一个 `\r` 永远等不到下一块，最后一个事件就一直发不出去。在长连接里，这意味着事件被延迟到下一批数据到来。
- **修复**：规范实现的通行做法——遇到 `\r` 立即结束这一行，同时记住“刚才是 `\r`”，下一块若以 `\n` 开头就跳过。再补一个边界：中间夹着空数据块时不能把这个标记清掉。
- **怎么测的**：把同一段事件流逐字符喂入、在每一个位置切成两块喂入，结果都必须与一次性喂入完全相同；外加 `\r\n`、纯 `\r`、跨块 `\r\n`、夹空块、多字节字符跨块。
- **学到**：修边界时要问“这个改动在别的输入下会不会变成新问题”；穷举切块位置的测试成本很低，却能覆盖大部分流式解析的边界。

### 只有在真实浏览器里才会发现的问题
- 单元测试全过之后，在浏览器里实际操作又发现两个问题：
  1. 生成中刷新页面后，“等待首字”的计时从 0 重新开始——用的是浏览器当前时间而不是服务端的 run 创建时间；改正后再考虑浏览器与服务端时钟偏差，显示不小于 0。
  2. 模型一个字都没输出就失败时，出现一个空的红框，提示语还写着“已显示的内容没有保存”——这是 Gemini 真实返回 503 时才暴露的。
- **学到**：单元测试验证的是逻辑，界面的“状态组合”（刷新 × 生成中、失败 × 无内容）要在真实环境里走一遍；真实依赖的故障（503）往往比构造的故障更能暴露界面上没考虑到的状态。

### Nginx 与流式输出
- **问题**：Nginx 作为反向代理时默认会缓冲上游响应，攒够一定量才发给客户端，SSE 会变成“一次性输出”。
- **两层处理**：后端 SSE 响应带 `X-Accel-Buffering: no`（Nginx 会遵守，并且不会把这个头转发给浏览器）；Nginx 对 `/api` 再全局 `proxy_buffering off`。
- **验证**：临时去掉第二层，仅靠响应头依然逐段到达，说明第一层已经足够；保留第二层，是为了以后新增的流式接口忘了带这个头时也不出问题。
- **另外两个配置坑**：`.dockerignore` 里写 `node_modules` 只匹配根目录，要写 `**/node_modules`；`docker compose up --force-recreate <服务>` 会连同依赖的服务一起强制重建。

### 【重点故事】取消功能差点让服务关不掉
- **背景**：实现“用户取消正在执行的 run”时，执行 Agent 的任务被取消，worker 里会收到 `CancelledError`；而服务关停时，worker 自己被取消，收到的也是 `CancelledError`。
- **第一反应的写法**：只要这个 run 在“已请求取消”的登记表里，就把 `CancelledError` 当作用户取消处理并吞掉。
- **问题**：如果用户刚点了取消、服务恰好在关停，这次关停的取消也会被吞掉。纯 asyncio 的取消只投递一次，worker 回到 `queue.get()` 上就再也收不到取消，`stop()` 永远等它结束——服务关不掉。
- **修复**：用 Python 3.11 起的 `Task.cancelling()` 判断外层 worker 任务本身是否正在被取消：是就按关停处理（记为 interrupted 并继续向上抛），否则才按用户取消处理。
- **怎么证明**：写一个“用户取消后立即关停”的测试，用 3 秒超时包住 `stop()`；变异检查去掉 `cancelling()` 判断后，`stop()` 挂住、被超时抓到。
- **学到**：处理取消时要分清“谁在取消谁”；吞掉 `CancelledError` 之前，一定要确认它不是来自外层。上一阶段 anyio 的实验（电平触发 vs 边沿触发）正是理解这个问题的基础。

### 迁移只能往后加，数据迁移也要测
- **现象**：加了 `error_code` 列之后，旧的失败记录在界面上显示成“服务内部错误”，而它们实际是 Gemini 503。
- **做法**：新建数据迁移 0003，按 `error` 列里的原始报错文本回填。不改已经执行过的 0002——已执行的迁移不会再运行，改了它，开发库、测试库、将来的生产库就会不一致。
- **怎么测**：在一个独立的新库上 `upgrade 0002` → 插入“旧格式”数据（包括开发库里真实出现过的报错）→ `upgrade head` → 断言每条的错误码；还要验证已有错误码的行、非失败的行不被改动，以及幂等。
- **边界用例的价值**：“took 5003 ms”不能被当成 5xx。变异检查把正则里的整词边界去掉，这条用例立刻失败。

### 测量结论差一个数量级：测试数据的可压缩性
- **背景**：想确认“每个 run 的 checkpoint 存一份完整历史”会不会让存储平方增长。
- **第一次测量**：用 `"测" * 340` 作为每轮约 1KB 的消息，第 20 轮单个 run 只有 11KB，看起来问题不大。
- **怀疑与验证**：PostgreSQL 会对大字段做 TOAST 压缩，高度重复的文字几乎能被压没。换成随机中文（几乎不可压缩）后，第 20 轮是 66KB，20 轮累计 756KB，是对话文字本身的 18 倍。
- **学到**：做容量或性能测量时，测试数据要像真实数据，尤其是可压缩性、分布和大小；否则结论可能差一个数量级，还会让人误以为“不用处理”。

### 部分索引：写错条件不会报错，只会悄悄变慢
- **场景**：后台定期找“已结束、checkpoint 还没清理”的 run。这些行只占全表很小一部分，于是建部分索引 `WHERE finished_at IS NOT NULL AND checkpoint_purged_at IS NULL`，索引始终很小。
- **坑**：查询的 WHERE 必须“蕴含”索引条件，规划器才会用这个索引；少写一个条件，查询照样能跑，只是悄悄变成全表扫描。
- **怎么测**：测试里 `SET LOCAL enable_seqscan = off`（表很小时规划器总会选全表扫描），再 `EXPLAIN` 查询，断言计划里出现索引名。变异检查去掉一个条件，这个测试立即失败。
- **另一个常见误区**：`DELETE` 之后磁盘占用不会立刻下降——行只是被标记为死行，由 autovacuum 回收后复用，`VACUUM FULL` 才把空间还给操作系统（会锁表）。

### 变异检查要看“失败在哪”，而不只是“有没有失败”
- **场景**：测试“访问日志不记录查询串”。变异把查询串拼进路径后，测试确实失败了。
- **但失败的原因不对**：测试先用“路径完全等于 `/api/conversations`”去找这条日志记录，变异后找不到，`next()` 在异步函数里抛 `StopIteration`，被 Python 转成 `RuntimeError`——测试是在“找记录”这一步挂的，真正检查查询串的断言根本没执行到。
- **改法**：按路径前缀找记录，再单独断言路径不含查询串；重做变异，失败准确落在目标断言上。
- **同类问题**：我还写过一条“无论代码对错都会通过”的断言——在测试任务里检查一个只在 worker 任务里设置的上下文变量。这类断言比没有断言更糟，因为它给人虚假的信心。
- **学到**：一个测试有效，意味着“被测行为错了 → 它在检查这个行为的地方失败”。变异检查时要读失败信息，确认失败点。

### 一个编号串起请求和后台执行
- **问题**：用户点“发送”后，回复由后台的派发器执行；出了问题时，访问日志和执行日志之间没有联系。
- **做法**：请求进来时生成 request-id；提交消息时记一条同时带 request-id 和 run_id 的日志；派发器执行期间把 run_id 放进上下文，开始和结束各记一条（结束日志带结局和耗时）。
- **实测**：客户端传入 `X-Request-ID: demo-req-002`，按它查到“run 已提交”并得到 run_id，再按 run_id 查到“开始执行”“执行结束：succeeded，395.5ms”。
- **一开始的缺口**：成功执行的路径上没有任何日志，所以按 run_id 只能查到提交那一条——上下文里有编号，但没有日志可带。可观测性要从“排查时需要看到什么”倒推需要哪些日志。

### Vue 侦听器的引用比较陷阱
- **现象**：点“加载更早的消息”后，视图被拉回了底部。
- **根因**：侦听写成 `watch(() => [最后一条 id, 回复文本])`。getter 每次都返回一个新数组，Vue 判断“是否变化”用的是引用比较，新数组永远不等于旧数组，所以消息列表任何变化都会触发“滚到底部”。
- **修复**：改成多个源的写法 `watch([() => a, () => b, () => c], ...)`，Vue 逐个比较里面的值；并区分两种情况——最后一条变了才滚到底部，只是前面多了消息就用插入前后的高度差保持位置。
- **学到**：响应式框架里“变没变”的判断规则要清楚；用浏览器实测才发现这个问题，单测（纯函数）覆盖不到界面行为。

### 测试要测“生产代码真正执行的那条查询”
- **现象**：变异检查把对话列表查询的归档条件删掉，索引测试仍然通过。
- **根因**：索引测试对我在测试里另写的一条查询做 `EXPLAIN`，与生产查询无关。
- **修复**：把生产查询抽成函数，测试直接对它做 `EXPLAIN`；重做变异后索引测试也失败。
- **学到**：测试里“复制一份被测逻辑”是常见的假测试来源；测试应该调用被测代码本身。

### 测量判据要贴合被测对象：思考模型的“首字”
- **现象**：冒烟脚本显示 DeepSeek 的首块只要 0.16 秒，但用户看到第一个字要等 2 秒多。
- **根因**：思考模型先输出一串“思考”块（不是正文），脚本把第一个任意块当成了首字。
- **修复**：分开统计正文块与非正文块，首字按第一个正文块计时，并打印用量（含思考 token、缓存命中）。
- **学到**：同一个指标在不同对象上含义可能变了。这是这个脚本第二次因判据问题被修正——第一次是“一个字的回复也有多个分块”被误判为流式。

### 推测没复现时怎么下结论
- **推测**：文档说带工具时必须传回思考内容，而 LangChain 的 OpenAI 客户端会丢掉它，所以 OpenAI 格式做工具往返会 400。
- **实测**：两种格式都成功了。
- **结论的写法**：不是“OpenAI 格式没问题”，而是“单轮工具往返这个场景没复现，触发条件待阶段 4 多轮工具调用时再测”；默认仍选 Anthropic 格式，因为它不依赖“恰好不触发”。

### 实验结果“太好”时，先确认测到的是什么
- **场景**：比较 pgvector 与 Qdrant 的带过滤向量检索。pgvector 第一轮结果召回全是 1.000，看起来“过滤检索没问题”。
- **追问**：pgvector 有一个众所周知的问题——HNSW 先取近邻再过滤，命中率低时结果会不足。为什么没出现？
- **原因**：看执行计划，规划器根本没走向量索引，而是全表扫描 + 精确排序（命中 1% 时精确计算更划算）。
- **补测**：强制走 HNSW，复现了“只返回 0.5 条”；再测 0.8 版的迭代扫描，条数补足但召回 0.62、延迟 12ms。
- **结论反而更有价值**：小规模下“租户内精确检索”就是最优解（1.2ms、全对）；规模大了才需要带过滤的近似检索。
- **学到**：结果好得出乎意料时，先确认测量路径（执行计划、实际走的索引），否则会得出“没问题”的错误结论。同一轮实验里，我还因为等待条件写错让脚本死等、因为输出缓冲丢了一半结果，都记在 dev-log。

### 【重点故事】一个 3.3MB 的文件只切出了 1 块
- **现象**：容器里验证入库流水线时，一个 3.3MB 的测试文件（连续的字母，没有空格和标点）处理成功，却只有 1 个分块，token_count=1。
- **定位**：直接拿分词器试——`"a"*100` 是 50 个 token，`"a"*101` 只有 1 个。bge 用的 WordPiece 有一条规则：超过 100 个字符的单个“词”整体记为 1 个 `[UNK]`。分块器按 token 限长，于是整段被当成“很短”。
- **为什么严重**：真实文档里的 base64、长 URL、哈希、压缩 JSON 都会触发。这种块的向量没有意义；一旦被检索到，会把几 MB 文本塞进模型上下文，按 token 计费。
- **解法**：分块计数取 `max(模型 token 数, 字符数 / 6)`。正常文本每个 token 远不到 6 个字符，不受影响；存库的 token_count 仍是模型的真实计数。
- **顺带的性能问题**：切超长句子时，每切一段都对剩下的全部文本重新分词，耗时随长度平方增长。二分查找的上界改为 `上限 × 6` 个字符。测试不靠计时，而是用一个记录“被要求计数的最长文本”的假计数器，确定性地证明每次计数都不超过 2880 个字符。
- **反思**：2.1 时我只确认了这个文件“上传成功”，没看它被切成了什么样。验证要看结果，不是只看状态码。

### Nginx 只解析一次后端地址
- **现象**：新增 qdrant 服务后，单独重建 api，经 Nginx 的请求全部 502，日志里是 `connect() failed ... upstream: http://172.18.0.4:8000`。
- **根因**：`proxy_pass http://api:8000` 写死主机名时，Nginx 在启动时解析一次就一直用这个 IP；容器重建后 IP 变了。以前总是整套一起重建，所以没暴露出来。
- **解法**：`resolver 127.0.0.11 valid=10s`（Docker 内置 DNS）+ 变量形式的 `proxy_pass`。验证：单独强制重建 api（IP 从 .4 变为 .6）后仍正常。

### 测试要能“确定性地”发现缺陷
- **场景**：测“重建索引期间完成的文档要补录”。第一版在重建写完第一批之后处理另一个文档。
- **问题**：分块 id 是随机 UUID，按 id 翻页时它的分块有一定概率排在后面，会在第一遍里被顺带写入——去掉补录代码，测试也可能通过。
- **解法**：在“切换别名之前”那一刻注入，确定性地制造“写进了旧集合”的情形；变异检查（删掉补录）能稳定发现。
- **学到**：测试的触发条件不能依赖随机顺序；用变异检查确认它真的能抓到问题。

### 【重点故事】本机的性能结论，在容器里是反的
- **现象**：大文件入库期间，检索的重排从约 2 秒变成约 4 秒。
- **第一次判断**：在本机做实验，把入库向量化的线程数限制到 4 个，入库和重排**都变快**了（线程过多互相抢核），于是把默认值改成 min(4, 核数/2)。
- **被推翻**：在容器里复测，重排仍然慢一倍。先进容器确认设置确实生效（ONNX 会话线程数 = 4），再把同一个实验脚本放进容器跑——容器里线程越多入库越快（10 线程 28ms/块，4 线程 38ms/块）；争用时限制线程让重排快 26%，入库却慢约一倍。
- **决定**：默认改回不限（入库是后台任务，大部分时间没有检索在跑），参数保留可调；根本解法是阶段 4 拆出独立 worker。
- **学到**：性能结论要在部署环境里测；“改了设置”之后先确认设置真的生效，再判断效果。

### 分块把空白吃掉了：测试数据太“干净”
- **现象**：检索测试页面上，Markdown 的标题和正文粘成一行，英文 `Really? Yes` 变成 `Really?Yes`。
- **根因**：切句时对每句 `strip()`，拼接时用空字符串连接。2.1 的测试只用了没有空白的中文句子，所以一直没暴露。
- **解法**：切句时保留句间空白，整块输出时才去首尾空白，跨页处补换行。
- **学到**：测试数据要覆盖真实输入的形状（段落、标题、中英混排）；做一个能直接看到中间结果的页面，问题会自己暴露。

### 【重点故事】模型偶尔不检索：从改提示词到改结构
- **现象**：30 题评测里，有 1 题模型没有检索，直接反问“您指的是哪项服务？”。
- **第一次尝试**：提示词里加“先检索再追问”。重跑后这题对了，另一题又出现同样的问题——两轮的失败题不同，说明是随机波动。
- **结构上解决**：实现预检索（先用原话检索，结果放进上下文），并保留开关，用同一套评测对比：30/30，模型调用减半，更快也更省。
- **学到**：只看一轮评测，判断不了改动有没有效；“偶发”的问题优先从结构上消除，而不是继续堆提示词。每个结论都附上评测数据和费用。

### 测试替身暴露了框架的合并语义
- **现象**：测“无视检索上限、一直调用工具的模型最终会报错”，结果没有报错，图正常结束了，“回答”是检索结果的原文。
- **定位**：剧本模型每次都返回同一个消息对象。第一次返回时 LangChain 给它分配了 id；再返回时，LangGraph 的 `add_messages` 发现 id 相同，就原地替换而不是追加，最后一条消息变成了工具结果，路由直接结束。
- **解法**：替身每次返回去掉 id 的副本。
- **学到**：`add_messages` 按 id 合并（这也是“更新某条消息”的机制）；测试替身要尽量模拟真实行为，否则测出来的是替身的行为。

### 等价变异：变异检查也能发现“多余的代码”
- **场景**：分块函数里有一个变量记录“当前块开头有几句是上一块带过来的重叠”，用来避免输出一个只有重叠内容的最后一块。
- **变异**：把条件 `len(current) > carried` 改成 `if current`，所有测试仍然通过。
- **分析**：不是测试漏了——代码只在“追加新句子之前”输出一块，所以循环结束时最后一句一定是新内容，“只剩重叠”根本不可能发生。这个变异和原代码在所有输入上行为相同（等价变异）。
- **处理**：删掉这个变量，代码更简单；保留测试作为这条性质的回归保护。
- **学到**：变异存活有两种原因——测试漏了，或代码本身多余。前者补测试，后者删代码；要分析清楚是哪一种。
